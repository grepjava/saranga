# Changelog

Each release of Saranga, newest first. Saranga is inspired by Apache ActiveMQ Artemis 2.57.0 and works interchangeably with it. [COMPAT.md](COMPAT.md) lists where the two differ.

## Unreleased

### Storage

- **The relational store**: with `database-storage`, a broker keeps its messages, paging and large bodies in PostgreSQL, in the tables of Artemis pull request 6838, so that either broker opens what the other wrote. `saranga create --database-storage` makes such an instance. See docs/guide/storage.md.
- **TLS to the database**, with the JDBC driver's `sslmode` and its certificate parameters.
- **Shared-store HA** on the store: the backup opens the tables when it takes over. Replication is refused with a reason, as there are no journals to copy.
- **`data print` and `data exp`** read the tables, and `data exp` writes what Artemis's exporter writes.

### Addresses

- **Retroactive addresses** (`retroactive-message-count`), as Artemis makes them: the address keeps its last messages in an internal ring queue per routing type, fed by a divert, and a queue made on it later is given those its filter accepts. The ring queues follow the address's settings, outlive a restart, and go with the address; the address, its queues and its divert report `RetroactiveResource`.

### Fixes

- **Configuration**: `reloadConfigurationFile`, the `configuration-file-refresh-period` reload, an acceptor's `reload`, TLS store auto-reload and the acceptors a reload creates read and parse their files off the runtime workers, so a slow disk no longer stalls the connections and queues sharing that worker.
- **Paging**: a message paged in a transaction counts in its queue's `messagesAdded` (and a mirror's store-and-forward queue's) when the transaction commits, as in Artemis, instead of when it is paged, so a rolled-back paged send is no longer counted.
- **XA**: the branch `xaFailed` creates after a failover times out at the session's `xaSetTimeout` value, as a branch `xaStart` creates does, instead of the resource manager's default.
- **Metrics**: a queue's sizes and its delivering, scheduled and durable counts are kept as messages come and go, as Artemis keeps them, so a Prometheus scrape, the console's samples and the management attributes read them without walking every message the queue holds and holding up its dispatch.
- **Security**: a client certificate's subject is written as Java writes it: in the RFC 2253 form `=` and `#` are escaped wherever they are and every leading and trailing space is escaped, and the legacy form (`getSubjectDN().getName()`, which `TextFileCertificateLoginModule` users files hold) quotes a value with consecutive spaces.
- **Security**: the HTTP client of the OIDC and Kubernetes login modules decodes a chunked response once as it comes, instead of again after every read, and refuses a response over 8 MiB.
- **Configuration**: `${...}` in an `xi:include`d file is replaced in the parsed values, as Artemis's `replaceSystemPropsInXml` replaces it, so a value holding `&`, `<` or quotes is taken as it is instead of breaking (or adding to) the XML; an entity-escaped `&#36;{...}` in `broker.xml` is replaced too.
- **Configuration**: broker property `clusterPassword` is set as given, as Artemis's `setClusterPassword` sets it, instead of being unmasked again when `broker.xml` has `<mask-password>true`; an `ENC(...)` value is still unmasked.
- **CLI**: the JMS `consumer`, `browser` and `producer` take an FQQN destination as Artemis's JMS client does: `queue://A::Q` makes and uses queue `Q` on address `A` (not a queue named `A::Q`), and a non-durable `topic://A::Q` consumer takes queue `Q`, made multicast if it is not there and kept after it closes, instead of a temporary queue of its own.
- **Client**: a non-durable or auto-created queue recreated after a failover keeps its last-value key, group, dispatch and auto-delete settings, as Artemis's client sends every attribute the queue query gave, where they were left out.
- **Console**: a live view of attributes names at most 1000 of them, as an attribute read does.
- **Journal**: a scheduled delivery time set in a committed transaction stays the last one through a compaction, instead of an older one set outside a transaction taking its place after a restart (issue 129).
- **Bridges**: `destroyBridge("foo")` destroys the bridges deployed as `foo`, and no longer also stops a bridge deployed on its own as `foo-1` (issue 130).
- **Cluster**: news of a node from before its removal no longer brings the node back into the topology when the removal lands while the news is taken (issue 131).
- **STOMP**: a `no-local` subscriber no longer receives its own connection's transacted SENDs (issue 132), and an `ack:auto` subscription with a `consumer-window-size` gets its credits back as deliveries are acknowledged instead of stopping after one window (issue 133).
- **Address settings**: the cache of resolved address settings holds at most 10,000 addresses, instead of one entry for every address name ever looked up (issue 134).
- **Paging and large messages**: reading a page file, and reading, copying and syncing a large message body (for a divert, a dead-letter or expiry move, a management copy or a conversion), no longer hold up the other tasks of the runtime worker doing it while the disk is slow.
- **Management**: under the RBAC guard, hawtio's `canInvoke` of an operation with its signature (`op(java.lang.String)`) is answered for the operation, as Artemis strips the parameter list, instead of always no.
- **Management**: an attribute read over REST or management messages checks the caller's permission on its getter before the value is worked out, so a refused read no longer computes the value or writes the audit log as if it ran. The getter is `is…` for the boolean attributes Artemis's control interfaces declare so.
- **Web server**: `bootstrap.xml`'s `maxRequestHeaderSize` and `maxResponseHeaderSize` limit request and response heads, 8 KiB each by default as in Jetty (a request over its limit is answered 431, a response over its limit is replaced by a 500), where any head up to about 400 KB was taken. The `<web>` attributes Saranga's web server has no part for, and `<request-log>`, are logged as not acted on.
- **MQTT**: finding a free packet ID is a lookup, instead of a scan of every packet-ID record the session holds for each ID tried; records of deliveries completed elsewhere are still kept, as in Artemis (issue 128).
- **Selectors**: a long run of `--` or `/*` with no end lexes in linear time instead of scanning to the end of the selector again at each position.
- **Core**: a 1.x client's send with an end-of-body position far out of range is refused as a malformed packet instead of overflowing (which panicked a debug build's connection task).
- **OpenWire**: a send to a composite destination with no members (`,`) is answered instead of leaving the producer waiting for good (issue 127). XA FORGET forgets a branch that management completed heuristically, instead of always failing with `XAER_NOTA`. An XA rollback no longer unregisters a branch another session began under the same Xid after this one was completed elsewhere.
- **CLI**: `upgrade` no longer panics on an `ARTEMIS_INSTANCE_ETC` or `ARTEMIS_DATA_DIR` path ending in a multi-byte character. An empty `HAWTIO_ROLES` turns the console's role check off, as the profile's comment says and Artemis does, instead of letting no one in, and a commented-out `-Dhawtio.roles` line in the profile is no longer read.
- **Bridges**: a send the target broker had confirmed, but whose acknowledgement was still on its way when the connection failed, is acknowledged rather than sent again after the reconnect, and no longer leaves a pending acknowledgement that made the next stop wait its full timeout.
- **Security cache**: granting a login access to one more address no longer copies every address it was granted before, which made a client using many addresses cost quadratic time under the cache's lock. A permission check that has to log the user in again (its authentication cache entry expired) no longer holds up the runtime worker it runs on while an LDAP, OIDC or Kubernetes login takes its time.
- **LDAP**: a base DN in `connectionURL` (`ldap://host:389/dc=example,dc=com`) roots the user and role searches, as JNDI does, instead of being ignored. With `authentication=GSSAPI` over LDAPS, an answer of more than about 16 KB arriving at once is no longer cut short, which failed the login.
- **Masked passwords**: the default codec takes its key from the `artemis.default.sensitive.string.codec.key` system property (`-D` in `JAVA_ARGS`) before the environment variable, as Artemis does, and `password-codec` may end in `;`.
- **Replication**: a backup whose connection is lost before its synchronization gets going no longer leaves the journals, paging and large messages in replication mode, where no journal file was reclaimed or compacted and no page file deleted until another backup synchronized fully.
- **AMQP broker connections**: stopping and starting a connection at once no longer loses track of the new connection (reported as not connected, and left open on the peer by every later stop), and the stopped run no longer interrupts the new run's federation and bridges.
- **AMQP**: a transfer the client sent before it saw the broker detach its link (a drain that timed out, a refused or closed link) is dropped with the link instead of closing the whole connection with `unattached-handle`.
- **STOMP**: `content-length:-1` reads the body up to its NUL, as in Artemis, instead of stalling the connection for good; another negative length is refused.
- **MQTT**: a message that cannot be made into a PUBLISH (a malformed TEXT body, malformed ordered user property names) is discarded and its Receive Maximum slot freed, instead of stranding the slot and every later QoS 1 and 2 message (issue 126). A re-SUBSCRIBE that changes a subscription's QoS while a message is being delivered no longer leaks a slot or lets more than the Receive Maximum be in flight.
- **OpenWire**: an expired acknowledgement on a non-destructive queue expires the message, as on any other queue.
- **Journal retention and replication**: the journal file closed when a backup starts to synchronize is copied to the retention directory at once, so the name the backup is sent stays the file's name; before, a rollover under load renamed the file back while it was being sent, and the backup could not synchronize.
- **Database store**: a message acknowledged in a local transaction takes its delivery-count and scheduled-time rows with it at the commit, as one acknowledged outside a transaction does, instead of leaving them (and their bookkeeping in memory) until a restart. A prepared XA branch's paged messages are no longer deleted as unreferenced when the broker starts, which rolled the branch back.
- **Routing**: the round-robin positions of an address's bindings go with the address, and with the last binding of a routing name, instead of piling up for every address routed to (an MQTT or JMS wildcard subscription with many topics, say).
- **XA**: a message sent in a branch another session has already committed is delivered, as Artemis delivers it, instead of being lost while still counted against its address; a message acknowledged in such a branch goes back to its queue (issue 125).
- **Core**: a second CreateSession on a session channel in use no longer leaves the session it replaced running after the connection closes, which kept the connection's teardown (its temporary queues, its registration) from finishing.
- **TLS**: `sslHandshakeTimeout=0` means no timeout, as in Artemis, instead of failing every handshake.
- **Paging**: a page removed from the middle of the stream (all its messages consumed or removed) is no longer counted out a second time when the regular cleanup reaches it, which stopped paging with messages left in the current page.
- **A move whose source queue is deleted while its journal write is on its way** (an expiry, a dead-letter move, redistribution, a management move or copy) reaches its target: the queue finishes the move before it stops, instead of the copies appearing only after a restart.
- **`_AMQ_ROUTE_TO` and wildcard addresses**: a message naming a queue bound to a wildcard address that matches its address reaches it, and an exclusive divert on such a wildcard address takes it first, as for a plain message; another broker's queue on a wildcard address takes the matching addresses' messages, and redistributes them, too.
- **Deletions of one queue that overlap**: one deletes it and the other finds no such queue, instead of both succeeding, and a deletion never removes a queue created again under the same name meanwhile.
- **AMQP**: a message whose journal write or sync failed is no longer answered Accepted (nor a discharge or a settle that waited for the write); a delivery for a link the client detached never goes out on the next link attached with the same handle, and an acknowledgement answered after its session ended does not finish on a session begun on the same channel.
- **WebSocket connections** no longer stall: the writer is woken when a read flushes the frames it waits on, and frames held back are flushed after each write, for every protocol.
- **MQTT**: a PUBREC or PUBACK followed at once by DISCONNECT (or the socket closing) keeps its effect: the QoS 2 exchange gets its PUBREL when the session resumes, and an acknowledged QoS 1 packet ID is not held after a restart.
- **Configuration reload and diverts**: a reload keeps the diverts management made and those the file no longer lists (deployed again from the journal unless `config-delete-diverts` is FORCE), and updates in place a divert whose address and exclusivity are unchanged, so it never stops routing.
- **With the database store, losing the database lock stops the store's writes** at once, so that a second broker that takes the database is the only one writing.
- **`producer --data` reads a large text message back whole** from what `consumer --data` wrote, and **`data exp` leaves out paged messages of pages a queue has consumed whole** (issue 124).
- **An AMQP map key that repeats reads as its last value.** Application properties and annotations with a key given twice are seen by selectors, grouping and conversion with the value the later entry gives, as proton's decode makes it, instead of the earlier one.
- **A connection whose handling fails unexpectedly still closes cleanly.** For every protocol, its sessions close, its consumers leave their queues and give back what they held, and its temporary queues go, instead of staying behind.
- **Messages with many properties convert in time linear in their number** between Core, AMQP and OpenWire.
- With the **database store**, paged messages whose write or commit lands after higher-numbered ones are read once it does, instead of waiting until nothing else is left to read; a send that waited for room while the store failed is refused instead of accepted.
- **At start**, a message left with no reference (its queue is gone) is deleted with its large-message file, duplicate IDs stored before `persist-id-cache` was turned off are deleted, legacy pending large-message records are deleted, and page transactions no paged message names any more are deleted, as Artemis does; the start-up messages of this path carry Artemis's IDs and texts.
- **Page files**: a page with a record that does not decode is finished once what was read before it is consumed, and kept as `.invalidPage`; a record too large for a page frame is refused instead of written with a wrapped size; a page's acknowledgements are kept when its complete record or the cleanup's commit cannot be written.
- A **heuristic completion** is journaled with Artemis's boolean byte (`0xFF`); IDs asked for while the broker stops are never the same twice; IDs near the largest wrap as Artemis's do; `critical-analyzer-timeout` 0 is the default two minutes instead of none; a queue journaled before `auto-delete` was recorded is auto-delete when it was auto-created; a journaled AMQP message records its expiration only in the format that has it.
- **Database connections** use TCP keepalives and bound unacknowledged writes by `jdbc-network-timeout`, so a vanished database ends them instead of holding them for good; **`replay`** reads the retention files off the broker's own threads.
- **`populate-validated-user` without a validated user** (security disabled) drops the user a producer claimed on its message, so `reject-empty-validated-user` refuses it instead of letting it through.
- **A depaged message being delivered or waiting for its time is counted once** in a queue's `DurableMessageCount`, `PersistentSize` and `DurablePersistentSize` (and their metrics), not again with the page subscription that still counts it.
- **`deliverScheduledMessages` and `deliverScheduledMessage`** put the messages at the head of the queue in delivery-time order, and honour the queue's ring size and last value as a message falling due does.
- **A last-value queue forgets a key when its message leaves the queue**, delivered or otherwise, as Artemis does, instead of keeping every key it ever saw.
- **Journal compaction keeps a message's delivery count and scheduled time for every queue it is on**, in the broker and in `data compact`, not only the last queue's.
- **`<persist-delivery-count-before-delivery>` is honoured**: a durable message's delivery count is journaled as it is delivered, so a crash counts the delivery. A message acknowledged in a prepared XA branch counts that delivery when the branch is rolled back after a restart.
- **XA:** a prepared branch cannot be joined, nor a branch joined by a session already in a transaction; a transaction timeout of 0 is the default, and the session's timeout is the one reported; a branch the timeout rolled back ends with `XA_RBTIMEOUT`; a heuristic completion whose record cannot be deleted is not forgotten.
- **Deleting a queue whose address the user may not delete** succeeds and keeps the address.
- **A file-based lock manager's mutable longs stop with it**, so a stopped broker cannot overwrite the activation sequence, and closing an old lock a second time no longer unregisters the lock that replaced it, which stopping then left held.
- **A backup synchronizing large messages** opens each body's file as its copy starts, not every listed body's at once.
- **A queue made non-destructive, or destructive again, acknowledges each delivery as it was sent**: an acknowledgement, rejection or expiry of a delivery made before the change no longer takes the wrong message's records, and a queue made non-exclusive forgets its exclusive consumer.
- **A large message a consumer was given early (forced delivery) and then cancelled** no longer leaves the forced-delivery marker behind.
- **A large message kept in another protocol's encoding is converted whole** for an MQTT retained-message replay and for management's message views, not from its first chunk.
- **`Broker::stop` frees its ports and closes its connections**, so an embedded broker can be started again on the same ports, and a start that fails part-way stops what it had started (queues, stores, the primary lock). A connection router with a negative cache timeout, or a pool check period of 0, is refused as Artemis refuses it; a negative check period never checks.
- **`<connection-ttl-override>` is read**, and a Core connection has it from the start.
- **An expiration or expiry delay at the edge of the 64-bit range no longer panics the broker**, the arithmetic wrapping as Artemis's does.
- **Local times in zones whose offsets change on the half or quarter hour** (Adelaide, St John's, Chatham) are right; they were cached by the hour.
- **Address settings built in code without a maximum redelivery delay** use ten times the redelivery delay, as `getMaxRedeliveryDelay` does, rather than 0, which cut every delay to nothing.
- **An address paused with `persist` stays paused after a restart when its routing types change** (Artemis unpauses it), and a deleted address's or queue's pause record goes with it.
- **The expiry scan expires paged messages**, of a paused queue too, reading the pages in as Artemis's scanner does.
- **`XPATH` selectors may have whitespace before a function's parenthesis, inside empty parentheses and around `::`**, as the JDK's XPath accepts. `AMQSize` is counted instead of encoding the message for every check, and a `byte[]` property is equal to itself, as in Artemis.
- **The plugins' exception hooks hear what Artemis's hear**: a refusal by `before_send` or `before_message_route` is no longer reported to `on_send_exception` or `on_message_route_exception`, and a send that fails after `before_send` (no address, a refused permission, an empty validated user, a failed write) always is. `before_send` sees the message as the client sent it.
- **The auto-delete reaper checks a queue's message count again as it deletes it**, as Artemis's `destroyQueue` does, so a queue that took messages since the reaper looked stays.
- **A send or commit whose journal write fails gives back what it took**: the duplicate ID, so the client's retry is not refused as a duplicate, its page transaction, and the memory its messages counted against their addresses; a failed commit gives its acknowledged messages back. An XA prepare whose record fails is left active, not prepared.
- **AMQP waits for a settled acknowledgement's journal writes**, and answers a session's End once its last writes are done, as the other protocols do.
- **What reaches a transaction after the XA timeout reaper rolled it back is rolled back too**, instead of staying in a transaction that would never end.
- **A failed session stops delivering before it rolls back**, as Artemis's does.
- **Messages sent or given back to a queue as it is deleted are acknowledged**, as Artemis's destroyed queue acknowledges them, instead of counting against their address for good.
- **A temporary queue's address goes with it when its connection closes**, whatever `auto-delete-addresses` says, as Artemis forces it.
- **An ended XA branch whose commit or rollback the session refused is still rolled back if the session fails.**
- **`<enable-ingress-timestamp>` stamps messages** sent to a matching address with `_AMQ_INGRESS_TIMESTAMP`.
- **`deleteAddress` with `force` removes an address that has diverts**, unbinding them with it (Artemis leaves them registered but no longer routing).
- **A dead-letter or expiry address given as `address::queue`, reached through a wildcard queue, or bound by another broker's queue takes the message** instead of it being dropped as if the address had no bindings. An address another broker's queue is bound to is no longer removed as unused, and a forced address deletion through management removes those bindings with it.
- **A deleted address takes its duplicate-ID cache with it** (and its bridges' `BRIDGE.<address>` cache), as does the last queue of an address, as in Artemis: a queue made there again no longer refuses a message whose ID the old one had seen.
- **Two transactions committing the same duplicate IDs in different orders** no longer both fail: the IDs are checked with every cache involved held at once.
- **A notification refused by its address's limits (`FAIL`) is not sent,** instead of being queued past the limit; and the topology a cluster connection asks for (`sendQueueInfoToQueue`) goes behind what its queue has paged.
- **A management copy is routed as a sent message:** a message scheduled for later stays scheduled, the destination's expiry delay applies, and the original's `_AMQ_ORIG_*` headers are kept rather than overwritten, so a copied dead letter can still be retried. A scheduled message is copied too, and stays scheduled where it was. A moved scheduled message has its time journaled with its reference.
- **A pre-acknowledged delivery counts as acknowledged,** so the slow-consumer check no longer takes a pre-acknowledging consumer (Core `preAcknowledge`, MQTT QoS 0) for one that acknowledges nothing and kills its connection under `KILL`. A browser's deliveries are no longer counted as the consumer's, and a cancelled, rejected or closed consumer's deliveries leave its in-transit size, as in Artemis. The check turned on for a queue measures the queue's rate since the last check, or its creation, instead of taking all it ever had for one period's traffic.
- **A consumer closed with unacknowledged deliveries returns them at once,** not after the address's `redelivery-delay`, as Artemis does (`cancel` with the redelivery check ignored).
- **`purge-on-no-consumers`, and MQTT's cleanup of a session's queue and of a replaced retained message,** take the queue's scheduled and paged messages too, not only those in memory.
- **A send to a wildcard address fails** with `AMQ229260` while wildcard routing is on, as in Artemis, instead of auto-creating a queue there that takes what is sent to every address the wildcard matches.
- **Diverts:**
  - A divert deploys without an address of its own, as Artemis's binding does, and goes to work once a send creates the address.
  - A divert that would send a message back to the address it is routed to (a wildcard tap onto a matching address) leaves it alone instead of delivering it again up to sixteen times under the same ID.
  - A send to one queue (`address::queue`) is diverted as a send to the address is.
  - A copy loses the cluster's `_AMQ_ROUTE_TO`, which named queues of the original's address and lost the copy.
  - A transformer's copy goes to the address the transformer gave it, and becomes a large message when it outgrows a journal record.
- **A synchronous journal write waits for the backup while a backup is replicating.** A binding created, updated or deleted, or a prepare, commit or rollback, with no completion of its own waited only for the local write: the primary could fail with the record acknowledged and not yet on the backup. It now waits for both, as Artemis lines up every replicated operation.
- **Records appended after a journal file of format version 1 load again.** Appended to that file under its version-1 header, they were read as version 1 at the next start and lost; the old file is now kept as it is and appends go to a new one.
- **A paged AMQP large message is read back from its page.** Its saved encoding was read to the end of the record, taking the queue IDs after it, so the page was found damaged and its messages from there on were not read.
- **A non-durable large message paged out of the page cache is read from its `.tmp` file,** not looked for as a `.msg` file, which failed its consumer; and its file goes with its page.
- **A page deleted no longer takes the file of a large message another queue holds.** A large message routed to a paging queue and to one that does not lost its body file when the paging queue consumed it; the file now goes once nothing holds the message.
- **A transaction that pages a non-durable and a durable message counts both for its durable queues,** as Artemis does: acknowledging the non-durable one could complete the page transaction and drop the durable message at the next start.
- **A message paged in a transaction is not read before its transaction is known,** which skipped it for good, and a page being written to is not found complete and deleted meanwhile.
- **A paged message acknowledged in a prepared XA transaction keeps its page across a restart** until the transaction ends: the page was deleted at start, losing the message if the transaction then rolled back.
- **Acknowledgements a rolled back transaction keeps go back ahead of what their consumer was delivered since** (OpenWire, AMQP), so a later cumulative acknowledgement no longer takes a message the client never acknowledged.
- **A client failing over no longer rolls back a prepared XA branch.** `SessionXAAfterFailedMessage` made the branch rollback-only, taking it out of `xa_recover` and failing its commit; a prepared branch is now left to the transaction manager, as in Artemis.
- **A transaction that journaled nothing commits and rolls back.** A duplicate ID with `id-cache-size` 0, or the acknowledgement of a paged message on a non-durable queue, made it look persistent, and its commit or rollback failed with "Cannot find tx"; a rollback that cannot be written also gives back what it acknowledged.
- **With the database store, a send with a duplicate ID or a management move that pages its message commits the paged rows,** and a prepared XA transaction's paged sends are read from the store after its commit, not delivered from memory and then again from the store.
- **A page file that cannot be read is a critical I/O error,** as in Artemis, instead of a page with no messages: its queues passed over it, delivering the pages after it, and a cleanup could find it finished and delete it unread. A page that cannot be read for its large bodies is kept too.
- **Address settings applied to an address in use take effect at once.** A producer blocked under the old `max-size-bytes` goes on under a higher one, and new `page-limit-bytes` or `page-limit-messages` are checked then, not at the next cleanup.
- **A producer blocked by `global-max-messages` alone goes on when the broker's messages are consumed,** what waits for the broker's memory or disk alone (an anonymous AMQP producer) goes on though no address is blocked, and a paging or dropping address unblocked through management lets its producers go.
- **A transaction's paged messages are delivered in order when its commit comes while a queue is reading them:** one read after the commit no longer goes ahead of one read before it.
- **A send with a duplicate ID that pages on one address and is refused by another rolls back what it paged,** which otherwise kept that address paging for good; a management move refused the same way takes back the rows the database store paged.
- **A critical I/O error in either journal stops the other's writes too,** a journal file that cannot be opened as replication starts is one, and so is a disk the disk monitor cannot read, which was taken for a disk with room.
- **A replayed message is routed as a sent one is:** one scheduled for later (`_AMQ_SCHED_DELIVERY`) waits for its time instead of being delivered at once, a bridge's duplicate ID comes off it and a duplicate of it is not routed, and its own duplicate ID is held by the target's cache. A native large message that is not replayed no longer leaves a body file behind, and a non-durable one is replayed non-durable.
- **A prepared transaction that cannot be loaded whole is rolled back** (AMQ222306), as in Artemis: one whose sent message is missing was recovered with its other operations alone, and one with a damaged Xid stopped the broker from starting.
- **A deleted address takes its paging store and page folder,** a page folder whose address no longer exists is removed at the start, and `purge-page-folders` removes an address's folder once it stops paging, as in Artemis.
- **On a full disk, a STOMP or MQTT send is failed only where its address would block:** a management request goes on, and an address whose `disk-full-policy` is FAIL or DROP refuses or drops the message without failing the connection.
- **A journal record too large for a file after its header is refused before it is replicated,** so a backup never holds a record its primary could not store.
- **With the database store,** a prepared send's scheduled delivery row is kept at the start, a prepared transaction's other records are not taken for committed ones, the queues of an address whose routing types change follow its new ID, and a deleted queue's paged messages that nothing else references are deleted with their large bodies.
- **A management move, expiry or dead-letter that fails on a message still in its page leaves it there,** read in its turn, instead of keeping it in memory ahead of earlier messages and delivering it twice.

- **A configuration reload keeps the queues and topics of a legacy `<jms>` section.** The reload read only the core's addresses, so with `config-delete-addresses` or `config-delete-queues` set to `FORCE` it deleted the `<jms>` destinations, with their messages, as no longer configured; it now reads `<jms>` again as Artemis does, and deploys one added to it.
- **The database store gives back every setting of a queue without a last-value key.** A queue's configuration came back from its stored JSON without the fields after the (absent) last-value or group-first key, so after a restart such a queue lost its non-destructive, ring-size, auto-delete and other settings, and a non-destructive queue consumed the messages it should keep.
- **The database store keeps a large message's file while a non-durable queue still holds it.** The file went with the message's row once its durable references were acknowledged, so a non-durable queue routed the same message could not read its body; the file now goes once the row is gone and no body in memory reads it.
- **`saranga run` started from an instance whose `etc` is elsewhere keeps its data and lock in the instance.** The instance directory was taken as `etc`'s parent rather than `ARTEMIS_INSTANCE`, and the data directory ignored `ARTEMIS_DATA_DIR`, so the broker wrote its journal and lock outside the instance and the data tools, which lock the instance, ran against a live broker's journal.
- **A STOMP or MQTT subscriber that reads slowly no longer has the whole queue sent to it.** Nothing held deliveries back while the connection's writer had bytes waiting, so an `ack:auto` STOMP subscription or a QoS 0 MQTT subscription was acknowledged the queue's messages as fast as they were handed to the writer, kept in memory, and lost with the connection. As Netty's writability holds Artemis's consumers, deliveries now wait while more than the acceptor's `writeBufferHighWaterMark` (128 KiB) is unwritten and resume below `writeBufferLowWaterMark` (32 KiB).

- **The database store writes nothing more after a critical failure.** A write that failed for good, or a critical I/O error elsewhere, refused new work but let what was already queued go on to the database, and answered a queued barrier as written; what waits now fails, barriers too, as the journal stops.
- **Deleting a queue in the database store waits for its paged messages sent before it.** With more than one write connection, the deletion could commit before an earlier paged reference to the queue, leaving that reference behind; it now holds the queue's place as paged references do.
- **An MQTT client's new delayed will is not published early.** The session scan took each will it had found due only after publishing the ones before it; a client that meanwhile connected again with a new delayed will and went had that will published at once. The scan now takes a will only if it is still the one it found and still due.
- **The OIDC login's `httpTimeout` bounds the whole exchange with the provider.** Each wait on the socket was given the full timeout and a response completed after it was accepted, so a slow provider could take far longer; each wait now gets what is left, and a late response is refused.
- **A malformed chunked response from an OIDC provider or the Kubernetes API fails the login instead of its task.** A chunk size too large to add to panicked, and a chunk without its closing CRLF was misread; both are now errors.
- **A message whose ID or correlation ID reads `ID:AMQP_BINARY:` followed by other than hex digits no longer stops an AMQP consumer's connection.** Converting it for AMQP split a character of more than one byte and panicked; it is now sent as the string it is, as Artemis sends an ID it cannot decode. A `%` before such a character in an OpenWire destination's options, or in an XInclude `href` of the configuration, panicked the same way and is now kept as it is.
- **The console's pages are not sent gzipped to a client that refuses gzip.** An `Accept-Encoding` refusing gzip but accepting any coding (`gzip;q=0, *`) was read as accepting it; gzip's own entry now decides, and `*` stands only for codings not named.
- **A journal holding a damaged prepare record loads.** A prepare record whose extra-data length was damaged to a negative value could pass the record checks and stop the broker at start with a panic; it is now skipped as damage, as other damaged records are (see COMPAT).
- **Management no longer expires the messages of a mirror's store-and-forward queue.** `expireMessage` and `expireMessages` removed what the peer had yet to receive; like the expiry scan, they now leave such a queue alone, as Artemis does.
- **The expiry scan leaves a queue whose expiry address is its own address alone.** It expired the queue's messages back onto the queue as new messages, with new IDs and expiry details; it now keeps them, as management's expiry already did and as Artemis does.
- **A message rolled back on a non-destructive queue comes back to its consumer.** The consumer that rolled it back was never given it again; it now is, counted as redelivered, and a message that has used its delivery attempts goes to the dead-letter address (see COMPAT). A message taken off such a queue and then returned, as when the management call that took it could not finish, was dropped; it now goes back on the queue.
- **A browser or non-destructive consumer no longer remembers every message it was sent.** The IDs it kept to avoid sending a message twice were never forgotten, so on a last-value or ring queue a long-lived consumer's memory grew with all the traffic; it now keeps only those of messages the queue still holds.
- **A paused queue whose delay-before-dispatch has ended no longer wakes itself without pause.** Until delivery could start, the queue's task woke at once again and again, scanning for nothing; the end of the delay now wakes it once, and resuming the queue or the deliveries it waits for finishing start delivery.
- **An AMQP message not sent to a receiver gives back the link credit it took.** A message too large for the receiver's `max-message-size`, or refused by an outgoing interceptor, kept its credit counted as used, so with one credit the next message waited until the client granted credit again; it now goes at once (see COMPAT for the interceptor case).
- **A refused OpenWire XA commit or rollback keeps what the branch acknowledged.** A commit of the wrong kind, or a rollback of a suspended branch, left the branch registered but dropped its acknowledgements and the prefetch credit its consumers get back, so the completion that followed left those consumers stalled.
- **A slow login no longer holds the runtime's workers for REST requests or a management `sendMessage` as a user.** Both logged in on the worker that handled them, so an LDAP, OIDC or Kubernetes login module that took its time delayed other messaging and management work; they now log in off the workers, as the console and the protocols do.
- **A STOMP frame arriving in many pieces is decoded in linear time.** Each read searched the whole body received so far for its NUL again, so a large frame sent in small pieces took time growing with the square of its size; the search now carries on from where the last read left it, as Artemis's decoder keeps its position.
- **No AMQP message larger than a receiver's `max-message-size` is sent to it.** The limit in a receiver's attach was ignored, so a client enforcing it detached on each such message, or was sent it presettled. The message now stays on the queue for other consumers, as if this one had returned it undeliverable here (see COMPAT).
- **AMQP deliveries acknowledged in a transaction are settled once the commit completes.** Their settled dispositions were sent as soon as the discharge was handled, ahead of the commit's journal write and its `sync` mirrors' acknowledgements; they now follow the discharge's answer, as Artemis settles them after the commit.
- **An aborted AMQP delivery gives back the credit it used.** Each aborted transfer took one credit from the producer's link and none was granted in its place, so a producer whose deliveries were aborted ran out of credit and stalled. As Artemis does, a started receiver now gets the credit back, a stopping or draining one may complete its stop, and a transaction coordinator is topped up below its low mark.
- **No AMQP link is attached on a handle above the peer's `handle-max`.** The broker took its lowest free handle without regard to the limit in the peer's Begin. When none the peer allows is free, the connection is now closed with `amqp:resource-limit-exceeded` (see COMPAT). An attach on a handle above the broker's own handle-max now ends the connection with `amqp:connection:framing-error`, as Proton-J does.
- **A refused XA commit or rollback keeps its branch from another session.** The branch was taken out of the resource manager while it was checked, so another session could start its Xid meanwhile, and the refused commit (one phase for a prepared branch, or of a suspended one) could not put the original back: it was lost until a restart. It now stays registered until the commit or rollback goes ahead, and management's completion of a prepared branch does the same.
- **An MQTT client reconnecting while its delayed will is being published keeps its new will.** The old will's publication finishing marked the new connection's will sent, so it was never published if that connection failed (see COMPAT).
- **On the database store, a message a prepared XA branch paged is deleted from the tables once acknowledged.** Recovered after a restart and committed, its reference was not taken for the store's, so a non-durable message's acknowledgement left its row and the message came back at the next restart.
- **A consumer created while its queue is being deleted is refused**, where it was created on the deleted queue and received nothing; one admitted first keeps a deletion that checks for consumers from going ahead. A non-durable shared subscription joined just as its last member left was the likeliest way in (see COMPAT).
- **A large retained MQTT message replayed to a new subscription survives a restart.** The copy took a new message ID but shared the retained message's body file, named after the old ID, so after a restart it had no body and was never delivered. Its body is now copied under the new ID, as Artemis's `copy` does.
- **A non-durable shared subscription's queue goes with its last consumer**, as Artemis's transient queues do. It stayed, gathering messages for a subscription nobody held, for Core and JMS shared non-durable subscriptions and AMQP shared volatile ones alike.
- **A shared subscription's address is created whatever `auto-create-addresses` says**, as Artemis creates it; the subscription was refused (AMQ229203). A shared queue already there with another address or filter is refused with Artemis's AMQ229082 or AMQ229083, and one another subscriber made at the same moment is taken.
- **MQTT clients connecting at once with one client ID no longer both stay connected.** Each looked the ID up, took over the connection it found and then registered, so two taking over the same client both stayed on its one session; the ID is now claimed in one step, and the second takes the first over in turn (see COMPAT).
- **A send or acknowledgement after an XA transaction timed out no longer leaks.** The send's message stayed counted against its address after the session closed, so repeated sends could fill the address and block its producers; an acknowledged message was never delivered again. As in Artemis, the work goes in a new transaction rolled back at once: the send is dropped and the message returns to its queue.
- **An AMQP disposition range crossing the wrap of the delivery IDs settles its deliveries**, as Proton-J's does, where it closed the connection as a reversed range. Only a range of more than 2^31 - 1 closes it, with `amqp:not-allowed`.
- **A move whose copy cannot be routed keeps the message.** A routing error (a plugin refusing the copy) on a dead-letter, expiry or management move was taken as no route at all: the original was acknowledged and the message lost. The move now fails and the original stays, as Artemis's does. Management moves and copies to a given queue now ask the plugins too, as Artemis's routing with a target binding does, where they bypassed them.
- **Internal queues (mirror and cluster store-and-forward queues) are exempt from what Artemis exempts them from**: no dead-letter or redelivery-delay check (a returned message was dropped after 10 attempts), no priorities (they deliver in the order messages came) and no message groups.
- **A mirror's store-and-forward queue no longer expires messages**, as Artemis's does not. Expiring one acknowledged it there, which a `sync` mirror takes as its peer having it: a send completed with no peer connected.
- **A delivery a client finds expired on a non-destructive queue leaves that queue**, as a rejected one already did, so deleting the queue afterwards no longer takes a durable message from another queue (see COMPAT).
- **With `id-cache-size` 0, one transaction can send an ID twice**: the transaction's own duplicate check still ran and marked it rollback-only, though duplicate detection is off.
- **An acknowledgement mirrored to several `sync` mirrors waits for every peer**, as Artemis's mirror aggregation does; it waited for the last mirror's only, so the client could be told it was done while an earlier peer still lacked it.
- **`id-cache-size` 0 turns duplicate detection off without journaling the IDs**, as Artemis's no-op cache does. Each ID was journaled and never deleted, so the journal grew until a restart, and an ID taken by a send under way still counted as a duplicate.
- **`send-to-dla-on-no-route` takes a message the address's queues all turn away**, through their filters, routing types or being disabled, as Artemis does, not only one sent to an address with no queue: such a message was dropped without a word. As in Artemis, a divert's copies do not count, so a message only a divert took goes to the dead-letter address as well.
- **Non-exclusive diverts sharing a `routing-name` take turns**, one of them diverting each message as Artemis's routing-name groups choose, where each of them diverted a copy.
- **Rejecting a message on a non-destructive queue no longer takes it from another queue.** The rejected delivery was acknowledged while the queue kept the message, so deleting the queue acknowledged it again and a durable message held by another queue lost its record, gone after a restart. The message now leaves the non-destructive queue as it is dead-lettered (see COMPAT).
- **A rollback returns messages in the order the queue had them**, not in message ID order: IDs are given at send, and transactions can commit in another order.
- **A STOMP cumulative ACK on a non-destructive queue gives back the window credit of every message it acknowledges**; only the last one's came back, so the subscription stalled.
- **MQTT sessions the session store has paged out are restored at start.** Only the records held in memory were read, so with the store paging, clients lost their subscriptions and found no session present after a restart.
- **A restored MQTT session expiring leaves a configured shared subscription's backlog to the members still on it**, as unsubscribing already did; its cleanup emptied the queue under them (see COMPAT).
- **A revoked permission no longer comes back through the authorization cache.** A permission check in flight while a security setting changed cached the grant it had read after the change had cleared the cache, so the revoked permission held until the entry expired (see COMPAT).
- **Removing a security or address setting with a fully qualified wildcard match or a literal match removes it.** `orders::tenant.*` and `(orders.#)` were looked for where they are not stored, so the removal did nothing and the setting stayed in force (see COMPAT).
- **MQTT clients joining a new shared subscription at once all subscribe.** Those that lost the race to make its queue on a multicast address were disconnected without a SUBACK (see COMPAT).
- **A transaction that pages across several page files has them all on disk when it commits.** A page was not synced when the broker moved on to the next one, and the commit synced only the last, so a power loss could lose committed messages. Leaving a page now syncs it, as Artemis does.
- **A divert that cannot copy a large message fails the send.** The copy was skipped with a warning, so a message taken by an exclusive divert was acknowledged to the producer and stored nowhere.
- **The store takes no more writes after a critical I/O error in a page or large message file**, as COMPAT says it does after a journal's own error; a send could still succeed while the broker stopped.
- **A page file that cannot be deleted no longer brings its acknowledged messages back.** Once every message on a page was acknowledged, its acknowledgement records were deleted even when the page file itself could not be, so the messages were delivered again after a restart. The page's acknowledgements are now kept, and the failure is a critical I/O error that stops the broker (see COMPAT).
- **A large message copy that cannot be written is a critical I/O error**, as it is in Artemis, where a divert, dead-letter or expiry copy failed without one. A body file that cannot be deleted is now logged as Artemis logs it (AMQ144000) rather than as a critical error, and is left for the next start's cleanup.
- **Deleting a non-destructive queue no longer loses another queue's durable message.** The deliveries its consumers held were acknowledged along with the queued references they copy, taking a message that another queue also held down twice: its journal record went, and the other queue lost it at the next start.
- **A presettled AMQP delivery is consumed only once it is sent.** One waiting for the client's session window was acknowledged as it was queued, so if its link closed first the message was gone without having been sent. It is now acknowledged when its last frame is written, and otherwise stays on the queue.
- **A WebSocket frame length in more bytes than it needs is refused**, as Netty refuses it, with a protocol error (1002), as is an eight-byte length that is negative read as a Java long.
- **A WebSocket close is checked before it is answered.** A close carrying a status code that may not be sent (such as 1006) is answered with a protocol error (1002), and one whose reason is not UTF-8 with 1007, as Netty answers them, rather than echoed.
- **A ring queue counts what it drops as replaced.** The message a full ring queue let go was counted in `MessagesKilled` and its acknowledgement sent to mirrors. It is now counted in `MessagesReplaced` and not mirrored, as Artemis's `enforceRing` does: the target's ring drops its own copy.
- **WebSocket protocol errors give Netty's reasons.** An unmasked frame is refused with "received a frame that is not masked as expected", and RSV bits without an extension with "RSV != 0 and no extension negotiated, RSV:" and their value.
- **A scheduled message that falls due is subject to its queue's policies.** On a last-value queue it was added beside the queued message with the same key instead of replacing it, and a full ring queue took it over its size. It now replaces the last value, and a full ring drops it, as Artemis does.
- **WebSocket frames out of place in a message close the connection.** A continuation frame with no message to continue, or a new message started inside a fragmented one, was passed to the protocol as if it belonged. These, fragmented or oversized control frames, a one-byte close and reserved opcodes are now refused with a protocol error (1002), as Netty refuses them.
- **An MQTT 5 topic alias reaches the client before it is used.** With overlapping subscriptions delivering the same topic, the publication that defined a new alias could be overtaken by one on another subscription that referred to it with an empty topic, which the client cannot resolve, so it disconnected. The publication that takes an alias is now on its way before any other uses it (see COMPAT).
- **No AMQP session is begun on a channel above the peer's `channel-max`.** Answering a peer's Begin, the broker took its lowest free channel without regard to the limit in the peer's Open. When none the peer allows is free, the connection is now closed with `amqp:resource-limit-exceeded` (see COMPAT).
- **An AMQP commit that fails does not settle its acknowledgements.** When a transaction could only roll back, such as after a refused send in it, discharging it with a commit was refused, but the deliveries acknowledged in it were still settled as accepted and forgotten while their messages went back to the queue. They now stay unsettled with their consumers, as after a rollback, and are settled as accepted only once a commit succeeds.
- **An AMQP rollback keeps unsettled acknowledgements made on other sessions.** A delivery acknowledged in a transaction declared on another session of the connection was given back to the queue on rollback and delivered again under a new delivery ID, while its first delivery stayed unsettled. It now stays with its consumer as delivered, as one acknowledged on the declaring session does.
- **An MQTT client reconnecting while its expired session is cleaned up keeps its new session.** The cleanup removes subscription queues, packet ID correlations and the stored session by client ID, and went on after the client had connected again, deleting what the new session had made. A connect now waits for that cleanup to finish.
- **An AMQP session window lowered under transfers in flight lets none through.** A client that lowered its incoming window below the transfers already on their way left the broker with a window of some four billion, so it went on sending past it. The window is now counted as a signed difference and nothing is sent while it is not positive (see COMPAT).
- **A detached AMQP link's waiting transfers are not sent after its detach.** Transfers held back for the client's session window stayed queued when their link closed, and went out once the window opened, on a handle no longer attached (or one a new link had taken). They now go with the link; its messages were already returned to the queue.
- **The console's links to its other nodes acknowledge their replies.** Each management reply, including one that arrived after its request timed out, stayed on the link's reply queue for as long as the link lived.
- **AMQP credit withdrawn under a delivery in flight stays withdrawn.** A receiver lowering its link credit below what was already on the way left the broker with a credit of some four billion instead of a negative one, so it went on sending. Credit is now signed, as Proton keeps it.
- **A large message whose body cannot be read is not delivered without it.** Its consumer got an empty body (AMQP, STOMP, MQTT, OpenWire) or zeros in place of the unreadable chunks (Core), and acknowledging that lost the message. The consumer is now failed and its client told to close it, as Artemis does, and the message goes back to the queue.
- **The console asks its other nodes on the configured management address.** With a `<management-address>` other than `activemq.management`, every request the console made to another node of the cluster timed out.
- **An AMQP outcome inside a transactional state is applied as it is outside one.** A Rejected outcome wrapped in a transactional state rejected the message even with `amqpTreatRejectAsUnmodifiedDeliveryFailed=true`, so it was dead-lettered or dropped instead of returned for another try, and a Modified one ignored `undeliverable-here`, giving the message straight back to the consumer that refused it. Both now do what the same outcome does without a transaction (see COMPAT for how that differs from Artemis), and a browser's outcome leaves the message alone in both cases.
- **A `management.xml` access key is a regular expression.** `<match key="...">` and allow-list keys were matched as `*`/`?` wildcards, so a key such as `queue=secret[0-9]` matched no queue and the broader rule applied: a user it was meant to restrict could call what that rule allowed. Keys are now compiled as Artemis compiles them (`*` standing for `.*`, the whole `name=value` matched), in Java's regular expression syntax (`\Q...\E`, the ASCII `\d`, `\w` and `\p{Lower}`, `\h` as horizontal whitespace and so on). A `management.xml` whose rules cannot be read, such as one with a key that is not a valid expression, now fails the start, as it does in Artemis, where it used to be replaced by the default access list.
- **`XPATH` selectors are evaluated.** An `XPATH` selector was accepted but never matched, so a consumer or queue filtered by one received nothing. It is now an XPath 1.0 expression over the body of a text message (a Core TEXT message, or an AMQP `amqp-value` string), evaluated as Artemis evaluates it: comments dropped, a DOCTYPE refused, text left next to text joined into one node, any other body or one that does not parse not matched, and an expression that does not compile making the selector invalid. It compiles as the JDK's compiler does: no more than 10 groups and 100 operators (`jdk.xml.xpathExprGrpLimit` and `jdk.xml.xpathExprOpLimit`), and only the functions that compiler knows, each with the arguments it takes, including `lang`, `id`, `current` and `generate-id`.
- **A JSON string with a lone high surrogate is read without failing.** A `\uD800`-style escape followed by another escape that was not a low surrogate was combined with it anyway, which overflowed (a panic in a debug build, a wrong character otherwise) when management or the console read such JSON. A high surrogate now joins only a low surrogate; alone, it becomes U+FFFD and the next escape is read on its own.
- **Two transactions cannot both deliver one duplicate ID.** Each transaction checked a duplicate ID only against the cache and its own sends, and the ID joined the cache only at commit, so two transactions that sent one ID before either committed both committed and the message was delivered twice. The commit (or XA prepare) now holds its IDs, and the second to commit fails as a duplicate and rolls back. A prepared branch still holds them after a restart. A transaction that rolls back takes the ID from no other. Artemis delivers both.
- **A failed paged send with a duplicate ID leaves no copy behind.** A send outside a transaction with a duplicate ID was paged outside the journal transaction that holds the ID, so when that transaction failed the client was told the send failed but the paged message was recovered after a restart, and sending it again delivered a second copy. The page record is now written in the same transaction, as Artemis writes it.
- **Management import and `sendMessage` take a body too big for a journal record.** They sent the message as it was, so a body larger than a journal record failed with `AMQ149005`, and a large message exported from the console could not be imported again. Such a body is now stored as a large message, as a client's send is.
- **A replicating backup reports a large body or page file it could not sync.** When syncing a body or page file failed as it was closed, the backup ignored the error and acknowledged the write, so the primary counted on data the backup had not kept. The error now fails replication, as any other write failure does.
- **A copied large message can be replayed.** A large message copied to a new ID (by a divert, dead-lettering, expiry, or a management copy or move) did not record its body under the new ID for journal retention, so replaying the copy's address found nothing to replay. The copy's body is now recorded as Artemis records it.
- **A journal retention `storage-limit` smaller than one journal file is a limit.** It was divided into a whole number of files, which came to zero and counted as no limit, so the copies grew without bound. It now keeps no copy, with a warning at start. Artemis has the same rounding.
- **Retention removes the oldest copies first.** Copies made in the same second were sorted by name as text, so file 10 was removed before files 8 and 9. They are now ordered by date and then by file ID as a number. Artemis sorts them as text too.
- **Replay no longer routes a large message with part of its body missing.** When retention had removed an earlier journal copy holding some of a large message's body, `replay` assembled the chunks that were left and routed the message as if whole (a body of `prefix…suffix` came back as `…suffix`). The body is now checked against the size it was stored with (for an AMQP large message, whose record keeps no size, the file must begin with the sections its record places there), and a message the retained copies no longer hold whole is skipped with a warning. Artemis replays the part that is left.
- **A replicating backup's `group-name` chooses its primary.** A backup took the first primary in the cluster's topology whatever its group, so with several groups it could replicate another group's primary and leave its own unprotected. Brokers now announce themselves with their `group-name`, and a backup with one replicates only a primary of its group, as Artemis's does.
- **A management copy is routed as a send is.** `copyMessage` wrote the copy straight into the destination queue, so it bypassed the destination's paging and its `FAIL` address-full policy, and never reached a mirror's peer. It now goes the way a move's copy does, as Artemis routes it: paged when the destination pages, refused when the destination is full under `FAIL`, mirrored (waiting for a `sync` mirror), with the original left where it is.
- **A copy of a large message that cannot be made is reported.** When the large body could not be copied, `copyMessage` logged it and reported success though nothing was copied; it now fails the operation.
- **The console's all-nodes lists reach past a node's first 10,000 rows.** Listing across the cluster fetched at most 10,000 rows from each node, so a page beyond that came back empty though the total counted every row. Each node's rows are now fetched as far as the page asked for.
- **Stopping an acceptor closes every connection it accepted.** A connection accepted just before the stop, whose task had not yet started, missed the stop and stayed open, as did one that finished being set up after the stop had gone through the connections. So did every connection of an acceptor stopped after a pause, and of one whose acceptor settings carried no name. A stop now ends the acceptor's run as a whole: each connection of that run is closed, however far along it was.
- **A STOMP transaction's session goes when it is committed or aborted.** Each transaction ID kept its session until the client disconnected, so a client giving every transaction its own ID piled up sessions (a hundred transactions, a hundred and one sessions). Artemis does the same; Saranga now closes the session when its transaction ends.
- **A console login no longer holds a web server worker.** The login modules (LDAP and others that call out to a server) ran on the web server's async workers, so a slow login stalled other requests and enough of them could stall the console. They now run on the blocking pool, as a STOMP client's login does.
- **A move to an address that refuses it fails, and the message stays.** When moving a message (by management, to a dead-letter or expiry address, or in redistribution) to an address full under `FAIL`, the refusal was logged and the move went ahead anyway, removing the original. It now fails as a send there does, and the original stays on its queue, as in Artemis, whose move transaction rolls back.
- **A management move waits for a `sync` mirror.** `moveMessages` and the other management moves answered before the mirror's peer had the moved copies and the originals' acknowledgements; they now wait for them, as Artemis's management operations wait for their I/O.
- **Browsing a message with a NaN or infinite property gives valid JSON.** A float or double property holding NaN or an infinity was written as a bare `NaN` or `Infinity` in a browsed or listed message, which is not JSON, so the console could not show that page. It is now text (`NaN`, `Infinity`, `-Infinity`), as the export writes it.
- **`resetGroup` forgets a group on a queue with `group-buckets`.** With group buckets set, the queue keeps a group's consumer under the bucket its ID hashes to, but `resetGroup` (and the cluster's release of a group) looked it up by the ID itself, so it reported success and left the group pinned to its consumer. It now looks the group up as delivery keys it, as Artemis does.
- **An exported message with a NaN or infinite property is valid JSON.** A float or double property holding NaN or an infinity was written as a bare `NaN` or `Infinity`, which is not JSON, so one such message made the whole export unreadable to the console and the import. It is now written as text (`NaN`, `Infinity`, `-Infinity`), which the import reads back.
- **An AMQP commit through another session is made before it is answered.** A transaction declared on one session and discharged through another was answered as committed while its queue updates still waited on the declaring session, so the messages could be missing from the queue after the client was told the commit was done. The discharge's answer now waits for them.
- **An AMQP transaction left open when its session ends is rolled back.** Its sends stayed charged against the broker's memory after the connection closed, as the connection's cleanup looked for the transaction's own session, already gone. Such a transaction still outlives its session, as in Artemis, and can be discharged through another one, but rolls back with the connection through any session left, or at once when its session was the last.
- **An empty password no longer reuses a cached anonymous login.** The authentication cache now tells a missing user or password from an empty one, so with `GuestLoginModule credentialsInvalidate=true` a client sending an empty password is refused, as it is when it logs in first. Artemis's cache conflates the two.
- **A selector with a very long operator chain is rejected, not a crash.** A selector such as `x + x + … + x` with thousands of terms parsed (the parser's nesting limit bounds only parentheses and unary operators) and then overflowed the stack when evaluated, aborting the broker. The parser now bounds the depth of the expression tree it builds; `OR` and `AND` lists, which stay flat, are unaffected.
- **Committing or rolling back a prepared transaction through management waits for a `sync` mirror.** `commitPreparedTransaction` and `rollbackPreparedTransaction` reported success before the mirror peer had acknowledged what the outcome sent and acknowledged; they now wait for it, as a client's commit does and as Artemis does.
- **The console's browse, export and import drop a failed link to another node.** When the connection to a peer node failed during one of these requests, the console kept the broken link cached (and reported a 400), so later requests reused it indefinitely; it is now evicted and remade on the next request, as for operations and attributes, and the failure is reported as the node being unreachable.
- **Changing a queued message's priority reaches the paged messages too.** `changeMessagesPriority` now changes the priority of matching messages still in pages — those held in the page cache — not only the ones in memory, the way Artemis's queue iteration reaches paged messages. As in Artemis, the new priority is not written to the page file, so a paged message is read back at its original priority after a restart or once its page leaves the cache.
- **A copy of a large message whose body cannot be written fails instead of succeeding silently.** When moving, copying, diverting, redistributing or mirroring a large message to a new ID, if its body cannot be copied to the new ID's file the operation is now refused — the original stays where it is — rather than handing back a message that shares the original's body under an ID with no body of its own, which could never be recovered after a restart.
- **A reject-duplicates move journals the duplicate ID.** Moving a message with `rejectDuplicates` now records the destination's duplicate ID in the same transaction as the move, so with `persist-id-cache` it still blocks a resend of that ID after a restart, the way an ordinary send's duplicate ID does, rather than being kept only in memory.
- **A paged large message's body outlives the first queue to acknowledge it (relational store).** Under database paging, a large message read into two queues from pages no longer loses its body file when the first delivery is acknowledged: the file now goes with the message's row, deleted once no reference is left on it, instead of being deleted by whichever reader dropped its copy first.
- **A deeply nested selector is rejected, not a crash.** A consumer filter (or any selector) that nests parentheses or unary operators beyond a fixed depth is refused with an error, rather than driving the recursive-descent parser past the stack and aborting the broker. A real selector nests a handful of levels, far below the limit.
- **Concurrent large-message sends on one session stay whole.** Two producers that share a session and each send a large message no longer interleave their headers and chunks across the credit waits between them — which could stall the sends or let one message's chunks land in another's — because the whole large send is now serialized per session.
- **Exporting a paging queue returns all of its messages.** The export reads the messages still in pages as well as those in memory, so a paging queue's export is complete instead of silently dropping the paged messages.
- **A large AMQP message keeps only its headers in memory.** Its body is streamed to its file as the message arrives — the whole delivery is never buffered in memory, so a single multi-gigabyte message no longer takes gigabytes of heap — and stays in the file, read back whole only when the message is delivered, rather than being held in memory for its whole life. A restart no longer reads every large body back in either, and a large AMQP message no longer double-counts its body in the memory it charges its address. This covers client sends and messages taken in over a mirror, a bridge or a federation link.
- **Changing a queued message's priority no longer leaks its address memory or journal records, or loses a multicast message.** `changeMessagesPriority` rebuilds the immutable message with its new priority; the rebuilt message shares the reference's paging-memory charge and journal accounting, so deleting the message frees its memory and deletes its journal record, and — for a message fanned out to several queues — changing its priority in one queue no longer deletes the journal record another queue still holds (which lost that queue's copy on restart).
- **A poison-acknowledged message no longer leaks its memory or journal record.** When a client's poison acknowledgement adds the failure's cause to a message before it is dead-lettered, the rebuilt message carrying the cause now keeps the reference's accounting, so dead-lettering or dropping it frees the address memory and deletes its journal record instead of leaving them charged.
- **An address containing an apostrophe no longer breaks its dead-letter or expiry resource queue.** The address is escaped before it goes into the resource queue's selector, so an address such as `orders'west` produces a valid filter and its auto-created dead-letter and expiry resource queues are built, rather than failing to parse and dropping the dead-lettered or expired message.
- **A move to a paging address pages the copy in the acknowledgement's transaction.** Moving, redistributing, expiring or dead-lettering a message to an address that is paging now writes the copy to the destination's pages inside the same transaction that acknowledges the source, so a crash can no longer leave the copy paged while the source stays unacknowledged (a duplicate) or drop the source before the copy is durable (a loss).
- **A configured legacy `<queues>` queue survives a reload.** Under `config-delete-queues=FORCE`, a queue declared in the deprecated top-level `<queues>` is kept when the configuration is reloaded, instead of being deleted and recreated with a new identity and no messages; the retained set now counts the legacy queues as configured, not only those under `<addresses>`.
- **Concurrent user-management edits no longer overwrite each other.** File-backed `addUser`, `resetUser` and `removeUser` serialize their read-modify-write of the users and roles files, so simultaneous changes all persist rather than all but one being lost to a last-writer-wins race.
- **Cluster routing reaches an unfiltered consumer on a mixed queue.** A remote queue that has both a filtered and an unfiltered consumer is now eligible for a message the filter rejects — the unfiltered consumer would take it — where before such a message could be stranded in on-demand routing and redistribution.
- **Active-node detection checks every cluster connector.** When a replication primary restarts with `check-for-active-server`, it now keeps asking the configured connectors after a peer that does not know the node, instead of stopping at the first reachable one — so it cannot miss a promoted backup reachable through a later connector and activate alongside it.
- **A malformed AMQP disposition closes its connection cleanly.** A delivery-disposition range whose first number is greater than its last is rejected as a protocol error instead of panicking the connection task, which left the session's queue consumer registered after the socket was gone. (The AMQP CLI client guards the same range.)
- **Quorum votes keep the peer's TLS settings.** A backup voting on whether its failed primary is down now dials each peer with its advertised TLS configuration rather than a plaintext connector rebuilt from host and port, so a cluster whose quorum needs votes from TLS-only peers can still fail over.
- **A retained `$` topic is not replayed to a wildcard subscription.** A subscription whose first level is a wildcard (`#`, `+/...`) does not see `$` topics ([MQTT-4.7.2-1]); the leading-`$` exclusion now applies to retained-message replay too, which inserts directly into the queue and bypassed the routing filter, so retained and live delivery agree.
- **Journal history recovery deletes only the recovered file's own copies.** A backup file left by a broker that stopped mid-copy is matched to its history copies by the whole file ID, so recovering file 1 no longer deletes the retained history of files 11, 21, and every other ID ending in 1.
- **XA management refuses an ambiguous prepared transaction.** A base64 Xid id (branch qualifier, global ID and format ID with no lengths) can be shared by distinct Xids; when more than one prepared branch shares the id given to commit or roll back, none is completed, rather than silently completing the wrong one.
- **A routing-cache entry refreshed as it expires keeps its persisted record.** The in-memory and journal views of a key are updated under one lock order, so a `put` that renews a key no longer races its expiry and leaves the entry live in memory with its journal record deleted (lost on restart).
- **A rejected STOMP acknowledgement can be retried.** The subscription is validated before the pending acknowledgement is consumed, so an ACK that names the wrong subscription (which leaves a STOMP 1.1+ connection open) no longer discards the entry, and a corrected retry acknowledges the message instead of failing as missing.
- **A cached login holds only for the client certificate it was made with**, not for another certificate with the same subject.
- **`OIDCLoginModule` reads RFC 8705's `cnf.x5t#S256`**: a token bound to a certificate that way logs in only with that certificate.
- **One retained message per MQTT topic.** Clients publishing retained messages to one topic at the same time could leave it several.
- **STOMP frames with `content-length`** wait for their NUL. Before, how a frame was read depended on how its bytes arrived.
- **The relational store** writes a queue or address changed twice at once. PostgreSQL refused the batch, and the store failed after its retries.
- **A message sent again after a refusal is delivered.** A send outside a transaction that an address refused (full under `FAIL`, say) kept its duplicate ID, so sending it again was dropped as a duplicate.
- **Duplicate detection holds in three more cases.** One transaction sending the same duplicate ID twice is now rolled back, where both messages were delivered. A refused send no longer pushes the oldest ID out of a full cache, so that ID is still a duplicate. And an ID held twice in the cache stays a duplicate until its newer copy leaves it, where it was forgotten when the older one did.
- **A move or copy whose journal write fails** reports the error and leaves the message where it was. Before, the copy was seen and the original acknowledged, and management reported success.
- **JSON and OpenWire nested too deeply** are refused, where they overflowed the stack and ended the broker: an OIDC token, or an OpenWire frame, before its connection logs in.
- **A duplicate ID is a duplicate from the moment its transaction commits**, not only once the commit's journal record is written. A pipelined retry in that window was delivered a second time.
- **An OpenWire body allocates what it holds, not what it declares.** A stream byte array longer than the rest of the frame is refused rather than padded out to its declared length, and a compressed body is inflated only up to 100 MiB and no further than the length it declares, so a small frame can no longer make the broker allocate gigabytes.
- **A cached permission holds only for the credentials it was granted to**, not for every login under the same user name.
- **An XA commit of the wrong kind** leaves the branch to be committed or rolled back properly. Before, it was lost until a restart.
- **`handshake-timeout` covers a WebSocket upgrade**: the HTTP request and the protocol header inside the WebSocket.
- **MQTT wills and expired sessions.** An MQTT 5 will without a delay is published as soon as its client fails, not when its session expires. A session resumed without a will no longer publishes the will of the connection before. A session restored at start that expires before its client returns stays gone after the next restart.
- **A STOMP frame has a size limit**: 64 KiB before the connection logs in, 100 MiB after. A larger one gets an ERROR and the connection closes.
- **`jdbc:postgresql:` URLs are read as the JDBC driver reads them**: parameter values and the database name are URL-decoded (`%26` is `&`, `+` a space), and an IPv6 host in brackets works with a port or without one.
- **MQTT No Local** takes a client ID with a quote, and a No Local subscriber gets messages that came without a client ID (from STOMP or the Core API).
- **MQTT shared subscriptions on a configured queue** keep their backlog when a member leaves; the queue is emptied only when no member or other consumer is left on it.
- **MQTT 5 Message Expiry and Will Delay Intervals** are read as unsigned counts of seconds: a message expiry longer than about 24.8 days no longer expires the message at once, and a will delay over 2^31 seconds no longer sends the will at once.
- **A disabled queue no longer takes an anycast address's routing turns.** A message to an anycast address goes to a queue that can take it, instead of being lost to a disabled queue's turn in the round robin. The same holds for a queue that purges when it has no consumers.
- **An MQTT 5 Maximum Packet Size** is read as an unsigned four-byte value, so a client that advertises a large one (over 2^31) still receives its messages.
- **An MQTT 5 property block of 128 bytes or more keeps the payload whole.** The property length is the count of the property bytes alone, so the last property is no longer read as the start of the payload.
- **A reused session-local consumer ID is refused** instead of leaving the first consumer registered on its queue with nothing to reach it.
- **An MQTT 5 DISCONNECT with reason 0x04** (Disconnect with Will Message) publishes the will, while a normal DISCONNECT still holds it back.
- **A large MQTT 5 Session Expiry Interval** (one with the high bit set) is read as an unsigned count of seconds rather than a negative that never expires; `0xFFFFFFFF` still means never.
- **A publication discarded for a client's MQTT 5 Maximum Packet Size takes back its topic alias**, so the next message to that topic carries the full topic name rather than an alias whose defining packet the client never received.
- **An MQTT 5 acknowledgement wakes a message waiting on any of the connection's subscriptions.** A QoS 1 or 2 message held back by Receive Maximum on one subscription is delivered as soon as an acknowledgement on another frees a slot.
- **An MQTT client taken over by a new connection with the same client ID has its will published**, as any other abnormal close does.
- **An MQTT 5 wildcard subscription with Retain As Published keeps the RETAIN flag** on the messages forwarded to it live, instead of the publication being dropped.
- **Receive Maximum bounds QoS 1 and 2 messages whatever their persistence.** A non-durable message — from a non-persistent Core or STOMP producer — delivered to an MQTT subscriber at QoS 1 now counts against the client's Receive Maximum instead of slipping past it.
- **An MQTT 5 delivery larger than the client's Maximum Packet Size is discarded.** The size check counts every property length prefix, and a packet ID only when the QoS carries one, so a packet whose true size exceeds the limit is no longer sent for the client to reject.
- **A queue's `max-consumers` holds under a race.** Two sessions adding their last consumer at the same moment can no longer both be admitted: the limit is checked and the slot reserved as one atomic step.
- **A large MQTT 5 Message Expiry Interval is forwarded whole.** The remaining seconds keep their unsigned value, rather than being cut to about 24.8 days when the interval is over 2^31.
- **An MQTT 5 will keeps its publication properties.** A published will carries its Message Expiry Interval (started when the will is published), Payload Format Indicator, Content Type, Response Topic and Correlation Data, not only its user properties — so an expiring will no longer stays queued or retained indefinitely.
- **`xaStart` no longer risks a deadlock with the transaction reaper.** Replacing an open, unprepared branch releases the transaction before it touches the resource-manager table, the order the reaper and recovery already take the two locks.
- **MQTT Receive Maximum is reserved as one atomic step.** A publication fanning out to several of a connection's subscription queues at once can no longer have two of them both pass the check and send past the limit.
- **A QoS 2 message holds its Receive Maximum slot until PUBCOMP.** The slot is freed when the exchange completes, not at PUBREC, so a slow receiver cannot accumulate more incomplete QoS 2 exchanges than its Receive Maximum (an error PUBREC still frees it early).
- **A resumed QoS 2 exchange grants no extra Receive Maximum credit.** Completing an exchange that outlived its connection — a PUBCOMP for a PUBREL retransmitted on a resumed session — releases a slot only when the current connection reserved one, so the quota can no longer be driven below zero into letting an extra PUBLISH past Receive Maximum.
- **An acknowledgement after an unsubscribe still frees its slot.** A PUBACK or PUBREC whose subscription's consumer has gone (unsubscribed or closed) now completes packet-level settlement — freeing the Receive Maximum slot and waking the connection's other subscriptions — instead of leaving the slot held until the client reconnects.
- **A null Core text body is delivered as an empty MQTT payload.** A TEXT message with no body (a JMS text message without text, or a management import without a `text` member) is sent on as an empty payload rather than failing the publish and stranding its reserved Receive Maximum slot.
- **Overlapping MQTT subscriptions keep their packet IDs across a reconnect.** One message delivered to several of a client's overlapping subscriptions now records a separate correlation per delivery, so a redelivery reuses each exchange's own packet ID instead of keeping only the last and generating fresh IDs for the rest, which broke client duplicate handling.
- **A Session Expiry Interval lowered (or raised) on DISCONNECT is persisted.** An MQTT 5 DISCONNECT that changes the session expiry now writes the revised interval, so after a restart the session expires on the interval the client last asked for, not the one from CONNECT.
- **A persistent MQTT session survives unsubscribing from its last topic.** Removing the final subscription keeps the durable session record (with an empty subscription set) instead of deleting it, so a resumed or restarted session is still found; only a clean session or an actual expiry ends it.
- **An MQTT message whose topic cannot be represented is discarded, not left to stall the connection.** When a Core address reaches a subscriber as a topic that has an MQTT wildcard character, the message is discarded (its Receive Maximum slot freed and its reference settled) the way an oversized one is, rather than failing the delivery and stranding the slot so later messages cannot flow.
- **An MQTT topic or property too long for its two-byte wire length is rejected, not truncated.** A converted topic or string property over 65535 bytes is discarded rather than encoded with a wrapped length that would corrupt the packet.
- **A wildcard address keeps a literal delimiter in its word.** An escaped delimiter (`a\.b`, as an MQTT topic level containing a `.` becomes) is one word, not split in two, so a subscription like `+/c` still matches `a.b/c`.
- **Wildcard matching backtracks.** An any-words wildcard whose first candidate word leaves the rest of the pattern unmatched tries the next, and a wildcard following an any-words wildcard is matched as a wildcard rather than literal text, so patterns such as `a.#.b.c` and `a.#.*.c` match the addresses they should instead of silently missing the subscriber.
- **An expiring MQTT session is not removed out from under a reconnection.** A client that reconnects while the session scan is expiring its old session keeps its session and queues: the scan re-checks and removes atomically, rather than deleting a session the client has just re-attached to.
- **MQTT topic names convert to distinct core addresses.** A literal backslash in a topic is kept as a literal (not read as an escape), so distinct topics such as `a\/b` and `a\\/b` map to distinct addresses that round-trip, instead of colliding so a publication reaches a subscriber of a different topic.
- **A literal backslash in an MQTT topic is matched as a literal.** A topic level containing a `\` is split and matched like any other (an MQTT topic has no escape), so a wildcard subscription still matches it and the delivered message keeps its subscription identifier.
- **An MQTT subscription whose core queue name collides with another client's is refused, not mis-delivered.** The queue name is `<client>.<address>`, and either half can contain the delimiter, so distinct client-and-topic pairs can name one queue (client `a.b` subscribing to `c` and client `a` to `b/c` both name `a.b.c`). When the name already belongs to a different address the subscription is refused (a SUBACK failure) instead of reusing the queue and serving one client the other's messages.

## 1.2.0 (2026-11-02)

Faster under load, connection routers, and the rest of Artemis's login modules and SASL mechanisms.

### Performance

- **Connections run on event loops**, as Netty runs Artemis's: each connection an acceptor takes runs on one of `remotingThreads` (or `nioRemotingThreads`) single-threaded loops, with what it creates. The default is one a processor, where Artemis has three (see COMPAT.md). A delivery no longer moves between threads at each step, and p50 latency is now lower than Artemis's in every benchmark scenario, OpenWire, STOMP and MQTT without persistence included.
- **Cheaper hot paths**: sends and acknowledgements with no journal write, Core responses written straight to the socket, routing to a lone queue, paging checks, the journal's maps, and AMQP transfers sent without copying. A non-persistent message no longer overtakes a persistent one sent before it on the same session, as in Artemis.
- **Benchmarks** rerun, with charts in the README and docs/benchmarks.md, and a second run with clients written in Rust (`CLIENT=rust scripts/bench.sh`), which showed that the JVM clients, not the broker, set Saranga's Core and AMQP figures.

### Connection routers

- **An acceptor's `router`** routes each connection, once authenticated, by client ID, user, role, source address or TLS SNI host, with Artemis's five policies, pools of static connectors, discovery groups or cluster connections, a cache that can be persisted, and the redirects each protocol's clients follow (Core, AMQP, MQTT 5 and OpenWire). `ConnectionRouterControl` answers over management messages and Jolokia. `saranga-client` follows a Core redirect as the Java client does.

### Security

- **Login modules**: `OIDCLoginModule`, `KubernetesLoginModule`, `PrincipalConversionLoginModule` and the JDK's `Krb5LoginModule` with Artemis's own `Krb5LoginModule`, as Artemis 2.57.0 has them. The system's Kerberos library (MIT Kerberos, or SSPI on Windows) is loaded when first used.
- **`LDAPLoginModule`** binds with GSSAPI (`authentication=GSSAPI`), over `ldap://` and `ldaps://`.
- **AMQP SASL**: `GSSAPI`, `SCRAM-SHA-256`, `SCRAM-SHA-512`, `OAUTHBEARER` and `XOAUTH2`.

### Protocols

- **AMQP**: `maxTransfersPerDelivery`, and the broker's Open gives `failover-server-list` when this node has a backup.
- **OpenWire**: the slow-consumer advisory, `updateClusterClients` and `rebalanceClusterClients`, and a `ConsumerControl` with prefetch 0 for a queue whose `queuePrefetch` is 0 (now taken from broker properties).
- **WebSockets**: `webSocketCompressionSupported` (permessage-deflate and deflate-frame).
- **Interceptors**: `<remoting-incoming-interceptors>` and `<remoting-outgoing-interceptors>` name interceptors an embedding application registers.

### Packaging

- **A FreeBSD image** for podman with ocijail: `docker/Dockerfile.freebsd`.
