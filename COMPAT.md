# Compatibility target

| Item | Value |
|---|---|
| Reference implementation | Apache ActiveMQ Artemis |
| Pinned version | **2.57.0** (tag `2.57.0`, checked out in `reference/activemq-artemis`, git-ignored) |

Saranga aims for wire compatibility (Core, AMQP 1.0, MQTT 3.1.1/5, STOMP, OpenWire, WebSockets)
and on-disk compatibility (journal, bindings, paging, large messages) with the pinned version.
See [docs/design.md](docs/design.md) for the strategy.

## Why we build the reference from source
Artemis 2.45.0 to 2.57.0 are tagged in git, but no distribution, server jars or Docker images
were published for them. Maven Central has POMs only, and the newest published release is 2.44.0.
`scripts/build-artemis.sh` therefore builds 2.57.0 from the tag and packages it with Artemis's own
`artemis-docker` Dockerfile as `saranga/artemis-ref:2.57.0`. Clone the reference with
`core.autocrlf=false` on Windows, because CRLF line endings break the container entrypoint.

## Artemis wire quirks Saranga reproduces on purpose
Saranga matches what Artemis actually puts on the wire, including the oddities below. Do not "fix" them, or interop breaks.

- **Two boolean encodings.** `ActiveMQBuffer.writeBoolean` writes true as `0xFF`. Packets and journal records use it. Netty's `ByteBuf.writeBoolean` writes `0x01`, and `TypedProperties` and `CoreMessage` headers use that one. Readers treat any non-zero byte as true. In Saranga these are `Writer::bool` and `Writer::byte_buf_bool`.
- **Two nullable encodings.** `writeNullableSimpleString` and similar write a `0x00`/`0x01` marker (`Option<T>`). `BufferHelper.writeNullableX` and boolean presence flags write `0x00`/`0xFF` (`Flagged<T>`).
- **Property order.** `TypedProperties` iterates a Java `HashMap`. Saranga keeps decode order, so re-encoding is exact.
- **Optional trailing fields.** Many `_V2` and later packets read their newest fields only "if bytes remain". Saranga models these as `Option<T>` written only when present. Some packets (`CreateQueueMessage_V2`, `SessionQueueQueryResponseMessage_V3`, `SessionBindingQueryResponseMessage_V4/V5`, `CreateSharedQueueMessage_V2`) use a `sections` count. Set it to the struct's `SECTIONS` constant when building a packet to send.
- **`FederationConnectionConfiguration` encode/decode mismatch.** Encode writes `retryInterval` into the slot that decode reads as `maxRetryInterval`. This is an Artemis bug (ARTEMIS-6306). Saranga keeps the wire value as-is, and a Saranga downstream encodes it the same way, so the other broker gets the same configuration from either.
- **`ReplicationSyncFileMessage`.** The primary sends the whole 32 KiB read buffer even when fewer bytes were read. Only `dataSize` bytes are meaningful, and the rest is kept as `trailing`.
- **1.x message layout.** Clients older than version 129 put an extra end-of-message offset into sends and receives. Artemis ignores it on decode. Saranga keeps it so the message re-encodes exactly.
- **Not reproduced: the old prefix on the queued message.** For clients older than version 129 (Artemis 1.x and HornetQ), Artemis's `ServerConsumerImpl.applyPrefixForLegacyConsumer` puts `jms.queue.` or `jms.topic.` on the address of the message in the queue itself, not on a copy. After one such delivery the message keeps the prefix in memory: management, other consumers and a move to a dead-letter or expiry address (its `_AMQ_ORIG_ADDRESS`) see `jms.queue.orders` where they saw `orders`. Saranga puts the prefix on what it sends that client and leaves the message as it is.

## Configuration differences
- **XML that is not well formed** is refused with the JDK's messages, at the JDK's line and column, through a port of the Xerces parser Artemis reads its files with. These cases differ:
  - The messages are in English, where the JDK uses the JVM's locale.
  - In `bootstrap.xml` and `management.xml`, multi-byte encodings other than UTF-8, UTF-16 and UCS-4, such as Shift_JIS, GBK or EUC-JP, are not decoded, and a file declaring one is refused. Single-byte encodings (ISO-8859-x, windows-125x, EBCDIC code pages) are. `broker.xml` is read as UTF-8 whatever it declares, in both brokers.
  - A DTD or an external entity is read only from a file, never over the network.
  - A few files the JDK's parser accepts are then refused when Saranga builds the document: general or parameter entities that expand to markup, control characters that only XML 1.1 allows, and elements with the `xml:` prefix. No configuration Artemis ships, or that its documentation shows, uses them.
- **`bootstrap.xml`'s `<component>`s, and every `<web>` after the first,** are ignored with a warning: Artemis starts each as a Java component, and Saranga runs one web server and no Java code.
- **`${...}`** in `broker.xml`, `login.config` and broker properties resolves from `saranga run -D name=value`, then from the properties `artemis run` defines (`artemis.instance`, `artemis.home`, `artemis.instance.etc`, `artemis.URI.instance`, `data.dir`, `java.io.tmpdir` (the instance's `tmp`; on Windows Java's own, as `artemis.cmd` leaves it), `java.security.auth.login.config`), then from environment variables, else from the default after `:` (`${name:default}`), else empty, as `XMLUtil.replaceSystemPropsInString` resolves them. An instance's `bin/artemis` passes on the `JAVA_ARGS` and `JAVA_ARGS_APPEND` of the profile it loads, as Artemis's does, and `saranga run` in an instance takes their `-D` options as system properties, before its own `-D` options, which win; the other options are for Java and are ignored. The arguments are split on spaces, as `bin/artemis` splits them, so a quoted value cannot hold one. On Windows Artemis's `artemis.cmd` misspells `JAVA_ARGS_APPEND` (`%$JAVA_ARGS_APPEND%`) and so never passes it (issue 10); Saranga's passes it. `webconfig.`-prefixed system properties update `bootstrap.xml`'s `<web>` as Artemis's `Run` does: `bindings.<name>.<attribute>` and `bindings.<name>.apps.<name>.<attribute>`, a binding or app found by its name, else its `uri` or `url`, and made when there is none; a property naming no attribute is logged as a warning, where Artemis records it in its status. `securityconfig.` system properties choose the security manager as Artemis's `BrokerFactory` does: `jaas.domain` and `jaas.certificateDomain` make it JAAS with those domains, else `manager.className` and `manager.properties.<key>` a security manager with those properties, over what `bootstrap.xml` says. The security chapter passes them as `artemis run -Dsecurityconfig...`, which Artemis refuses (`Unknown option`, docs/upstream/artemis-issues.md, issue 9); `saranga run` takes `-D` options, so there it works, and through `bin/artemis` the profile's `JAVA_ARGS` works on both.
- **Broker properties** are read from `.properties` files (and any other extension) and from `.json` files, whose nested members become dotted keys as Artemis's `loadJson` makes them. YAML files are reported as a load error. The collections Saranga applies are `addressSettings`, `securityRoles`, `addressConfigurations`, `acceptorConfigurations`, `divertConfigurations`, `bridgeConfigurations`, `clusterConfigurations` and `jaasConfigs`, plus the top-level settings it supports. Every other key is reported as a warning, and, as Artemis reports it, in the broker's `Status` under `configuration.properties.<source>`, with the Adler32 checksums of its entries and of its file. The JAAS properties files read for a login are reported there too, under `server.jaas.properties`.
- **Configuration reload** swaps the security settings and address settings, reconciles diverts, and deploys and undeploys addresses and queues, as Artemis does. Bridges are reloaded too: a configured bridge that changed is deployed again, a new one deployed, and one no longer configured destroyed. Acceptors, `jaasConfigs` and AMQP broker connections are reloaded as Artemis reloads them, and each changed file (`broker.xml` or a broker properties source) reloads once. A broker connection whose configuration changed is shut down and made again, started if it was started or has `auto-start`; a new one is made; one no longer configured is shut down; and one with a `<mirror>` is left as it is, with Artemis's log line. Connection routers are reloaded as Artemis reloads them. Neither reloads the `login.config` file itself.
- **A configured legacy `<queues>` queue under `config-delete-queues=FORCE`** is kept, not deleted. Artemis decides what to undeploy by comparing against the queues declared under `<addresses>` only, while the deprecated top-level `<queues>` are deployed configuration-managed; so under `FORCE` it treats a still-configured legacy queue as unconfigured and deletes it, then redeploys it, at start and on every reload — changing the queue's identity and losing its messages. Saranga counts the legacy `<queues>` as configured, so such a queue keeps its identity and its messages across a reload.
- **Core federation** (`<federations>`) is read as Artemis 2.57 reads it, oddities included (issue 13): an `address-policy`'s hops come from a `max-consumers` attribute, not `max-hops`, so from `broker.xml` they are always 0 and a message that has crossed one federation is not federated again; `share-connection` is not read. Include and exclude matches are tested the way Artemis's `Pattern.asPredicate` tests them: the pattern is anchored only at the end, so `news.#` also matches `breaking.news.x`. Policy transformers are Rust transformers, registered by class name as diverts' are. Federation connections do not use TLS, and `federationConfigurations` broker properties are not supported. Where Artemis differs:
  - With `enable-divert-bindings`, Saranga gives up a divert's demand when the last queue it forwards to is removed. Artemis looks the queue up by its address, misses it, and keeps the remote consumer (issue 14).
  - A federated consumer that cannot find its queue on the other broker closes only its own session. Artemis also cleans up the session factory it shares with the stream's other consumers.
  - The client underneath does not reconnect by itself: when a connection fails, each federated consumer connects again (at once, then after 1, 2, 4… up to 30 seconds), as Artemis's consumers do once their locator gives up.
- **AMQP broker connections** (`<broker-connections>`) are read as Artemis 2.57 reads them, every element included. Saranga acts on `sender`, `receiver` and `peer` as Artemis does: it connects out, makes the same links for the queues that match, retries with the same counts and logs (`AMQ111001`, `AMQ111002`, `AMQ111003`), and makes the connection again when the peer closes one of its links. `BrokerConnectionControl` and the server's `listBrokerConnections`, `startBrokerConnection` and `stopBrokerConnection` work. Where Saranga differs:
  - `lock-coordinator` is not acted on, and `AMQPConnections` broker properties are not supported.
  - Two connections of the same name fail as in Artemis (no broker connections at startup, a failed reload), but the `IllegalStateException`'s message shows different hash codes for the two configurations. Java's come partly from identity hash codes, so they change from run to run.
- **AMQP federation** (`<federation>` in a broker connection, and the target end a peer's control link makes) works as Artemis 2.57's: the control link with the federation's configuration, the remote policies sent on it, the events links, local address and queue policies attaching federation receivers where there is demand (with their demand counting, stop by draining, restart, idle timeouts and hops), and the senders a peer's receivers attach to. Where Saranga differs:
  - Address federation always uses one receiver per address (the conduit consumer). `enable-divert-bindings`, `allow-wildcard-groupings` and `ignoreAddressBindingFilters=false` are sent to the peer but not acted on here: diverts are not demand, and bindings' filters are not passed on.
  - Policy transformers (`transformer-class-name`) are sent to the peer but not applied.
  - A queue receiver with no credit (`amqpCredits=0`) is given 100 credits at a time rather than pulling only while the local queue is empty.
  - On a target, the federation does not check that the connection's user may send to the addresses and queues it federates into (`AMQ111013`, `AMQ111014`).
  - The federation's management controls (source, target, policies, consumers and producers, and the remote broker connection) are not registered, and there are no AMQP federation plugin hooks.
  - The control and events links have no attach timeout (only federation receivers do, `attach-timeout`).
- **AMQP bridges** (`<bridge>` in a broker connection) work as Artemis 2.57's, and need no more of the peer than an AMQP endpoint. From policies attach receivers to the peer's addresses and queues for the demand here (a queue bound to a matching address, a consumer of a matching queue), or for every match with `disableReceiverDemandTracking`. Their demand counting, stop by draining, restart and idle timeouts work as in federation, and so do durable and shared durable subscriptions, filters, priorities and `remote-address`, its prefix and suffix. To policies attach senders from each matching address (through a temporary or durable subscription of their own) and queue. A link the peer closes is attached again after `linkRecoveryInitialDelay`, then `linkRecoveryDelay`, up to `maxLinkRecoveryAttempts`, and a close for not-found, resource-deleted or detach-forced does not fail the connection. Where Saranga differs:
  - `enable-divert-bindings` is not acted on: diverts are not demand.
  - Policy transformers are not applied.
  - A queue receiver with no credit (`amqpCredits=0`) is given `amqpPullConsumerCredits` each time it runs out, without waiting for the local queue to have no backlog.
  - Core messages are always sent converted to AMQP: no core tunnelling is offered or desired (see below).
  - There are no management controls (bridge, policies, receivers and senders) and no metrics.
  - A durable subscription a to-address policy makes takes `auto-delete-durable-subscription` and its count and delay. Artemis sets them from the new queue's own settings, so they are never applied (issue 15).
  - Once a sender the peer closed is attached again, its next recovery starts over from `linkRecoveryInitialDelay` with a fresh attempt count. Artemis's sender never hears it was attached, so its attempts accumulate across recoveries and later ones wait `linkRecoveryDelay` (issue 16).
- **AMQP mirroring** (`<mirror>` in a broker connection, and the target end a peer's mirror link makes) works as Artemis 2.57's, either way and with a mirror each way. The store-and-forward queue `$ACTIVEMQ_ARTEMIS_MIRROR_<connection>` takes every message the broker routes (a copy when it pages) and a control message for each acknowledgement and each address and queue added or removed, as `queue-creation`, `queue-removal`, `message-acknowledgements` and `address-filter` allow. The mirror link carries them with Artemis's delivery and message annotations, and checks the peer's `amq.mirror` and broker ID (`AMQ119018`, `AMQ119019`, `AMQ119022`). The target routes what it gets locally, without diverts, keeping each message's broker and ID (`x-opt-amq-bkr-id`, `x-opt-amq-mr-id`) and dropping duplicates. It applies acknowledgements through the `AckManager`, which retries those whose message it cannot find yet, on the queue then in its pages (`mirror-ack-manager-*`), journaling them as `ACK_RETRY` records. Neither end sends back what the other sent, and with `sync` a client's send, acknowledgement or commit is answered once the peer has it. Where Saranga differs:
  - Core messages are always sent converted to AMQP: no core tunnelling is offered or desired, where Artemis's mirror desires it by default.
  - A message routed to chosen queues of its address (`_AMQ_ROUTE_TO`, from a cluster node) is mirrored without the queues (`x-opt-amq-mr-trg-q`), so the peer routes it to all of the address's queues. The target honours the annotation when it gets one.
  - An acknowledgement is put in the store-and-forward queue once made, after its transaction commits; Artemis routes it in the transaction. Control messages join the queue as their record is written, not once it is.
  - The target does not withhold credit while its `AckManager` holds more than `mirrorMaxPendingAcks`, and `ackManagerFlushTimeout` and `mirror-page-transaction` are not acted on. Retries look among scheduled messages too.
  - There are no mirror metrics or management beyond the store-and-forward queue's own control.
- **Namespaces.** Elements are matched by local name, so prefixed elements that Java would miss are accepted.
- **Features Saranga does not have.** A colocated backup (`<colocated>`) and the JDBC journal (`<database-store>` without `database-storage`) stop the broker from starting with a reason, and so does replication with `database-storage`, which has no journals to copy. Starting anyway would pretend to be something it is not. The following elements are read but not acted on, each with a warning: `scale-down`, `<lock-coordinators>`, the metrics plugin (`<metrics>`, `<metrics-plugin>`; the web server's metrics app exports metrics without them) and `<resource-limit-settings>`. `<cluster-connections>` with `static-connectors` or a `discovery-group-ref` are read: a backup announces itself to its primary through one, and a replicating backup finds its primary through one, so that clients get the pair in their topology, and the topology a cluster connection's node announces is sent to clients. Cluster connections move messages between the nodes, redistribute them to nodes with consumers and keep message groups together with a grouping handler; `<federations>` federate addresses and queues from other brokers (see Phase 10 in PHASES.md).
- **On-demand routing to a remote queue with mixed consumers.** When a cluster node decides whether a remote queue would take a message (on-demand load balancing and redistribution), Saranga reports the queue as eligible if it has any consumer with no filter, even alongside filtered consumers whose filters reject the message — the unfiltered consumer would accept it. Artemis's `RemoteQueueBindingImpl.isHighAcceptPriority` reports the queue eligible only when it has no filtered consumers or one of their filters matches, because an unfiltered consumer is counted but not recorded among the filters; so a message a filter rejects can be stranded even though an unfiltered consumer is present. Saranga delivers it.
- **Discovery** (`<broadcast-groups>`, `<discovery-groups>`) is over UDP multicast only: a JGroups group (`jgroups-file`) stops the broker from starting with a reason. The datagrams are Artemis's, so Java and Saranga brokers and clients hear each other. As in Artemis 2.57, discovery is off unless the `artemis.discovery.enabled` system property (given to `saranga run` with `-D`, or in the profile's `JAVA_ARGS`) or the `ARTEMIS_DISCOVERY_ENABLED` environment variable is `true`: a broker with broadcast or discovery groups then does not start (`AMQ229262`, `AMQ229263`), and a `udp://` URL is refused (`AMQ219070`). A broadcast group starts once the broker is active, so a waiting backup does not broadcast. As `parseBroadcastGroupConfiguration` reads them, every `connector-ref` of a broadcast group is its first one. A client resolves a connector's host to its IPv4 addresses first, as Java does, so `localhost` is 127.0.0.1 before `::1`.
- **Core bridges** (`<bridges>`, or `createBridge` through management) forward a queue to another broker as `BridgeImpl` does: the same sessions (pre-acknowledging, with the bridge's confirmation window and producer window), `_AMQ_BRIDGE_DUP` with duplicate detection and blocking sends without it, each message acknowledged on the queue once its send is acknowledged, and reconnection to the same node `reconnect-attempts-same-node` times before the static connectors or the discovery group. Another protocol's message (AMQP) goes embedded in a Core message (`EMBEDDED_TYPE`, `LARGE_EMBEDDED_TYPE`) and a broker receiving one over Core takes it out again, as Artemis does. A bridge that fails to authenticate stops the broker's bridges, broadcast groups and cluster connection (`AMQ224058`). Bridges created through management are journaled (`BRIDGE_RECORD`) and deployed again on restart. Differences: a large message is read whole into memory before it is sent, and `pause` and `resume` (which no control exposes) are not there.
- **saranga-client's confirmation window** answers each send through the async response cache and confirms what it receives, but keeps no resend cache: after a failover a session is recreated, not reattached, and the sends still awaiting their response fail (`sendFailed`).
- **Acceptors** pick each connection's protocol from its first 8 bytes, as Artemis does, among the protocols the acceptor lists. Saranga serves all six of Artemis's: CORE, AMQP, STOMP, HORNETQ, MQTT and OPENWIRE. HORNETQ is Core with HornetQ 2.x clients' handshake, which they may leave out, and with their `_HQ_` property names and `HQ` filter identifiers converted both ways, as Artemis's interceptors convert them. A host binds to the address Java's `InetAddress.getByName` gives, which is IPv4 first, so `localhost` means 127.0.0.1 as it does for Artemis.
- **Remoting threads.** An acceptor's connections run on `remotingThreads` (or `nioRemotingThreads`) event loops, read as `NettyAcceptor` reads them, but the default is one a processor, where Artemis's is three. A loop also runs the queues its connections create, and more loops than processors only had them wake each other more often (with 100 queues, a third more CPU a message and a higher p50).

## Persistence differences
- Saranga writes journal files the way Artemis's `NIO` journal does: records follow each other without block alignment, whatever `journal-type` says. Artemis reads such files with any journal type, and Saranga reads `ASYNCIO` files (aligned flushes padded with zeros).
- Appends wait while the journal compacts; Artemis keeps appending and replays the appends afterwards. The compacted files are the same.
- Group commit comes from a flusher thread that syncs whatever accumulated while the previous sync ran, rather than `TimedBuffer`'s timer, so `journal-buffer-timeout` has no effect.
- `server.lock` holds the node ID and state as in Artemis (`0`, `F`, `L` and `P`), and the primary and backup locks are locks on `serverlock.1` and `serverlock.2`, all taken as Java takes them: `fcntl` record locks on Unix, `LockFileEx` on Windows. A Java broker and a Saranga broker therefore exclude each other on one journal directory, and either can be the other's shared-store backup. As in Artemis, a primary whose lock another broker holds waits for it, for `journal-lock-acquisition-timeout`.
- **Shared-store backups.** A backup waits for the backup lock, then for its primary to fail, as Artemis's does, and its web server and acceptors start once it is active. It announces itself to its primary through its cluster connection (`NodeAnnounce`), and, once active, hears the restarted primary announce itself the same way and gives way to it (`allow-failback`), waiting as a backup again with `restart-backup`. Without a cluster connection it logs `AMQ222308` as Artemis does.
- **Replication.** A replicating primary and backup each keep their own data, as Artemis's do, and neither takes the primary lock. The backup moves its old data to `oldreplica.N` (`max-saved-replicated-journals-size`), registers with the primary through its cluster connection, copies the primary's journal files under their file IDs, its page files and its large messages, then gets every record, page write and large-message write as the primary makes it; a client is answered once the backup has what its operation wrote. When the primary's connection goes, a synchronized backup asks the other primaries of the cluster whether they still see its primary (in a single pair nobody is asked and it takes over at once), and becomes active on its copy with the primary's node ID, logging `AMQ221007` as Artemis does; a backup not yet synchronized starts again. A primary that loses its backup goes on alone, after a vote with `vote-on-replication-failure`. Each broker announces itself with its `group-name`, and a backup with one replicates only a primary of its group, as in Artemis. A primary with `check-for-active-server` that starts while a broker of the cluster is active with its node ID (which it checks with a session as the cluster user, as Artemis does) moves its data aside and replicates that broker, asking it to hand back; a broker that allows it (a backup with `allow-failback`, or a primary, which always does) waits for the new backup to announce itself, tells it to take over (`STOP_CALLED`, then `FAIL_OVER`), stops and replicates it again as its backup, logging `AMQ221039`. When it does not allow it, the restarted primary logs `AMQ224056` and stays its backup.
- **Replication's `cluster-name`** picks the cluster connection a replicating backup and primary use, as the manual says, on a backup too: the backup finds its primary, and announces itself, through it. Artemis 2.57 sets it for a colocated backup only (`haStarted`), so its replicating backup uses the first cluster connection whatever `cluster-name` says, and one that cannot reach the primary leaves it waiting (issue 21). A primary, and a backup's announcement to its primary, use it in both. A name no cluster connection has fails the activation with Artemis's `Missing cluster-configuration for replication-clustername` message.
- **Replication with a lock manager** (`<manager>` in the replication `primary` or `backup`). Saranga has Artemis's two managers, by their class names: Curator's ZooKeeper manager (`CuratorDistributedLockManager`, the default, and the deprecated `CuratorDistributedPrimitiveManager`) with its properties (`connect-string`, `namespace`, `session-ms`, `session-percent`, `connection-ms`, `retries`, `retries-ms`; any other is refused as Artemis refuses it), and `FileBasedLockManager` (`locks-folder`). The ZooKeeper client is Saranga's own, and makes the znodes Curator makes: a node's lock is the one-lease `InterProcessSemaphoreV2` at `/<node ID>/locks`, with its mutex and protected sequential nodes, and its activation sequence the `DistributedAtomicLong` at `/<node ID>/activation-sequence`. So a Java and a Saranga broker coordinate on one ensemble. The local sequence is `server.activation.sequence` beside `server.lock`. A broker is active only with the node's lock and a local sequence the coordinated one has not passed (`ActivationSequenceStateMachine`, unfinished claims repaired as Artemis repairs them), and it claims and commits the next sequence first. A primary whose data is stale replicates the broker active with its node ID, asking for failback. A backup activates once the primary is gone, its copy complete and the lock free, which after a crash is when the primary's ZooKeeper session expires. An active broker that loses its backup moves the sequence on, so the backup's copy cannot activate. One that loses the lock or the ensemble stops ("Quorum UNAVAILABLE"). A broker that hands back (`allow-failback`) waits for the other to activate before replicating it (`AMQ221039`). `coordination-id` is applied as Artemis applies it (16 characters at most, `+` padding, dashes made dots) and written to `server.lock` as `setNodeID` writes it. `artemis activation list` and `activation set` read and force the local and coordinated sequences. Lock coordinators (`<lock-coordinators>`, a technical preview in Artemis) are not implemented.
- When an update changes a queue's filter (configuration reload, or management), the queue binding record Saranga writes holds the new filter. Artemis 2.57.0 writes the old one, because `QueueImpl.setFilter` does not update the queue's `QueueConfiguration`, which is what gets journalled (drafted upstream in [docs/upstream/artemis-issues.md](https://github.com/grepjava/saranga/blob/main/docs/upstream/artemis-issues.md), issue 2). The record has the same layout, and either broker reads the other's. A queue whose filter was changed by a Java broker and not by broker.xml therefore comes back on Saranga with the old filter, as it would on Artemis. Queue queries, as on Artemis, keep reporting the old filter until restart.
- A message to an anycast address goes to a queue that can take it: the round robin passes over a queue that is disabled, or that purges when it has no consumers and has none, as it passes over one whose filter does not match. Artemis 2.57.0 chooses the binding first and drops the message when the chosen queue is disabled, so a fraction of sends to an address with a disabled queue reach no queue at all.
- A session-local consumer ID identifies one consumer: reusing it on the same session is refused (`IllegalState`). Artemis registers the second consumer on its queue and keeps only it in the session's map, leaving the first on the queue, reachable by nothing and not closed when the session closes.
- The XA error messages print `XidImpl (<n> ...` with a hash of the Xid where Java prints an identity hash.
- **Journal retention** (`<journal-retention-directory>`) works as in Artemis. Each message-journal file the journal moves on from is copied to the retention directory as `activemq-data-<yyyyMMddHHmmss>-<id>.amq`, named in local time. Copies older than `period`, or beyond `storage-limit`, are removed, oldest first by date and then by file ID as a number. Artemis sorts the copies' names as text, so among copies made in the same second it removes file 10 before files 8 and 9. A `storage-limit` smaller than one journal file keeps no copy (a warning says so at start); Artemis counts it as no limit, and the copies grow without bound. Paged messages and large-message bodies are also written to the journal as events, so the copies hold them, and `data compact` keeps the compacted files in the history. The broker's `replay` operations route the retained messages again. A large message whose body the retained copies no longer hold whole (a copy with its first chunks was removed) is not replayed, with a warning; Artemis replays the part that is left as if it were the whole body. Artemis's `data print --journal <retention>` reads Saranga's copies, and the other way round. When a start recovers a backup file left by a broker that stopped mid-copy, Saranga removes only that file's own history copies, matching the whole file ID (`-<id>.<ext>`); Artemis matches `<id>.<ext>` with no delimiter, so recovering file 1 also deletes the history of files 11, 21, and every other ID that ends in 1.

## Paging differences
- **Paging needs persistence.** Without `persistence-enabled`, Artemis still writes page files (its null storage manager keeps no journal but the page store works); Saranga keeps every message in memory, and only BLOCK, FAIL and DROP limit an address.
- **Full disks** are handled as Artemis handles them: every `disk-scan-period` the stores' disks are checked against `max-disk-usage` (or `min-disk-free`, which wins when both are set), and while one is past it each address does what its `disk-full-policy` says (BLOCK, FAIL or DROP), with Artemis's log messages; the management address, which has no paging store, is never blocked. Connections without flow control (STOMP, MQTT and management's `sendMessage`) cannot be held back, so while the disk is full a send from one fails it with `AMQ229119`, as Artemis does. The usage is read from the operating system (`statvfs`, `GetDiskFreeSpaceExW`).
- **Queue browsers** see the messages a queue holds in memory, including those read in from its pages up to `max-read-page-messages` and `max-read-page-bytes` (1,000 messages when neither is set), but not the rest of a longer backlog. Artemis browsers read through the page files as well (`QueueBrowserIterator`).
- **Page counters** are rebuilt from the page files at every start, and the counter records Artemis writes are deleted when Saranga loads them. Artemis rebuilds its counters the same way when the records are missing, so the data directory still moves back.

## Queue semantics differences
- **Wildcard address matching — Artemis bugs not copied:**
  - **An escaped delimiter stays in its word.** Saranga splits an address into words on the delimiter but not on an escaped one (`a\.b` is one word), so an address with a literal delimiter — as an MQTT topic level containing a `.` becomes (`a.b/c` → `a\.b.c`) — matches a subscription like `+/c` (`*.c`). Artemis's `AddressImpl` splits on every delimiter, reading `a\.b.c` as three words, so the subscription silently misses the message.
  - **Matching backtracks and reads a wildcard as a wildcard.** Saranga matches the word lists so an any-words wildcard whose first candidate word leaves the rest unmatched tries the next, and a wildcard after an any-words wildcard is a wildcard, so `a.b.b.c` matches `a.#.b.c` and `a.b.c` matches `a.#.*.c`. Artemis's `AddressImpl` takes the first candidate and never backtracks, and compares the word after an any-words wildcard as literal text, so both miss and the subscriber is silently not routed to.
- **delay-before-dispatch** ends on a timer. Artemis has no timer: it starts dispatching at the next delivery attempt after the delay, such as a new message, a consumer's credits or a forced receive.
- **Last-value queues** drop a replaced value as soon as its replacement arrives. Artemis prunes on its next delivery pass. The queue holds the same messages afterwards.
- **Message groups.** While a group's consumer has no credit, only that group's messages wait. Artemis ends the whole delivery pass at that point.
- **Clustered grouping.** When the queue a grouping handler named is gone, Saranga retries only that routing name, so the message's other routing names do not get it twice.
- **Duplicate detection** checks the message a client sends. Copies a divert makes are not checked against the forwarding address's cache.
- **Duplicate detection where Artemis lets a duplicate through:**
  - A transaction that sends one duplicate ID twice is rolled back. Artemis adds the ID to the cache only at commit, and checks each send against the cache alone, so it delivers both.
  - A send refused after its duplicate check (an address full under `FAIL`) leaves the cache as it was. Artemis has already added the ID, pushing the oldest one out of a full cache, and takes back only the new one.
  - Of two transactions that send one ID before either commits, the second to commit (or to prepare, for XA) fails as a duplicate and rolls back. A prepared branch holds its IDs until it ends, after a restart too, so another send of one meanwhile is a duplicate. Artemis checks the ID only when it is sent and adds it to the cache at commit, so both commit and the message is delivered twice. A transaction that rolls back takes the ID from no other.
- **A prepared XA branch's duplicate IDs** keep their own journal record IDs after recovery. Artemis files them under the transaction's ID.
- **A prepared XA branch's record deletes** on the relational store wait in `DB_BROKER_DATA` as rows of type 201, where Artemis deletes at the prepare and cannot undo it at a rollback. Artemis warns of such a row and finishes the transaction without that delete; the next Saranga start removes the row.
- **An XA commit of the wrong kind** (one phase for a prepared branch, two phase for one not prepared) is refused and leaves the branch as it was, to be committed or rolled back properly and recovered. Artemis takes the branch out of its resource manager before it checks, so the branch is gone until a restart.
- **Large-message files** are deleted once nothing holds the message any more, which is when Artemis's reference count releases it. When the broker stops, the files of messages still in memory are kept, as Artemis keeps them.
- **Auto-created dead-letter and expiry resource queues for an address containing an apostrophe** are built and receive the dead-lettered or expired message. Artemis puts the address into the resource queue's selector (`_AMQ_ORIG_ADDRESS = '<address>'`) unescaped, so an address such as `orders'west` makes an unparseable filter, the resource queue is not created, and the message is dropped. Saranga doubles the embedded apostrophe, as a selector string literal requires.
- **A selector nested beyond 64 levels** of parentheses or unary operators is rejected. Artemis parses much deeper selectors: its generated parser recurses on the JVM stack, and it catches the `StackOverflowError` a pathological one throws (`SelectorParser.parse` wraps the parse in `catch (Throwable)`) and reports it as a filter error. Saranga's recursive-descent parser cannot catch a Rust stack overflow — it would abort the process — so it bounds the nesting instead. For the same reason a selector whose expression tree is more than 128 levels deep is rejected: the binary operators (`+`, `-`, `*`, `/`, `%`, `=`, `<>`, comparisons, `IS NULL`, `LIKE`) build a chain as deep as it is long, so `a + a + … + a` with a few hundred terms parses in both brokers but overflows the stack when it is evaluated — Artemis's `FilterImpl.match` lets the `StackOverflowError` unwind the thread, where it would abort Saranga. `OR` and `AND` build flat lists and are not limited this way. A real selector nests a handful of levels, so nothing a client would write is affected.
- **An `XPATH` selector over a body nested more than 1,024 elements deep** does not match it, and the body is not parsed. Artemis parses and evaluates any depth. Parsing such a body here would take time growing with the square of its depth, and evaluating it recurses on the stack, for a body any sender chooses.
- **An `XPATH` selector's groups and operators** are limited to the JDK's defaults, 10 and 100, as Artemis has them on any current JDK, but cannot be raised with `-Djdk.xml.xpathExprGrpLimit` or `-Djdk.xml.xpathExprOpLimit`. In it, `system-property('name')` is `''`: Artemis answers a name without a prefix from the JVM's system properties.
- **A `management.xml` key** is read in Java's regular expression syntax, except for what has no equivalent here: `\G`, `\X`, `\N{...}`, `\b{g}`, Unicode blocks (`\p{InGreek}`), `java...` properties, `--` in a class, and the `d`, `s` and `U` flags. A key using one fails the start, where Artemis would take it. The `i` flag folds case beyond ASCII, as Java's does only with `u`.
- **Changing the priority of paged messages** (`changeMessagesPriority`) reaches the messages still in pages that are held in the page cache — the page being written and the last few read. A message in a page beyond the cache keeps its priority until its page is read. Artemis's queue iteration depages messages into memory as it goes and so reaches further down the backlog, bounded instead by `max-read-page`. Neither broker writes the new priority to the page file, so after a restart a paged message is read back at its original priority.
- **Divert transformers** are Rust plugins, not Java classes. The embedding application registers a `Transformer` under the class name that `broker.xml` gives. A divert whose transformer is not registered is not deployed, and a warning is logged.
- **A large message's body failing to read part-way through a Core delivery** fails the consumer, as a failure before the first chunk does in both brokers, and the message goes back to the queue when the client closes it. Artemis logs the error and leaves the delivery unfinished, holding the consumer.

## STOMP differences
- **The `server` header** of CONNECTED is `Saranga/<version>`. Artemis sends `ActiveMQ-Artemis/2.57.0 ActiveMQ Artemis Messaging Engine`. `disableStompServerHeader` leaves it out on both.
- **`AMQ339011 Error sending message`** names the message by its ID, durability and address. Artemis prints the whole `CoreMessage.toString()`.
- **Byte-array properties** appear in MESSAGE headers as `[B@` followed by a hash of their contents. Artemis prints the array's identity hash. Neither means anything to a client.
- **The connection TTL** closes a silent connection when it runs out. Artemis notices at its next `connection-ttl-check-interval`, up to that much later.
- **A `\r` that is the last byte read** waits for its `\n`. Artemis reports `There is a CR not followed by an LF` when the two arrive in different packets.
- **A STOMP 1.1 or 1.2 frame with `content-length`** ends at the NUL after its body, as in Artemis, but Saranga waits for that NUL. When the bytes between the body and the NUL arrive in a later packet, Artemis has already taken the frame and reads them as the start of the next one.
- **Frame size:** a frame still arriving may hold up to 64 KiB before the connection logs in and 100 MiB after (ActiveMQ's default `maxFrameSize`). A larger one gets an ERROR and the connection closes.
- **A rejected ACK keeps its pending acknowledgement.** Saranga checks the subscription (including the `subscription` header) before it consumes the pending acknowledgement, so an ACK that names the wrong subscription — which under STOMP 1.1+ leaves the connection open — can be retried with the right one. Artemis removes the entry first, so the corrected retry fails as `failToAckMissingID` and a `client-individual` delivery stays unacknowledged and uncredited until the connection closes.
- **A transaction's session ends with it.** COMMIT and ABORT close the session the transaction ran in, so a client that gives each transaction its own ID keeps one session, not one per transaction. Artemis keeps each transaction's session until the connection closes (`StompSession.end` only clears its pending flag), so its session count grows with every transaction ID used.

## MQTT differences
- **Artemis bugs not copied.**
  - **Live retained messages to MQTT 5 wildcard subscriptions:** a retained PUBLISH sent while a client is subscribed by a filter other than the exact topic (such as `a/#`) never reaches that client in Artemis, where `sendMessage` looks the subscription up by topic name and throws a `NullPointerException` that drops the delivery (logged `AMQ832000`). Saranga delivers it. The retain flag is kept when the subscription that delivered the message asks for retain-as-published, found by its consumer rather than by the topic name, so a wildcard retain-as-published subscription keeps it too.
  - **Retained messages published at once:** Artemis looks up a topic's retained-message queue and creates it if missing without a lock. When the first retained messages to a new topic arrive together, all but one publisher fail with `AMQ229019` (queue already exists): the client gets no PUBACK and the message is lost. Saranga handles one topic's retained messages one publish at a time, from creating the queue to replacing the message.
  - **Retained `$` topics and wildcard subscriptions:** Saranga applies the leading-`$` exclusion ([MQTT-4.7.2-1]) when replaying retained messages, so a wildcard-leading subscription (`#`, `+/...`) does not receive a retained `$secret/status`, matching live routing. Artemis replays retained messages with `sendMessageDirectlyToQueue`, which bypasses the subscription queue's routing filter, so the same `#` subscriber receives the retained `$` topic that a live publication would not reach. An explicit `$`-leading filter receives it on both.
  - **Packet-ID records on a clean start:** Artemis's `JournalHashMap.clear` removes the client's packet-ID correlations from memory but leaves their records in the journal, so they come back after a restart. Saranga deletes them. Either broker reads the other's journal.
  - **Wills and session expiry:** an MQTT 5 will without a Will Delay Interval is published as soon as its client fails, also when the session outlives the connection. Artemis sends it only when the session expires. Each CONNECT sets the will afresh, so a resumed session never publishes the will of a connection before it, as Artemis does. A session restored from the session store at start that expires before its client returns is removed with its subscription queues and its record. In Artemis that fails (`AMQ834008`), and the session comes back after the next restart.
  - **No Local:** a No Local subscription is the client ID filter `__AMQ_CID IS NULL OR __AMQ_CID <> 'id'`, with quotes in the ID doubled. Artemis leaves out the `IS NULL` part, so messages without the property (from STOMP or the Core API) never reach the subscriber, and does not escape the ID, so a client ID with a quote cannot subscribe with No Local.
  - **Shared subscriptions made at once:** when members of a new shared subscription on a multicast address subscribe together, all but the one that makes its queue fail in Artemis (`AMQ229019`, queue already exists) and are disconnected without a SUBACK; Artemis recovers from this for an anycast address only. Saranga gives them the queue that was made.
  - **Topic aliases on overlapping subscriptions:** Artemis takes a topic alias and writes the PUBLISH that defines it without anything ordering the two against another subscription's delivery of the same topic, so the use can reach the client before the definition (and two topics can be given the same alias). Saranga holds the session's state from taking the alias until the defining PUBLISH is queued to be written.
  - **Configured shared queues:** unsubscribing from a subscription whose queue is configured in broker.xml empties the queue only when no consumer is left on it. Artemis empties it whenever any member leaves, under the members still subscribed.
  - **Long intervals:** Message Expiry, Session Expiry and Will Delay Intervals are unsigned and computed in 64 bits. Artemis multiplies them by 1000 as a Java int, so an interval over 2147483 seconds (about 24.8 days) wraps: such a message expires at once, and such a session at the next scan. A Session Expiry Interval with the high bit set (over 2^31, roughly 68 years) is also negative in Artemis's int and so never expires; Saranga treats it as the large finite value it is, with `0xFFFFFFFF` meaning never.
  - **Maximum Packet Size:** the MQTT 5 Maximum Packet Size is read as an unsigned four-byte value. Artemis keeps it in a Java int, so a value with the high bit set (over 2^31) is negative and every message to that client is discarded; Saranga sends them.
  - **A topic alias behind a discarded publication:** when a PUBLISH is dropped for exceeding the client's Maximum Packet Size ([MQTT-3.1.2-25]), Saranga takes back the server topic alias it had assigned for that topic, so the next message to the topic sends a fresh defining packet. Artemis leaves the alias registered, so the next message is sent as an alias reference with an empty topic name, which the client cannot resolve because it never received the defining packet.
  - **Receive Maximum and other subscriptions:** the MQTT 5 Receive Maximum quota is the connection's, so when an acknowledgement frees a slot Saranga wakes every subscription on the connection. Artemis wakes only the subscription whose message was acknowledged, so a QoS 1 or 2 message waiting for a slot on another subscription can starve until some other event prompts it.
  - **Will on takeover:** when a new connection takes over a client ID (link stealing), Saranga publishes the stolen client's will — an immediate will at once, a delayed will unless the taking-over CONNECT resumes the session. Artemis closes the stolen session as if it were a clean disconnect and never publishes its will.
  - **Receive Maximum and persistence:** Saranga counts every QoS 1 and QoS 2 delivery against the client's Receive Maximum ([MQTT-3.3.4-9]), whatever the message's persistence. Artemis gates the quota on the message being durable, so a non-durable message (from a non-persistent Core or STOMP producer) delivered at QoS 1 slips past the Receive Maximum and more than that many can be in flight unacknowledged.
  - **Maximum Packet Size counts every byte:** Saranga measures a PUBLISH at its true encoded size — each property's length prefix included and a packet identifier only at QoS 1 and 2 — before comparing it to the client's Maximum Packet Size. Artemis's estimate omits the two-byte length of each UTF-8 string property and the four bytes of lengths in each User Property pair, and always counts a packet identifier, so it can send a packet larger than the client allowed, which the client then rejects.
  - **Will publication properties:** Saranga keeps a will's Message Expiry Interval, Payload Format Indicator, Content Type, Response Topic and Correlation Data and sets them on the will PUBLISH, the Message Expiry Interval starting when the will is published. Artemis saves only the will's delay interval and user properties, so a published will loses its expiry (it can stay queued or retained indefinitely) and its other publication properties.
  - **QoS 2 and Receive Maximum:** Saranga holds a successful QoS 2 message's Receive Maximum slot until PUBCOMP, as MQTT 5 flow control (4.9) requires. Artemis frees it at PUBREC, so it can send another QoS 2 PUBLISH while the previous exchange is still incomplete, letting a client exceed its advertised Receive Maximum. Both brokers free the slot early for an error PUBREC (reason 0x80 or greater).
  - **Acknowledging after an unsubscribe:** when a PUBACK or PUBREC arrives for a message whose subscription consumer has gone (unsubscribed or closed in flight), Saranga still frees the Receive Maximum slot and wakes the connection's other subscriptions. Artemis returns `PACKET_IDENTIFIER_NOT_FOUND` and leaves the slot held, so with a small Receive Maximum the connection's other subscriptions stall until the client reconnects.
  - **A null text body:** Saranga delivers a Core TEXT message with a null body (a JMS text message without text, or a management import without a `text` member) as an empty MQTT payload. Artemis passes the null to `ByteBufUtil.utf8Bytes`, which throws, so the delivery fails after the Receive Maximum slot was reserved: the message is never sent, the slot leaks, and reconnecting redelivers the same poison message.
  - **Overlapping subscriptions and packet IDs:** Saranga records a correlation per outbound delivery, so when one message reaches several of a client's overlapping subscriptions each exchange keeps its own packet ID across a reconnect or restart. Artemis keys the packet-ID correlation by message and address alone, so the later exchange overwrites the earlier one's record; on redelivery one exchange reuses the surviving ID and the other is given a fresh one, so the retransmitted IDs no longer match what the client holds and its duplicate handling is defeated.
  - **Session Expiry Interval on DISCONNECT:** Saranga persists a Session Expiry Interval changed by an MQTT 5 DISCONNECT, so a restart honours the revised lifetime. Artemis updates it only in memory, so after a restart the session reverts to the interval persisted at CONNECT — outliving or underliving the lifetime the client last requested.
  - **The last unsubscribe:** Saranga keeps a persistent session's durable record when its final subscription is removed (an empty subscription set does not end the session), removing it only on a clean session or an actual expiry. Artemis deletes the record as soon as the subscription set becomes empty, so after a restart the session is reported absent and its continuity (and any remaining packet-exchange records) is lost after a routine unsubscribe.
  - **An unrepresentable topic:** when a Core message reaches an MQTT subscriber as a topic that carries a wildcard character (a Core address such as `orders+east` delivered to a wildcard subscription), Saranga discards the message — freeing its Receive Maximum slot and settling its reference — since the topic cannot be published ([MQTT-3.3.2-2]). Artemis fails the delivery after reserving the slot and sends nothing, so with a small Receive Maximum the connection stalls and its other traffic is blocked.
  - **Session expiry and reconnection:** Saranga re-checks and removes an expiring session atomically with reconnection, so a client that reconnects while the session scan is expiring its old session keeps its session and queues. In Artemis the scan chooses sessions to expire, then removes and cleans them without re-checking that each is still detached, so a client that reconnects in that window can have its now-active session's subscription queues and durable record deleted.
  - **Topic names with a literal backslash:** Saranga converts an MQTT topic to a core address treating a `\` in the topic as the literal character it is (MQTT has no escape), so distinct topics map to distinct addresses and round-trip. Artemis's `WildcardConfiguration.convert` reads a `\` before a delimiter as an escape, so `a\/b` and `a\\/b` both become the address `a/b`: a publication to one reaches a subscriber of the other, and outbound conversion rewrites the topic. Saranga likewise matches a `\` in a topic as a literal when testing a subscription, so a wildcard subscription matches such a topic and the delivery keeps its subscription identifier, where Artemis's escape-aware match can miss it.
  - **Colliding subscription queue names:** the core subscription queue is named `<client>.<address>`, and either half can contain the delimiter, so distinct client-and-topic pairs can name one queue (client `a.b` subscribing to `c` and client `a` to `b/c` both name `a.b.c`). Saranga refuses a subscription whose queue name already belongs to a different address (a SUBACK failure; MQTT 3.1, which has no failure code, is disconnected). Artemis reuses the existing queue without checking its address, so the second client silently receives the first client's messages and none of its own. Saranga keeps the same queue names as Artemis, so a broker still opens what the other wrote; only the ambiguous collision is refused rather than mis-served.
- **Outbound wire strings are bounded.** Saranga discards an outbound PUBLISH whose topic or string property exceeds the two-byte length it is encoded with (over 65535 bytes) rather than writing a wrapped length; such a value normally cannot arrive over a protocol's wire (the core frame size bounds it) and this guards the in-broker paths that can produce one.
  - **A property block of 128 bytes or more:** the Property Length counts only the property bytes that follow it, so Saranga reads the whole block and the payload after it. Artemis 2.57.0 bundles netty-codec-mqtt 4.1.137, whose decoder counts the length's own bytes against the block and stops that many bytes early, so the last property of a block whose length needs two or more bytes is read as the start of the payload (the payload is corrupted). Netty fixed this in 4.1.139, which Artemis uses on its main branch.
  - **DISCONNECT with Will Message:** a DISCONNECT with reason 0x04 (5.0 3.14.2.1) publishes the will; a normal DISCONNECT (0x00) holds it back. Artemis ignores the reason code and holds the will back for both.
- **A second CONNECT** on a connection closes it, after a DISCONNECT 0x8E (session taken over) for MQTT 5. That is what Artemis's link stealing ends up doing when the client ID is the same. Artemis would instead start a second session if the client ID differed.
- **The connection TTL** closes a silent connection when it runs out. Artemis notices at its next `connection-ttl-check-interval`, up to that much later.
- **`mqtt-session-state-persistence-timeout`** is accepted and reported as deprecated (`AMQ221038`), as in Artemis, but as a warning rather than at INFO level.
- **A large message** (over the journal's record size) published as a retained message stays a regular message in the retained-message queue. Artemis converts it to a large message there.

## AMQP differences
- **The Open's `product` and `version`** properties are `saranga` and its version. Artemis sends `apache-activemq-artemis` and its own.
- **Artemis bugs not copied:**
  - **Link failures:** some link failures close the whole connection in Artemis with `amqp:internal-error` "Unrecoverable error: ...". Examples are a receiver attach with no target, and an exception from the core broker while attaching a consumer (a missing queue, an FQQN filter mismatch). Saranga refuses only that link, with the same error.
  - **Unknown transactions:** a transfer that names an unknown transaction closes the connection in both brokers. Artemis still routes the message, outside any transaction; Saranga does not.
  - **Failed SASL outcomes:** Artemis leaves the socket open after a failed outcome, and PLAIN or SCRAM with no initial response is an internal error there. Saranga closes the socket after the outcome and answers PLAIN or SCRAM with no response with outcome `auth`.
  - **Outcomes inside transactional states:** Released, Rejected and Modified wrapped in a transactional state do nothing in Artemis, so the message stays delivered to the consumer. Saranga applies them as it would outside a transaction.
  - **A session window lowered under transfers in flight:** Proton-J computes the client's remaining incoming window as an unsigned number, so a flow that counts fewer transfers than were sent wraps it round to some four billion and Artemis goes on sending. Saranga keeps it signed and sends nothing until the client opens the window again.
  - **The peer's channel-max:** Proton-J takes the lowest free channel up to 65535 when answering a Begin, whatever channel-max the peer's Open gave. Saranga keeps within it, and closes the connection with `amqp:resource-limit-exceeded` when no channel it allows is free.
  - **Delivery tags** go back to the session's pool only when a delivery is settled. Artemis returns them on every disposition, so two unsettled deliveries can share a tag.
  - **Conversion to Core:**
    - An `amqp-value` body of a type other than null, string, binary, list or map becomes a BytesMessage holding the encoded section. Artemis copies the wrong bytes there (ARTEMIS-6316).
    - An application property or stream item that Core has no type for is left out. Artemis fails the whole conversion.
- **Not supported:**
  - **Core-message tunnelling** (`AMQ_CORE_MESSAGE_TUNNELING`): Core messages always go out converted to AMQP.
- **Large messages:**
  - An AMQP large message is held whole in memory while the broker holds it. It is also written to its large-message file, with Artemis's record, so either broker reads the other's.
  - A copy to a dead-letter or expiry address copies the file as it is. Artemis rewrites the copy's header and properties without the expiry.

## OpenWire differences
- **A frame nesting structures more than 32 deep, or throwable causes more than 256 deep**, fails its connection. Artemis follows it until the thread's stack runs out, which also fails only the connection; in Saranga a stack overflow would end the process. Clients nest structures a few deep.
- **`brokerName`** defaults to the host name from `HOSTNAME`, `COMPUTERNAME` or `/etc/hostname`, lowercased, then to the node ID. Artemis asks the JVM for the local host name.
- **Browsers** get a snapshot of the queue when they are created, all of it at once, then the end-of-browse dispatch. Artemis walks the live queue within the browser's prefetch.
- **A pull with no timeout** (prefetch 0, `receive()` or `receiveNoWait()`) gets its null dispatch when the forced-delivery marker reaches the consumer. Artemis blocks the connection's commands until then, for up to 10 seconds.
- **A poison acknowledgement** inside a transaction moves the message to the dead-letter address at once. Artemis moves it when the transaction commits.
- **Removal advisories** on connection close are sent for the temporary destinations the connection made. Artemis also sends them for the temporary subscription queues of its topic consumers, under `ActiveMQ.Advisory.TempQueue`.
- **Dispatched properties** of messages that came from Core or the journal are marshalled in the order they were put, not in the order of a freshly decoded Java `HashMap`. Clients read them into a map.
- **A stream message's byte array longer than the rest of the frame** fails the connection, and a compressed body is inflated only up to 100 MiB (ActiveMQ's default `maxFrameSize`) and no further than its declared uncompressed length. Well-formed messages are unaffected.
- **`openwireMaxPacketChunkSize` and `actorThresholdBytes`** are accepted and change nothing. In Artemis the first makes a frame larger than it be read into a heap buffer rather than Netty's pooled ones, and written in pieces of that size without a flush between them, so the client gets the same bytes at the same time; Saranga reads every frame into its own buffer and writes it whole. The second is how many bytes of commands Artemis lets queue for the connection's executor before it stops reading; Saranga handles a connection's commands as it reads them and reads nothing more while it does, so nothing queues.

## WebSocket differences
- **A broker write is one WebSocket message**, which can hold several protocol frames: the connection's writer batches what is ready. Artemis sends each protocol frame as its own message. Clients read the payloads as a stream.
- **A refused upgrade.** An upgrade request that is not a GET gets `403 Forbidden`. Artemis does not answer it.
- **A frame over the maximum payload** gets a close frame with status 1009 before the connection closes. Artemis closes the connection, and its close frame may not arrive.
- **Not supported:**
  - The draft-00 handshake of clients that send no `Sec-WebSocket-Version`: they get `426 Upgrade Required`.
  - Core over HTTP (`httpEnabled`, `HttpAcceptorHandler`): an HTTP request without a WebSocket upgrade gets `403 Forbidden`.

## Management differences
- **Cluster connections** each have their control (`component=cluster-connections`, `ClusterConnectionControl`) with every attribute, `getBridgeMetrics`, and `start` and `stop`. `Topology` describes the topology as Artemis's `Topology.describe` does, but its identity hashes are Saranga's own. The server's `listNetworkTopology` lists the members of each cluster connection in the order they were deployed; Artemis takes them from a `HashSet` of the connections, in an order that changes from run to run.
- **`getVersion`** reports 2.57.0, the Artemis release whose management interface Saranga answers, so tools that check the version keep working.
- **`browse`** over management messages answers `no operation`, by design. Artemis answers it with JMX `CompositeData` objects, Java-serialized and base64-encoded inside the JSON, which only a Java client can read; Saranga does not produce Java serialization. `listMessages` and `listMessagesAsJSON` return the same messages as plain JSON, and the REST API (`GET /api/queues/{name}/messages`) and the Jolokia layer return `browse`'s messages as JSON. `ConnectionRouterControl.getTarget` is the same: `getTargetAsJSON` answers over management messages, and the Jolokia layer returns `getTarget`'s target as JSON.
- **`changeMessagesPriority`** changes the messages in memory. Artemis also changes paged messages it reads in through the queue's own cursor; Saranga leaves messages still in pages as they are.
- **`listBindingsForAddress`** names a queue binding as `LocalQueueBinding [address=..., queue=...]`. Artemis prints its queue object there, with an identity hash.
- **Connection IDs** are eight random hex digits, as Netty's short channel IDs look, but not Netty's.
- **Dates** of the prepared transactions and the message counters are written as `DateFormat`'s short date and medium time write them in the `en_US` locale, where Artemis uses the JVM's locale. They are in the local time zone, as Artemis's are.
- **`commitPreparedTransaction` and `rollbackPreparedTransaction`** refuse a base64 Xid id that more than one prepared branch shares, completing none. A base64 id is the branch qualifier, global ID and format ID with no lengths, so distinct Xids can share one; Artemis completes the first branch that matches, which may not be the one meant.
- **`proxyAddress` and `proxyProtocolVersion`** are always empty: Saranga does not take the PROXY protocol.
- **A STOMP consumer closed by management** is removed from its session after the `ERROR` frame. Artemis drops the subscription but leaves the server consumer in place.
- **`getRoles` and `getRolesAsJSON`** list roles in the order the setting gives them. Artemis lists them in `HashSet` order.
- **`listUser`** lists users and each user's roles in the order Java's `HashMap` and `HashSet` iterate them, as Artemis does. For a basic security manager the users are first put in name order; Artemis puts them in the order of its own map of the journal's users, so a long list can come out in a different order.
- **Notifications.** A divert's `BINDING_ADDED` carries a new ID in `_AMQ_Binding_ID`, as Saranga's diverts have none of their own.
- **`management-message-rbac`** checks the permission before it looks for the operation. For an operation that does not exist, a caller without the permission gets the permission error; Artemis looks for the operation's method first and answers `AMQ229069: no operation`.
- **Slow consumers** are checked by one task for all queues, within 200 ms of each queue's check period. Artemis schedules a task for each queue.
- **JSON numbers beyond a double's range** (such as `1e400`), in management arguments or JSON configuration, are an error. Artemis's Johnzon reads them as a `BigDecimal`.
- **JSON nested more than 256 deep**, in management arguments, JSON configuration or an OIDC token, is an error. Johnzon follows it as deep as the thread's stack allows; in Saranga a stack overflow would end the process.
- **Records.** Paused queues and addresses, address settings and diverts are journaled as Artemis journals them (`QUEUE_STATUS_RECORD`, `ADDRESS_STATUS_RECORD`, `ADDRESS_SETTING_RECORD_JSON`, `DIVERT_RECORD`), so they move with the data directory in both directions. Like Artemis, Saranga journals every deployed divert, configured ones included.

## Connection router differences
- **Regular expressions** (`key-filter`, `local-target-filter`, and the control's setters) are compiled by `fancy-regex`, which reads Java's syntax, lookarounds and backreferences included. A construct only Java has, such as `p{javaLowerCase}`, is refused as a syntax error, which stops the broker from starting as an invalid expression does in Artemis.
- **A persisted cache entry that is replaced** (its target no longer ready, the key sent to another) keeps a journal record, for the new target. With a `timeout`, Artemis's cache deletes the record when it replaces the entry: Caffeine reports the replacement as a removal. After a restart Artemis then routes the key afresh, where Saranga restores the new target.
- **Stopping a router** (a reload that changes it, or the broker stopping) does not wait for routings in progress, which finish with the targets they had. Artemis's `stateLock` makes the stop wait for them.

## Web server differences
Artemis serves its web console, with Jolokia, and the metrics plugin's app. Saranga serves them too, and more:
- **A REST API at `/api` on every binding**, which Artemis does not have. It is Saranga's documented management interface: the resources, operations and security of management messages, as plain JSON over HTTP (see `crates/saranga-management/src/rest.rs`). With broker security off it asks for no login, as the Core acceptors do.
- **A console of Saranga's own at `/saranga/`**, with its API at `/saranga/api/v1`, on every binding, which Artemis does not have (see the guide's [Management](docs/guide/management.md#the-saranga-console) page). It logs in with the users and console roles of Artemis's console, and `management.xml` or the RBAC guard decides each call. `-Dsaranga.console.enabled=false` turns it off. Where Artemis's `console.war` is not installed, `/` goes to `/saranga/`.
- **The metrics** where `bootstrap.xml` declares the metrics app. JVM, process and Netty metrics are not exported; the broker, address and queue metrics are.
- **Artemis's own web console.** Where `bootstrap.xml` declares the console's app, Saranga serves the `console.war` directory of the instance's `web` directory, else of the home's (`ARTEMIS_HOME`), as Artemis does: its pages, and the hawtio 4.7.0 endpoints behind them (the login form and its session, logout, `/user`, `/refresh`, the auth configuration, Keycloak, plugins and the proxy), answered as Artemis answers them. Saranga ships no `console.war` of its own: without one, the pages are not served and Jolokia is. The differences:
  - Only Artemis's settings exist: no Keycloak, no OIDC, no Spring Security, and the proxy is always disabled (`/proxy/enabled` is `false`). `hawtio.sessionTimeout` and `hawtio.http.strictTransportSecurity` are read as `-D` options, in `JAVA_ARGS` or on `saranga run`.
  - Directories of the `.war` are not listed; Jetty lists them.
  - Sessions live in memory, as Jetty's do, and end with the broker.
- **A Jolokia compatibility layer** at `/console/jolokia`, which answers the Jolokia 2.4.3 protocol from Rust: there is no JMX and no Java. Without the console's app there is no Jolokia layer. Its approximations:
  - Artemis's MBeans exist, with hawtio's permission checks (`hawtio:type=security,area=jmx,name=ArtemisJMXSecurity`) and the five platform MBeans the console reads (`java.lang:type=Runtime`, `Memory`, `OperatingSystem`, `Threading`, `ClassLoading`). There are no other `java.lang`, `java.nio`, `JMImplementation`, `jdk.management`, `com.sun.management` or `jolokia` MBeans, and no other `hawtio` MBeans (`RBACRegistry`, so the console lists MBeans in its default way).
  - The platform MBeans describe the Saranga process, not a JVM. `Runtime` gives its start, uptime, arguments and system properties (those `artemis run` defines and the `-D` options); `Memory`'s heap is its resident memory; `OperatingSystem` gives the machine's CPU, memory and load. `Threading` lists the threads by name and state on Linux, with no stacks, and nowhere else. What only a JVM has reads as zero (loaded classes) or fails as unsupported (the JVM specification), which a read of all attributes leaves out.
  - `listCache` is ignored: `list` answers in its usual form, which Jolokia's clients read, not in the cached form, whose keys Artemis groups by its access rules.
  - An operation that fails answers status 500 and the failure's text, with the `error_type` of the class Artemis's message bundles declare for its AMQ code (`scripts/gen-exception-catalog.py`), or `java.lang.IllegalStateException` for the `ActiveMQServerControl` methods that rethrow as one. A failure without an AMQ code answers `java.lang.Exception`, where Artemis may name another class.
  - The console roles come from `-Dhawtio.roles`, `HAWTIO_ROLES` in `artemis.profile` or `-Dhawtio.roles=` in `artemis.profile.cmd`, and are `amq` by default.
  - Who may call what is `management.xml`'s `<authorisation>`, as Artemis's guard applies it. Without one, and with `-Djavax.management.builder.initial=org.apache.activemq.artemis.core.server.management.ArtemisRbacMBeanServerBuilder` among the system properties (the profile's `JAVA_ARGS`), the broker's security-settings on `mops.` addresses (`management-rbac-prefix`) guard the MBeans as Artemis's `ArtemisRbacInvocationHandler` does: each attribute and operation needs `view` or `edit` (by `view-permission-method-match-pattern`) on `mops.<component>.<name>.<method>`, a refusal answers status 403 with the `AMQ229032` message, and `search`, pattern reads and `list` keep only the MBeans the caller may view.
  - The overloads of an operation are listed in an order fixed by the catalog. Java lists them in `Class.getMethods` order, which can differ from one JVM run to the next.
- **`browse`'s messages** (in both APIs) are shown in the layout of Core messages' `toCompositeData`. An AMQP message is shown converted to Core, with `protocol` `AMQP`; Artemis shows it with the AMQP message's own items. A bytes property appears in `PropertiesText` as `[B@` and a number, as in Java, but not the same number.

## CLI differences
The Artemis CLI's `queue`, `address`, `user`, `producer`, `consumer`, `browser`, `transfer`, `check` and `stop` work against Saranga unchanged. The `saranga` command has them too, with the same options and output; these are the differences:
- **Connections** are Core, over TLS when the URL has `sslEnabled=true`, with the TLS parameters and `javax.net.ssl.*` system properties a connector takes, or AMQP with `--protocol AMQP` (and `--source-protocol`/`--target-protocol amqp`, `perf --consumer-protocol`) as Artemis's CLI connects with Qpid JMS 1.17: the same URL options, SASL mechanisms (PLAIN, ANONYMOUS, EXTERNAL, XOAUTH2 and SCRAM; not CRAM-MD5 or GSSAPI), links, message IDs, JMS-to-AMQP mapping and, for `transfer` between the protocols, the same conversions. Two things differ:
  - `--properties` JSON that is not well formed fails with the exception class Artemis's shaded Johnzon parser throws, but not with its exact message.
  - `transfer` from AMQP to Core of an object message whose body is an AMQP-typed value (sent by a client other than Qpid JMS) works for a String; for any other value it fails with `Failed to serialize object`, where Artemis writes the Java serialization of what Proton decodes.
- **The default URL** comes from the instance's acceptor called `artemis` (or `--acceptor`), else from its connector of that name, as in Artemis.
- **Files of messages** (`producer --data`, `consumer --data`) are Artemis's XML, written and read as its `XMLMessageSerializer` writes and reads them. `--serializer` cannot load a Java class: a class other than `XMLMessageSerializer` is reported as Artemis reports one it cannot load (`Error: unable to instantiate serializer class`), and the XML serializer is used. A large message is written as `data exp` writes one, in Base64 pieces of 1,000 bytes, and `producer --data` sends it back; Artemis 2.57's `consumer --data` fails on a large message with an `IndexOutOfBoundsException`, losing the message it received and stopping the thread. The parser stops on the same malformed content the JDK's does (a `]]>` outside a CDATA section, which a text body holding `]]>` writes), with the same message, but is otherwise more lenient.
- **A failed connection** is reported as Artemis reports it (`Connection failed::<reason>`), then, unless `--silent` is given, the URL (not when the credentials were refused), the user and the password are asked for and the connection is tried once more, as Artemis does, with a terminal or without. Standard input ending at a question fails the command as Artemis's does (`No line found`, then the usage). Where Artemis ends in an uncaught exception, with `--silent` or when the second try fails too, it prints the stack trace; Saranga prints one line and stops with status 1, as Artemis does.
- **`browser --verbose`** prints a message as `ActiveMQMessage[<id>]:PERSISTENT`. Artemis appends the Core message's own `toString`.
- **`--verbose`** does not print the `Executing <class> <arguments>` and `Home::...` lines.
- **`help`** prints Artemis's help: picocli's usage message of the command, laid out as picocli lays it out at 80 columns, with Artemis's descriptions and the commands `buildCommand` offers from an instance, from the home and in the shell. It is printed without picocli's colours. Every option it lists is one Saranga takes: `run` takes the data tools' folder options, which Artemis's takes and does not use. `saranga --help` (and `-h`) prints Saranga's own help, its own options included.
- **Connection URLs** of the messaging commands (`producer`, `consumer`, `browser`, `queue`, `address`, the shell's `connect` and the like) take a list of servers, `(tcp://a:61616,tcp://b:61616)?params`, tried in turn from a random one as Artemis's round-robin policy tries them, and the `ServerLocator` parameters `ha`, `reconnectAttempts`, `failoverAttempts`, `initialConnectAttempts`, `retryInterval`, `retryIntervalMultiplier`, `maxRetryInterval`, `callTimeout`, `callFailoverTimeout`, `clientFailureCheckPeriod` and `connectionTTL`; the others are ignored. With `reconnectAttempts`, a connection fails over to the backup its server's topology names, then to the other servers, and recreates its sessions and consumers there, as Artemis's client does. The consumer credits and expiries it would send while a failover is in progress are dropped rather than held until it ends; the failover gives each consumer its credits again. On Windows, `bin\artemis.cmd` hands its arguments to `cmd` again, which takes an `&` as the end of the command even inside quotes, so separate the parameters with `;`, which Artemis and Saranga both accept.
- **`saranga create`** writes the instance `artemis create` writes, from the same templates: the `etc/` files are the same but for the password hash's salt and the paths. `bin/` holds `artemis` and `saranga` (`artemis.cmd` and `saranga.cmd` on Windows), which run the `saranga` that made the instance, for the instance, and on Unix `artemis-service`, unchanged; there is no Windows service wrapper (`artemis-service.exe`). Without `--aio`, `--nio` or `--mapped` the journal type is `NIO`, as Artemis chooses where libaio is missing. The auto-tuning measures the NIO writes only. `--clustered`, `--static-cluster`, `--replicated`, `--shared-store`, `--backup` and `--failover-on-shutdown`, with the cluster user and password, write the cluster, replication and shared-store settings Artemis writes; Without `--static-cluster`, `--discovery-enabled` writes Artemis's broadcast and discovery groups and puts `-Dartemis.discovery.enabled=true` first in both profiles' Java options, as Artemis does. `--jdbc` is refused, and `--encoding` takes only UTF-8. The messages printed name Saranga.
- **`saranga run`** with neither `--config` nor `--etc` runs the instance named by `ARTEMIS_INSTANCE`, as an instance's `bin/artemis run` does, and stops cleanly on SIGTERM as well as on Ctrl-C, so `artemis-service stop` works. Its configuration URI picks another bootstrap file, as `artemis run -- xml:path/to/bootstrap.xml` does (the path relative to the current directory), and `--broker` another `broker.xml`; a URI with no scheme, another scheme than `xml`, or a file that is not there is refused with Artemis's `Invalid configuration URI` messages, and status 1.
- **The data tools** (`data print`, `exp`, `imp`, `compact`, `encode`, `decode` and `recover`) take the same options and print the same output, the JDBC ones included, though `--jdbc` is refused (Saranga has no JDBC journal) and the others go unused, as Artemis leaves them without it: the configuration URI (`xml:<bootstrap.xml>`, refused as Artemis's `ConfigurationException` is, with status 1), `--verbose`, and for `print`, `exp` and `recover` `--f`, which skips the CLI lock so the data of a running broker can be read, and `--output`. `data exp` takes `log-interval` and `undefined-prefix` as Artemis declares them, without dashes (issue 11), and with them; on the golden data directories `data exp` writes Artemis's XML byte for byte and `data encode` its text. Without `--directory`, `encode` and `decode` use `broker.xml`'s `journal-directory` as written, so a relative one is taken from the current directory, not the instance, as Artemis's do (`getJournalDirectory`); from an instance's `bin`, the default `data/journal` is not there. `data imp` sends over Core only, to `--url`, or to `--host` and `--port` when `--host` is given (Artemis ignores `--port` alone). Like Artemis, they take the instance's CLI lock, so they refuse an instance whose broker is running. On a broker with `database-storage`, `data print` and `data exp` read the tables the broker's `broker.xml` names. `data exp` then writes the XML of Artemis's relational exporter byte for byte (checked against it on one database, with paged and large messages); `data print` has its layout and its totals, differs in how it wraps long JSON and in the time zone of timestamps, and decodes the address bindings Artemis prints as `UNKNOWN`. `compact`, `recover`, `encode` and `decode` work on journals, which that broker does not have. When a tool fails, it says so as Artemis's `treatError` does: `Error:<message>` on stderr between blank lines, with exit status 0. A held lock, or a missing directory for `print` or `recover`, ends the command with status 1, the latter with the usage hint. Java's stack traces are not printed.
- **`version`** prints `Saranga <version> (Apache Artemis 2.57.0)`, then the home and instance lines.
- **`kill`** writes `KILL_ME`, which a broker honours only when it was started with `run --allow-kill`, as in Artemis.
- **`perf client`, `producer` and `consumer`** take the same options and print the same reports, `--json` file and `--hdr` log (HdrHistogram's log format, readable by its tools). A send completes as soon as it is written, as the Core JMS client's `CompletionListener` does without a confirmation window, so `--max-pending` never holds a send back and `total blocked` stays 0. Artemis 2.57's own `perf producer` can stall over Core with the default `--max-pending 1`: a completion is lost while the producer waits for one, and the run never ends; `--max-pending 0` avoids it. The JVM's notice that it has no microsecond clock is not printed.
- **`perf-journal`** measures every journal type with plain file writes and `fdatasync`, as Artemis's `NIO` does; `--max-aio` has no effect. It also works outside an instance, on `./data/journal`; Artemis has it only in an instance's CLI.
- **`upgrade`** rewrites an instance's scripts and profiles as `artemis upgrade` does, with the same steps, backups (`old-config-bkp.<n>`) and kept lines (`ARTEMIS_INSTANCE_ETC`, the data and dump paths, `HAWTIO_ROLES`, `-Xmx` and the other kept JVM arguments), and the same `bootstrap.xml` and logging changes. Its `bin/artemis` then runs this `saranga`, so `saranga upgrade` moves an Artemis instance to Saranga and `artemis upgrade` moves it back. It also writes `bin/saranga` (`saranga.cmd`) beside `bin/artemis`. On Windows, an Artemis instance's service wrapper (`artemis-service.exe`, its `.config` and `artemis-service.xml`) is left as it is.
- **`completion`** prints the bash (and zsh) completion script `artemis completion` prints, generated as picocli 4.7's `AutoComplete.bash` generates it from Artemis's command line: TAB offers the subcommands, a word starting with `-` the options, and after an option that takes a value its candidates (`--protocol`'s `AMQP` and `CORE`) or file names. The script is Artemis's, byte for byte.
- **`shell`**, and `saranga` without a command, run the CLI's commands typed at a prompt, as `artemis shell` does. In it, `connect` keeps a URL, user and password for the commands that follow and `disconnect` forgets them; the first command to connect keeps its own the same way, and the prompt names the connection. The history file is `--history`, else `ARTEMIS_SHELL_HISTORY` (which an instance's `bin/artemis` takes from its profile on Linux, where it defaults to `~/.artemis_history`, as Artemis's does), else the instance's `etc/history-file` after the same question, written in JLine's format. The differences: there is no line editing, completion or recall, since Saranga reads plain lines; the banner and prompt name Saranga. An empty line, and one starting with `#`, run nothing, as JLine's command registry has it. A mistake is reported as Artemis's shell reports it: `Unknown command: <word>` on standard output when the first word names none of the shell's commands, else picocli's message and then the command's usage, or for an unmatched word the commands or options it may mean (`Did you mean: queue stat?`, `Possible solutions: --url, --user`, chosen as picocli chooses them), on standard error; `--help` is no option there, as in Artemis's shell. Without a terminal the lines of standard input are read at the prompts, as Artemis reads them through JLine's dumb terminal, except after a history question: Artemis's answer is read by a buffering `Scanner` that takes the lines after it too, so they never run there, and here they do.
- **`lock list`, `start` and `stop`** answer as Artemis's do for a broker without lock coordinators, which Saranga does not implement: `No Lock Coordinators configured`, and Artemis's uncaught `No lock coordinator found with name` failure.
- **`check cluster`** asks every node of the topology for its own topology and its time, and prints what Artemis's prints; a failure Artemis prints with a stack trace is printed as its first line.
- **`properties`** writes the file `artemis properties` writes: `broker.xml` read as `FileDeploymentManager` reads it (outside an instance, the defaults with the data under `./data`), then every property `ConfigurationImpl.exportAsProperties` reaches by reflection, sorted, quoted and redacted as it writes them, with the defaults its getters give, the `HashMap` and `HashSet` orders it walks, `globalMaxSize` from the instance's `-Xmx` as `run` takes it, and the platform's line ends. On Artemis's own test and example configurations the file is Artemis's, byte for byte, and so are the warnings. Artemis's slips are kept: a federation's `addressPolicies` and `queuePolicies` export nothing; a replica (backup with quorum voting) fails at `checkForPrimaryServer` with a `ClassCastException` and an AMQP bridge policy with `remote-terminus-capabilities` with a `NullPointerException`, leaving the lines written before. What differs: `ConnectionPeriodicExpiryPlugin` is taken from `broker.xml` as Artemis's manual configures it, and exported in `brokerPlugins` as Artemis exports it when it is configured through broker properties, where Artemis 2.57's parser refuses it (issue 20); a divert without a `routing-name` gets a new time-based UUID, as in Artemis, so the two never agree; a broker plugin and an LDAP security setting plugin are keyed by `Object.toString`, a class name and an identity hash Java makes up; lock coordinators are in document order, where Artemis's `HashSet` of them has no fixed order. Only the plugin classes Artemis ships load (the logging, notification and message authorization broker plugins, the logging and simple metrics plugins and the LDAP security setting plugin); any other class is reported as Artemis reports one it cannot load (`java.lang.ClassNotFoundException`), where Artemis would load it from its `lib/`. Saranga does not connect to the LDAP server an LDAP security setting plugin names: the plugin's settings are exported, but not the roles Artemis would read from the directory, nor the `AMQ224066` errors it logs when it cannot reach it. A `NullPointerException` is printed as its first line, without the stack trace.
- **`exportConfigAsProperties`** writes `broker_config_as_properties.txt` in `java.io.tmpdir` (the instance's `tmp` where `bin/artemis` sets it; on Windows Java's own, the user's temporary directory, since `artemis.cmd` sets none) with the export above, of the configuration the broker runs on: as it read it at start, the broker properties it applied included (`ConfigurationImpl.populateWithProperties`, the same keys the broker takes, converted as BeanUtils converts them), with what each reload replaced (`updateReloadableConfigurationFrom`: the security and address settings, diverts, addresses, bridges, connectors, acceptors, AMQP connections, connection routers, JAAS realms and `purgePageFolders`), as Artemis's has it; a file changed since without a reload is not in it. Checked against Artemis 2.57's export of the same `broker.xml` and broker properties, byte for byte (`tests/golden/properties/bp-*`). The configured queues are as the broker's last deployment of them left them, as Artemis's deployment leaves their `QueueConfiguration`s: a queue it made with its journal ID, `configurationManaged` and `autoCreateAddress` set and the defaults its address settings give; one that was there (after a restart) with Artemis's static defaults too and no ID; none of it for a queue whose address failed to deploy before it. A running Artemis 2.57 and Saranga on the same files export the same file, the IDs included, on a new broker and after a restart. A broker started without an instance (an embedded test broker) has no configuration file and fails the operation.
- **Command lines** are parsed as picocli 4.7 parses Artemis's (`crates/saranga-cli/src/help/parse.rs`, checked against what Artemis's own command line makes of some 49,000 command lines in `tests/golden/cli/parse.txt`): the same options, values and conversions, and on a mistake the same message on standard error, then `help help`, with status 1. `saranga --help` (`-h`) and `--version` (`-V`) are Saranga's own and are taken anywhere on the command line, where picocli finds no such option. A negative count, size or time fails or is taken as Artemis's command fails or takes it, with its message, except where Artemis's own fails in another thread or never ends: `perf client --message-size` below 0 fails with the size alone, and `perf client`, `consumer` and `perf consumer` with `--shared` below 0 take no shared subscriptions.
- **Every command works from an instance and from the home**: `user`, `stop`, `kill`, `perf-journal` and `activation`, which Artemis has only in an instance's CLI, and `create` and `upgrade`, which it has only in the home's. `help` and `completion` list the commands Artemis's lists where it runs. Run from the home, a command other than `run` logs only errors, to standard output in log4j 2's default pattern, as Artemis's home `bin/artemis`, which names no logging configuration, has it.
- **`mask --password-codec`** reads the codec from the `broker.xml` of `--config`, else of the instance, as Artemis's reads the instance's.
- **`mask --scram <user> <password>`** (with `--iterations`) is Saranga's own: it prints the lines `java -cp "lib/*" org.apache.activemq.artemis.spi.core.security.jaas.SCRAMPropertiesLoginModule <user> <password> [<iterations>]` prints in Artemis, for a users file read by `SCRAMPropertiesLoginModule`, since Saranga has no Java to run that class with.
- **`stop`** finds the instance through `ARTEMIS_INSTANCE` (or `ARTEMIS_INSTANCE_ETC`), as an instance's `bin/artemis` sets it, through a `xml:<bootstrap.xml>` argument, or through `--broker <broker.xml>`.

## Logging differences
`saranga run` logs as Artemis does: it reads the instance's `etc/log4j2.properties` (or the file `-Dlog4j2.configurationFile` names, on `saranga run` or in the profile's `JAVA_ARGS`) and writes Artemis's format, codes and logger names to its console and files, so runbooks that read `log/artemis.log` or change levels in that file work unchanged (see `crates/saranga-cli/src/logging.rs`). The differences:
- **Logger names.** Each message is logged under the logger of the Artemis message bundle its code belongs to (`AMQ22xxxx` under `org.apache.activemq.artemis.core.server`, `AMQ14xxxx` under `org.apache.activemq.artemis.journal`, and so on). A message without a code is logged under one logger for its component, where Artemis uses the class's own logger, so a level set for a single Artemis class has no effect.
- **Messages.** The startup and shutdown messages runbooks look for are there, with their codes (`AMQ101000`, `AMQ221000`, `AMQ221001`, `AMQ221002`, `AMQ221007`, `AMQ221020`, `AMQ241001` and the like); their text names Saranga and its version where Artemis names itself. Other messages carry Artemis's code and text where Saranga has the same event; Saranga's own messages have no code. JVM and Netty messages do not exist.
- **log4j 2.** The properties format is supported, with `Console`, `File`, `RandomAccessFile`, `MemoryMappedFile`, `RollingFile` and `RollingRandomAccessFile` appenders, rolling on time, a cron schedule, size and startup, with the default rollover strategy's `max` and `.gz` archives compressed, `PatternLayout`, `ThresholdFilter`, logger levels, appender references and additivity, `${sys:}`, `${env:}` and `property.` lookups, and `monitorInterval`. Rolling follows the date in `filePattern`: a `CronTriggeringPolicy` rolls when that date changes, whatever its schedule. XML, JSON and YAML configurations, other appenders and layouts, async loggers and colours are not supported; what is not understood is logged as a warning. `%t` is the Rust thread's name.
- **`RUST_LOG`**, when set, chooses what is logged in place of the configured levels, except that loggers set to `OFF` stay off.
- **The CLI's other commands** log as Artemis's `bin/artemis` has every command but `run` log (`artemis-utility.profile`): WARN to the console in Artemis's pattern, configured by the instance's `etc/log4j2-utility.properties` when there is one. From the home, whose `bin/artemis` names no configuration, and in an instance without that file, it is log4j2's default, as in Artemis: errors only, to standard output.

## Audit log differences
The three audit loggers (`org.apache.activemq.audit.base`, `.resource` and `.message`) are off unless `log4j2.properties` turns them on, as in Artemis, and log the same codes, texts and callers (`user(roles)@address`). The base logger's message for each management method comes from a catalog generated from Artemis's `AuditLogger` and `*ControlImpl` classes (`scripts/gen-audit-catalog.py`), so a method logs what Artemis's control logs, quirks included (the management `createQueue` and `destroyQueue` name their caller `anonymous`). Management calls are audited whichever way they come: management messages, the REST API or the Jolokia layer. [tests/interop/audit/audit.sh](https://github.com/grepjava/saranga/blob/main/tests/interop/audit/audit.sh) checks a CLI session's audit log against Artemis 2.57.0's. The differences:
- **Objects in messages** (sessions, connections, messages, routing contexts, transactions, queues, addresses) are shown in their Java classes' `toString` layout with Saranga's values. Their identity hash codes are not Java's, and a session's parameters show its connection briefly.
- **Not logged:** MBean registration and the JMX guard (601019, 601138, 601718), which Saranga does not have; the getters Artemis's list views (`listQueues` and the like) call on each queue's control; acknowledgements made without a consumer (`system@internal`: messages removed by management, expired, or left on a deleted queue); the end of XA branches; and the broker's own sends (management replies, OpenWire advisories).
- **Callers.** The console's (Jolokia) callers have no address (`@unknown`), as in Artemis. REST API callers, which Artemis does not have, have theirs. `%t` in the audit pattern is a Saranga thread's name.
- **Security failures** (601264) are logged without the stack trace Artemis appends.

## Critical analyzer differences
The analyzer reads `critical-analyzer`, `critical-analyzer-timeout`, `critical-analyzer-check-period` and `critical-analyzer-policy` as Artemis does, and watches the components Artemis watches: the journal's writer (Artemis's `TimedBuffer`), each queue and each session. A component past the timeout is reported once, with AMQ224107, AMQ224081/AMQ224080/AMQ224079 and AMQ222199, and the plugins are told (`criticalFailure`). LOG only logs, SHUTDOWN stops `saranga run` cleanly and HALT ends the process with status 70. The differences:
- **The "thread dump"** (AMQ222199) lists the components in a critical path and how long each has been there. A Rust process cannot dump its threads' stacks.
- **What a path covers.** A queue is in its critical path while its task handles one command, and a session while it sends or acknowledges, so the paths are not drawn exactly where Artemis's `CriticalMeasure`s are.

## Critical I/O error differences
As in Artemis (`IOCriticalErrorListener`), a failed write, sync, open, rename or removal under the journals, and a failed write, sync, open or rename of a page file or a large message file (a copy's among them), is a critical I/O error. It is logged with AMQ144011 (AMQ144010 when there is no file) and AMQ222010. The journal then accepts no more writes, the client waiting on the operation gets an `IO_ERROR` exception, and the broker stops as `stopTheServer(true)` stops it: the lock is paused, or let go with `failover-on-shutdown`, and whatever more the stop writes may fail. The differences:
- **The process ends.** Artemis's server stops but `artemis run` stays up with nothing running. `saranga run` exits with status 1, so a service manager sees the failure and can restart it.
- **The journals take no more writes after any critical I/O error**, a page or large message file's included, so nothing is written as stored while the stop runs. In Artemis only the stop ends them: until it reaches the journals, a send or acknowledgement can still succeed.
- **A page file that cannot be deleted** once all its messages are acknowledged is a critical I/O error too, and the acknowledgements it would have taken with it are kept, so after the restart its messages are still acknowledged. Artemis only logs it, and deletes the acknowledgements anyway: the page's messages come back at the next start.
- **A large message file that cannot be deleted** is logged with AMQ144000, as Artemis logs it, and left for the cleanup at the next start: not a critical I/O error.
- **What is covered.** Page directories and their `address.txt`, the large-message directory and a replicating backup's synchronization files are made outside the critical path: an error there fails the operation that needed them but does not stop the broker.

## Network check differences
`saranga run` reads `network-check-list`, `network-check-URL-list`, `network-check-period`, `network-check-timeout` and the ping commands as Artemis does (`NetworkHealthCheck`). Each address and URL is checked once as it is added, with AMQ202001, AMQ202002 and AMQ202003, and then every period. While none answers, the broker is stopped (AMQ201001). Once one answers again, a new broker is started on the same data and ports (AMQ201000), and the web server serves it. The runbook suite takes an instance made with `create --ping` through a network outage and back. The differences:
- **Reachability.** Without a custom ping command, an address first gets a TCP connection to its echo port (7), and a refusal counts as an answer, as `InetAddress.isReachable` does without privileges. Saranga never sends ICMP itself. When there is no answer, it runs the ping command, as Artemis does.
- **`network-check-NIC`** is reported and not used: the addresses are checked through any interface.
- **URLs** are read as Java's `URLConnection` reads them: redirects to the same protocol, the status, `https` with the `javax.net.ssl.*` truststore and a host name check, the `http.proxyHost`, `https.proxyHost` and `http.nonProxyHosts` proxies, and Java's exceptions in `AMQ202006`. Without a truststore, an `https` server is checked against the platform's certificate authorities, where Java uses its own `cacerts`. SOCKS proxies (`socksProxyHost`) are not used.
- **Host names** are given to the ping command as the address they resolve to. Artemis gives the canonical host name from a reverse lookup.
- **An unhealthy network at startup** stops the broker right after it has started, as in Artemis. Artemis's `run` then fails to register the web server with the stopped broker (`IllegalStateException`) and the process exits. Saranga keeps the process and its web server, and starts the broker once the network answers.
- **While the broker is stopped**, the web server serves the stopped broker's last state. Artemis unregisters its MBeans.

## Broker plugin differences
A plugin is Rust code implementing `saranga_server::plugin::BrokerPlugin`, the equivalent of `ActiveMQServerPlugin`, registered by an embedding application in `BrokerConfig::plugins` or with `Broker::register_plugin`. `<broker-plugins>` in `broker.xml` selects Saranga's ports of the plugins Artemis ships, by their Java class names and with their properties: `LoggingActiveMQServerPlugin`, `NotificationActiveMQServerPlugin`, `BrokerMessageAuthorizationPlugin` and `ConnectionPeriodicExpiryPlugin`. [tests/interop/plugin/plugin.sh](https://github.com/grepjava/saranga/blob/main/tests/interop/plugin/plugin.sh) checks the logging plugin's lines for a CLI session against Artemis 2.57.0's. The differences:
- **`ConnectionPeriodicExpiryPlugin`** works from `<broker-plugins>` as Artemis's manual shows, with `init`'s checks and messages. Artemis 2.57's parser loads every `<broker-plugin>` as an `ActiveMQServerPlugin`, which this plugin is not (it is an `ActiveMQServerBasePlugin`), so Artemis fails to start with `IllegalStateException: clazz [...ConnectionPeriodicExpiryPlugin] is not assignable from expected type: interface ...ActiveMQServerPlugin` and takes it only through broker properties (issue 20). A `broker.xml` that uses it therefore does not start Artemis 2.57.
- **Other classes.** A `<broker-plugin>` naming any other class is Java code Saranga cannot run, and the broker does not start: leaving out what such a plugin enforces could open what it closes. The same goes for a built-in plugin's own configuration errors.
- **Hooks.** Saranga has the hooks for connections, sessions (not `beforeCreateSession`), session metadata, consumers, addresses (adding and removing), queues, bindings of queues, sends, routing, `canAccept`, deliveries, acknowledgements, expiry and critical failures. The bridge hooks are given the bridge's name and the message's ID rather than the bridge and the reference. It has `beforeRemoveBinding`, and the binding hooks are called for diverts too. It does not have the hooks for federation (`ActiveMQServerFederationPlugin`), `beforeRemoveAddress`, `updateAddress` or message moves, and the routing hooks are not given the transaction. Hooks run on the broker's tasks: a plugin must not block.
- **Arguments.** A message's acknowledgement is reported without its transaction (the logging plugin prints `with transaction: null`) and without its consumer; a destroyed queue is reported without the session that destroyed it (`session: null`).
- **Notifications.** The notification plugin's `MESSAGE_EXPIRED` has no `_AMQ_ConsumerName`, as expiry by a consumer is reported as by the reaper.
- **Objects in messages** print as in the audit log (Saranga's values, identity hashes not Java's), and a message's properties are in insertion order, not a Java `HashMap`'s.

## Interceptor differences
An interceptor is Rust code: a `saranga_server::interceptor::Interceptor`, named, that implements `Intercept<P>` for the packets of the protocols it takes, Artemis's `Interceptor`, `StompFrameInterceptor`, `MQTTInterceptor`, `OpenWireInterceptor` and `AmqpInterceptor`: Core's `saranga_core_protocol::Packet`, STOMP's `Frame`, MQTT's `codec::Packet`, OpenWire's `DataStructure` and AMQP's `AmqpMessage`. An embedding application registers it in `BrokerConfig::interceptors` under the class name `<remoting-incoming-interceptors>` (or `<remoting-interceptors>`) and `<remoting-outgoing-interceptors>` give, and can add and remove interceptors on a running broker through `Broker::interceptors`, as `RemotingService` allows. A class name with no interceptor registered stops the broker from starting, as a class Artemis cannot load does. They are called where Artemis calls them, and a refusal does what it does there: a Core packet is dropped, a STOMP frame is dropped (the frames read with it wait for more bytes), an MQTT or OpenWire connection is closed (an OpenWire command refused before the connection is made is only dropped), an AMQP message is rejected with `failed` "Interceptor rejected message", and an outgoing packet is not sent. One that fails is logged (`AMQ212038` for Core, `AMQ224082` for the others) and the next is called. A STOMP MESSAGE is encoded before the outgoing interceptors see it, and an AMQP message's application properties are changed without its encoding, so what an interceptor changes of them does not reach the client, in either broker. [tests/interop/interceptors](https://github.com/grepjava/saranga/blob/main/tests/interop/interceptors/interceptors.sh) runs the same interceptors in both brokers, in Java and in Rust (the CLI's `interop-interceptors` feature). The differences:
- **Interceptors are given the connection** as `ClientConnection`, which every protocol's connections share, not as the protocol's own connection class.
- **The outgoing interceptors of Core and AMQP** are given a copy of the delivered message, for that delivery. Artemis gives them the message the queue holds, so what one changes stays with the message for its later deliveries.
- **A refused Core large message** takes no consumer credit. Artemis asks the packet it did not encode for its size, which fails the delivery.

## Security differences
- **Login modules.** `PropertiesLoginModule`, `GuestLoginModule`, `TextFileCertificateLoginModule`, `ExternalCertificateLoginModule`, `LDAPLoginModule`, `SCRAMPropertiesLoginModule`, `SCRAMLoginModule`, `OIDCLoginModule`, `KubernetesLoginModule`, `PrincipalConversionLoginModule`, `Krb5LoginModule` and the JDK's `com.sun.security.auth.module.Krb5LoginModule` are supported. Custom Java modules are not. A `login.config` entry that names one gets a warning at startup, and logins that reach that module fail.
- **`OIDCLoginModule`** checks tokens as Artemis's Nimbus JOSE + JWT does: the same algorithms, key choice, claim checks, plain and encrypted JWTs refused, and the provider's metadata and keys fetched and cached as Artemis caches them. Where it differs:
  - A `provider` URL ending in `/` is taken without it. Artemis 2.57 keeps only the slash while stripping it and loops for ever, so its login never ends.
  - RSA keys of fewer than 2048 bits do not verify. Java's do.
  - ES256K verifies in neither: Java has had no secp256k1 since JDK 16.
  - `userPrincipalClass` and `rolePrincipalClass` other than Artemis's `UserPrincipal` and `RolePrincipal` make principals of that class name, which no other module or check counts. Artemis loads the class, and fails to initialize without it.
  - Over HTTPS without `caCertificate`, the provider's certificate is trusted through the platform's trusted certificates, where Java uses its own `cacerts`.
- **Kerberos** (AMQP's GSSAPI, the JDK's `Krb5LoginModule`) uses the system's Kerberos library, loaded when first used, where Artemis uses Java's own Kerberos: MIT Kerberos 1.11 or later (macOS's Heimdal is not used), or on Windows MIT Kerberos for Windows, else SSPI. Without one, those logins fail. Where it differs:
  - `krb5.conf` is the one `java.security.krb5.conf` names, else the library's default (`KRB5_CONFIG`, else `/etc/krb5.conf`), not Java's (`<java.home>/conf/security/krb5.conf`, `C:\Windows\krb5.ini`). `java.security.krb5.realm` and `java.security.krb5.kdc` are not read: a warning says so.
  - Without `keyTab`, the keytab is the library's default (`KRB5_KTNAME`, `default_keytab_name`, else `/etc/krb5.keytab`), where Java takes `~/krb5.keytab` when `krb5.conf` names none. The default ticket cache is the library's too.
  - Keys made from a password (`storeKey` with no keytab, as an acceptor) cannot accept GSSAPI contexts. In Artemis they can, though no GSSAPI login can give a password, its realm being logged into without a callback handler.
  - JAAS's shared state is not kept between modules, so `useFirstPass` fails and `tryFirstPass` asks the handler, as when no module before stored a name and password. `storePass` and `clearPass` do nothing.
  - `refreshKrb5Config` is always in effect: the library reads `krb5.conf` each time.
  - Through SSPI (Windows without MIT Kerberos for Windows), the broker accepts as the account it runs as, for that account's service principal names, whatever keytab is named; `useKeyTab` for a TGT fails; the ticket cache is the logon session's; a password is tried against the KDC only when a context is first made with it, so a login with a wrong one succeeds; and principals without a realm take the session's domain. It needs the machine in a Kerberos (Active Directory) realm.
- **Security managers.** The JAAS security manager (`<jaas-security>`) and `ActiveMQBasicSecurityManager` are supported. The basic manager keeps its users in the bindings journal, so its users move with the data directory in both directions. Any other `<security-manager>` class stops the broker from starting. As in Artemis, the basic manager has no users without persistence. Users are added through the bootstrap credentials or through management (`addUser`).
- **The authentication cache** keys a login by whether each credential was given as well as by its bytes, so a missing user or password and an empty one are cached apart. Artemis hashes the bytes alone, so after an anonymous login is cached, a client that sends an empty password reuses it, even where `GuestLoginModule` with `credentialsInvalidate=true` would refuse that client when asked.
- **The authorization cache** keeps a granted permission only if the security settings have not changed since the check read them. Artemis caches the grant once the check ends, so a check in flight while a setting is changed or removed puts the old grant back into the cache the change cleared, and the revoked permission holds until the cache entry expires (`security-invalidation-interval`).
- **Removing a security or address setting** removes it from where adding it put it: a fully qualified match with a wildcard (`orders::tenant.*`) and a literal match given in its markers (`(orders.#)`) are removed. Artemis looks for the first among the wildcard matches, where it is not, and for the second with its markers, so neither is removed and the setting stays in force.
- **A role named `*`** in a security setting grants nothing in Artemis 2.57, despite looking like a wildcard. Saranga matches this.
- **Security setting plugins** (`<security-setting-plugin>`) are not supported and produce a warning.
- **`LDAPLoginModule`** binds as `connectionUsername` with simple authentication, or with `authentication=GSSAPI` as the broker's Kerberos identity (the realm `saslLoginConfigScope` names, `broker-sasl-gssapi` by default), as JNDI does, over `ldap://` and `ldaps://`. Where it differs:
  - A GSSAPI bind's security layer must be `auth`, JNDI's default: a `javax.security.sasl.qop` that settles on `auth-int` or `auth-conf` fails the bind, where JNDI would protect each message after it.
  - Artemis fails every connection with a `NullPointerException` when `initialContextFactory`, `connectionProtocol` or `authentication` is not given, which is why its examples set `connectionProtocol=s`. Saranga connects without them, binding with simple authentication when `authentication` is not given.
- **TLS** is rustls: TLS 1.2 and 1.3, and the cipher suites rustls has. A suite name it does not have is logged and skipped, and an acceptor left with none stops the broker from starting. `trustManagerFactoryPlugin`, `sslContext`, `crcOptions`, `ocspResponderURL` and `useDefaultSslContext` stop the broker from starting, as does a connector with them, rather than connecting without them. `verifyHost` on an acceptor is logged and ignored.
