# Compatibility target

| Item | Value |
|---|---|
| Reference implementation | Apache ActiveMQ Artemis |
| Pinned version | **2.57.0** (tag `2.57.0`, checked out in `reference/activemq-artemis`, git-ignored) |

Saranga aims for wire compatibility (Core, AMQP 1.0, MQTT 3.1.1/5, STOMP, OpenWire, WebSockets)
and on-disk compatibility (journal, bindings, paging, large messages) with the pinned version.
See [docs/design.md](docs/design.md) for the strategy.

## Why we build the reference from source
Artemis 2.45.0 to 2.57.0 are tagged in git, but no distribution, server jars or Docker images
were published for them. Maven Central has POMs only, and the newest published release is 2.44.0.
`scripts/build-artemis.sh` therefore builds 2.57.0 from the tag and packages it with Artemis's own
`artemis-docker` Dockerfile as `saranga/artemis-ref:2.57.0`. Clone the reference with
`core.autocrlf=false` on Windows, because CRLF line endings break the container entrypoint.

## Artemis wire quirks Saranga reproduces on purpose
Saranga matches what Artemis actually puts on the wire, including the oddities below. Do not "fix" them, or interop breaks.

- **Two boolean encodings.** `ActiveMQBuffer.writeBoolean` writes true as `0xFF`. Packets and journal records use it. Netty's `ByteBuf.writeBoolean` writes `0x01`, and `TypedProperties` and `CoreMessage` headers use that one. Readers treat any non-zero byte as true. In Saranga these are `Writer::bool` and `Writer::byte_buf_bool`.
- **Two nullable encodings.** `writeNullableSimpleString` and similar write a `0x00`/`0x01` marker (`Option<T>`). `BufferHelper.writeNullableX` and boolean presence flags write `0x00`/`0xFF` (`Flagged<T>`).
- **Property order.** `TypedProperties` iterates a Java `HashMap`. Saranga keeps decode order, so re-encoding is exact.
- **Optional trailing fields.** Many `_V2` and later packets read their newest fields only "if bytes remain". Saranga models these as `Option<T>` written only when present. Some packets (`CreateQueueMessage_V2`, `SessionQueueQueryResponseMessage_V3`, `SessionBindingQueryResponseMessage_V4/V5`, `CreateSharedQueueMessage_V2`) use a `sections` count. Set it to the struct's `SECTIONS` constant when building a packet to send.
- **`FederationConnectionConfiguration` encode/decode mismatch.** Encode writes `retryInterval` into the slot that decode reads as `maxRetryInterval`. This is an Artemis bug. Saranga keeps the wire value as-is.
- **`ReplicationSyncFileMessage`.** The primary sends the whole 32 KiB read buffer even when fewer bytes were read. Only `dataSize` bytes are meaningful, and the rest is kept as `trailing`.
- **1.x message layout.** Clients older than version 129 put an extra end-of-message offset into sends and receives. Artemis ignores it on decode. Saranga keeps it so the message re-encodes exactly.

## Configuration differences
- **`${...}`** in `broker.xml`, `bootstrap.xml`, `login.config` and broker properties resolves from `saranga run -D name=value`, then from the properties `artemis run` defines (`artemis.instance`, `artemis.home`, `artemis.instance.etc`, `artemis.URI.instance`, `data.dir`, `java.security.auth.login.config`), then from environment variables, else from the default after `:` (`${name:default}`), else empty, as `XMLUtil.replaceSystemPropsInString` resolves them. An instance's `bin/artemis` passes on the `JAVA_ARGS` and `JAVA_ARGS_APPEND` of the profile it loads, as Artemis's does, and `saranga run` in an instance takes their `-D` options as system properties, before its own `-D` options, which win; the other options are for Java and are ignored. The arguments are split on spaces, as `bin/artemis` splits them, so a quoted value cannot hold one. On Windows Artemis's `artemis.cmd` misspells `JAVA_ARGS_APPEND` (`%$JAVA_ARGS_APPEND%`) and so never passes it (issue 10); Saranga's passes it. `webconfig.`-prefixed system properties update `bootstrap.xml`'s `<web>` as Artemis's `Run` does: `bindings.<name>.<attribute>` and `bindings.<name>.apps.<name>.<attribute>`, a binding or app found by its name, else its `uri` or `url`, and made when there is none; a property naming no attribute is logged as a warning, where Artemis records it in its status. `securityconfig.` system properties choose the security manager as Artemis's `BrokerFactory` does: `jaas.domain` and `jaas.certificateDomain` make it JAAS with those domains, else `manager.className` and `manager.properties.<key>` a security manager with those properties, over what `bootstrap.xml` says. The security chapter passes them as `artemis run -Dsecurityconfig...`, which Artemis refuses (`Unknown option`, docs/upstream/artemis-issues.md, issue 9); `saranga run` takes `-D` options, so there it works, and through `bin/artemis` the profile's `JAVA_ARGS` works on both.
- **Broker properties** are read from `.properties` files (and any other extension) and from `.json` files, whose nested members become dotted keys as Artemis's `loadJson` makes them. YAML files are reported as a load error. The collections Saranga applies are `addressSettings`, `securityRoles`, `addressConfigurations`, `acceptorConfigurations`, `divertConfigurations` and `jaasConfigs`, plus the top-level settings it supports. Every other key is reported as a warning, and, as Artemis reports it, in the broker's `Status` under `configuration.properties.<source>`, with the Adler32 checksums of its entries and of its file. The JAAS properties files read for a login are reported there too, under `server.jaas.properties`.
- **Configuration reload** swaps the security settings and address settings, reconciles diverts, and deploys and undeploys addresses and queues, as Artemis does. Saranga does not reload acceptors, bridges, connection routers or `jaasConfigs`. It also does not reload the `login.config` file itself, which Artemis does not reload either.
- **Namespaces.** Elements are matched by local name, so prefixed elements that Java would miss are accepted.
- **`xi:include`** is not expanded yet; it produces a warning.
- **Features Saranga does not have yet.** A replicating or colocated backup (`<ha-policy>` with `<replication>` and a backup role, or `<colocated>`) and the JDBC store (`<database-store>`) stop the broker from starting with a reason. Starting anyway would pretend to be something it is not. The following elements are read but not acted on, each with a warning: a replication primary `<ha-policy>`, `scale-down`, broadcast and discovery groups, `<bridges>`, `<federations>`, `<broker-connections>`, `<connection-routers>`, `<grouping-handler>`, metrics and `<resource-limit-settings>`. The critical analyzer settings are accepted silently. `<cluster-connections>` with `static-connectors` are read: a shared-store backup announces itself to its primary through one, so that clients get the pair in their topology, and the topology a cluster connection's node announces is sent to clients. Messages do not move between the nodes of a cluster yet.
- **Acceptors** pick each connection's protocol from its first 8 bytes, as Artemis does, among the protocols the acceptor lists that Saranga has. Protocols Saranga does not have yet produce a warning, and an acceptor that lists only such protocols is not opened. A host binds to the address Java's `InetAddress.getByName` gives, which is IPv4 first, so `localhost` means 127.0.0.1 as it does for Artemis.

## Persistence differences
- Saranga writes journal files the way Artemis's `NIO` journal does: records follow each other without block alignment, whatever `journal-type` says. Artemis reads such files with any journal type, and Saranga reads `ASYNCIO` files (aligned flushes padded with zeros).
- Appends wait while the journal compacts; Artemis keeps appending and replays the appends afterwards. The compacted files are the same.
- Group commit comes from a flusher thread that syncs whatever accumulated while the previous sync ran, rather than `TimedBuffer`'s timer, so `journal-buffer-timeout` has no effect.
- `server.lock` holds the node ID and state as in Artemis (`0`, `F`, `L` and `P`), and the primary and backup locks are locks on `serverlock.1` and `serverlock.2`, all taken as Java takes them: `fcntl` record locks on Unix, `LockFileEx` on Windows. A Java broker and a Saranga broker therefore exclude each other on one journal directory, and either can be the other's shared-store backup. As in Artemis, a primary whose lock another broker holds waits for it, for `journal-lock-acquisition-timeout`.
- **Shared-store backups.** A backup waits for the backup lock, then for its primary to fail, as Artemis's does, and its web server and acceptors start once it is active. It announces itself to its primary through its cluster connection (`NodeAnnounce`), and, once active, hears the restarted primary announce itself the same way and gives way to it (`allow-failback`), waiting as a backup again with `restart-backup`. Without a cluster connection it logs `AMQ222308` as Artemis does.
- When an update changes a queue's filter (configuration reload, or management from Phase 8), the queue binding record Saranga writes holds the new filter. Artemis 2.57.0 writes the old one, because `QueueImpl.setFilter` does not update the queue's `QueueConfiguration`, which is what gets journalled (drafted upstream in [docs/upstream/artemis-issues.md](docs/upstream/artemis-issues.md), issue 2). The record has the same layout, and either broker reads the other's. A queue whose filter was changed by a Java broker and not by broker.xml therefore comes back on Saranga with the old filter, as it would on Artemis. Queue queries, as on Artemis, keep reporting the old filter until restart.
- The XA error messages print `XidImpl (<n> ...` with a hash of the Xid where Java prints an identity hash.
- **Journal retention** (`<journal-retention-directory>`) works as in Artemis. Each message-journal file the journal moves on from is copied to the retention directory as `activemq-data-<yyyyMMddHHmmss>-<id>.amq`, named in local time. Copies older than `period`, or beyond `storage-limit`, are removed. Paged messages and large-message bodies are also written to the journal as events, so the copies hold them, and `data compact` keeps the compacted files in the history. The broker's `replay` operations route the retained messages again. Artemis's `data print --journal <retention>` reads Saranga's copies, and the other way round.

## Paging differences
- **Paging needs persistence.** Without `persistence-enabled`, Artemis still writes page files (its null storage manager keeps no journal but the page store works); Saranga keeps every message in memory, and only BLOCK, FAIL and DROP limit an address.
- **Full disks** are handled as Artemis handles them: every `disk-scan-period` the stores' disks are checked against `max-disk-usage` (or `min-disk-free`, which wins when both are set), and while one is past it each address does what its `disk-full-policy` says (BLOCK, FAIL or DROP), with Artemis's log messages; the management address, which has no paging store, is never blocked. The usage is read from the operating system (`statvfs`, `GetDiskFreeSpaceExW`).
- **`global-max-size`** defaults to 1 GiB. Artemis defaults to half the JVM's maximum heap, which Saranga does not have.
- **Messages sent in a transaction** count against the address size when the transaction commits. Artemis counts them as they are routed, before the commit. Under transactional producers a Saranga address therefore fills a little later.
- **Queue browsers** see the messages a queue holds in memory, including those read in from its pages up to `max-read-page-messages` and `max-read-page-bytes` (1,000 messages when neither is set), but not the rest of a longer backlog. Artemis browsers read through the page files as well (`QueueBrowserIterator`).
- **Page counters** are rebuilt from the page files at every start, and the counter records Artemis writes are deleted when Saranga loads them. Artemis rebuilds its counters the same way when the records are missing, so the data directory still moves back.

## Queue semantics differences
- **delay-before-dispatch** ends on a timer. Artemis has no timer: it starts dispatching at the next delivery attempt after the delay, such as a new message, a consumer's credits or a forced receive.
- **Last-value queues** drop a replaced value as soon as its replacement arrives. Artemis prunes on its next delivery pass. The queue holds the same messages afterwards.
- **Message groups.** While a group's consumer has no credit, only that group's messages wait. Artemis ends the whole delivery pass at that point.
- **Duplicate detection** checks the message a client sends. Copies a divert makes are not checked against the forwarding address's cache.
- **A prepared XA branch's duplicate IDs** keep their own journal record IDs after recovery. Artemis files them under the transaction's ID.
- **Large-message files** are deleted once nothing holds the message any more, which is when Artemis's reference count releases it. When the broker stops, the files of messages still in memory are kept, as Artemis keeps them.
- **Divert transformers** are Rust plugins, not Java classes. The embedding application registers a `Transformer` under the class name that `broker.xml` gives. A divert whose transformer is not registered is not deployed, and a warning is logged.

## STOMP differences
- **The `server` header** of CONNECTED is `Saranga/<version>`. Artemis sends `ActiveMQ-Artemis/2.57.0 ActiveMQ Artemis Messaging Engine`. `disableStompServerHeader` leaves it out on both.
- **`AMQ339011 Error sending message`** names the message by its ID, durability and address. Artemis prints the whole `CoreMessage.toString()`.
- **Byte-array properties** appear in MESSAGE headers as `[B@` followed by a hash of their contents. Artemis prints the array's identity hash. Neither means anything to a client.
- **Frame interceptors** (Java classes) are not supported.
- **The connection TTL** closes a silent connection when it runs out. Artemis notices at its next `connection-ttl-check-interval`, up to that much later.
- **A `
` that is the last byte read** waits for its `
`. Artemis reports `There is a CR not followed by an LF` when the two arrive in different packets.

## MQTT differences
- **Artemis bugs not copied.**
  - **Live retained messages to MQTT 5 wildcard subscriptions:** a retained PUBLISH sent while a client is subscribed by a filter other than the exact topic (such as `a/#`) never reaches that client in Artemis, because `publishToClient` looks the subscription up by topic name and fails. Saranga delivers it. The retain flag is set only when the subscription found under the topic name asks for retain-as-published.
  - **Packet-ID records on a clean start:** Artemis's `JournalHashMap.clear` removes the client's packet-ID correlations from memory but leaves their records in the journal, so they come back after a restart. Saranga deletes them. Either broker reads the other's journal.
- **A second CONNECT** on a connection closes it, after a DISCONNECT 0x8E (session taken over) for MQTT 5. That is what Artemis's link stealing ends up doing when the client ID is the same. Artemis would instead start a second session if the client ID differed.
- **The connection TTL** closes a silent connection when it runs out. Artemis notices at its next `connection-ttl-check-interval`, up to that much later.
- **`mqtt-session-state-persistence-timeout`** is accepted and reported as deprecated (`AMQ221038`), as in Artemis, but as a warning rather than at INFO level.
- **Interceptors** (Java classes) and connection routers (redirects) are not supported. The cluster-wide `SESSION_CREATED` notification that disconnects a client connected to another node waits for clustering (Phase 10).
- **A large message** (over the journal's record size) published as a retained message stays a regular message in the retained-message queue. Artemis converts it to a large message there.

## AMQP differences
- **The Open's `product` and `version`** properties are `saranga` and its version. Artemis sends `apache-activemq-artemis` and its own.
- **Artemis bugs not copied:**
  - **Link failures:** some link failures close the whole connection in Artemis with `amqp:internal-error` "Unrecoverable error: ...". Examples are a receiver attach with no target, and an exception from the core broker while attaching a consumer (a missing queue, an FQQN filter mismatch). Saranga refuses only that link, with the same error.
  - **Unknown transactions:** a transfer that names an unknown transaction closes the connection in both brokers. Artemis still routes the message, outside any transaction; Saranga does not.
  - **Failed SASL outcomes:** Artemis leaves the socket open after a failed outcome, and PLAIN with no initial response is an internal error there. Saranga closes the socket after the outcome and answers PLAIN with no response with outcome `auth`.
  - **Outcomes inside transactional states:** Released, Rejected and Modified wrapped in a transactional state do nothing in Artemis, so the message stays delivered to the consumer. Saranga applies them as it would outside a transaction.
  - **Delivery tags** go back to the session's pool only when a delivery is settled. Artemis returns them on every disposition, so two unsettled deliveries can share a tag.
  - **Conversion to Core:**
    - An `amqp-value` body of a type other than null, string, binary, list or map becomes a BytesMessage holding the encoded section. Artemis copies the wrong bytes there (docs/upstream/artemis-issues.md, issue 7).
    - An application property or stream item that Core has no type for is left out. Artemis fails the whole conversion.
- **Not supported yet:**
  - **SASL mechanisms:** SCRAM-SHA-256/512, GSSAPI, OAUTHBEARER and XOAUTH2. An acceptor's `saslMechanisms` that lists them gets outcome `sys` for them.
  - **Core-message tunnelling** (`AMQ_CORE_MESSAGE_TUNNELING`): Core messages always go out converted to AMQP.
  - **Broker connections, federation and mirroring links** (Phase 10). Their link names and capabilities are treated as ordinary links.
  - **Connection routers and interceptors.**
  - **Credit under an address-full policy:** credit is not withheld from producers to a full address under BLOCK. There is no reject threshold, no drain on transient errors, and no link quiesce timeout.
  - `maxTransfersPerDelivery`.
  - The `failover-server-list` connection property.
- **Large messages:**
  - An AMQP large message is held whole in memory while the broker holds it. It is also written to its large-message file, with Artemis's record, so either broker reads the other's.
  - A copy to a dead-letter or expiry address copies the file as it is. Artemis rewrites the copy's header and properties without the expiry.

## OpenWire differences
- **`brokerName`** defaults to the host name from `HOSTNAME`, `COMPUTERNAME` or `/etc/hostname`, lowercased, then to the node ID. Artemis asks the JVM for the local host name.
- **Browsers** get a snapshot of the queue when they are created, all of it at once, then the end-of-browse dispatch. Artemis walks the live queue within the browser's prefetch.
- **A pull with no timeout** (prefetch 0, `receive()` or `receiveNoWait()`) gets its null dispatch when the forced-delivery marker reaches the consumer. Artemis blocks the connection's commands until then, for up to 10 seconds.
- **A poison acknowledgement** inside a transaction moves the message to the dead-letter address at once. Artemis moves it when the transaction commits.
- **Removal advisories** on connection close are sent for the temporary destinations the connection made. Artemis also sends them for the temporary subscription queues of its topic consumers, under `ActiveMQ.Advisory.TempQueue`.
- **Dispatched properties** of messages that came from Core or the journal are marshalled in the order they were put, not in the order of a freshly decoded Java `HashMap`. Clients read them into a map.
- **Not supported yet:**
  - Address-full policies for OpenWire producers: BLOCK does not pause the connection's reads, and FAIL does not answer `ResourceAllocationException`.
  - The `ConsumerControl` that tells a client about `queue-prefetch` 0.
  - The slow-consumer advisory.
  - Marking advisory addresses and subscriptions internal (`suppressInternalManagementObjects`), and the DROP policy on advisory subscriptions.
  - `ConnectionControl` for cluster clients (`updateClusterClients`, `rebalanceClusterClients`), connection routers and interceptors.
  - The `openwireMaxPacketChunkSize` and `actorThresholdBytes` back-pressure: frames are read and written whole.

## WebSocket differences
- **A broker write is one WebSocket message**, which can hold several protocol frames: the connection's writer batches what is ready. Artemis sends each protocol frame as its own message. Clients read the payloads as a stream.
- **A refused upgrade.** An upgrade request that is not a GET gets `403 Forbidden`. Artemis does not answer it.
- **A frame over the maximum payload** gets a close frame with status 1009 before the connection closes. Artemis closes the connection, and its close frame may not arrive.
- **Not supported yet:**
  - `webSocketCompressionSupported` (permessage-deflate).
  - The draft-00 handshake of clients that send no `Sec-WebSocket-Version`: they get `426 Upgrade Required`.
  - Core over HTTP (`httpEnabled`, `HttpAcceptorHandler`): an HTTP request without a WebSocket upgrade gets `403 Forbidden`.

## Management differences
- **`getVersion`** reports 2.57.0, the Artemis release whose management interface Saranga answers, so tools that check the version keep working.
- **`browse`** over management messages answers `no operation`, by design. Artemis answers it with JMX `CompositeData` objects, Java-serialized and base64-encoded inside the JSON, which only a Java client can read; Saranga does not produce Java serialization. `listMessages` and `listMessagesAsJSON` return the same messages as plain JSON, and the REST API (`GET /api/queues/{name}/messages`) and the Jolokia layer return `browse`'s messages as JSON.
- **`changeMessagesPriority`** changes the messages in memory. Artemis also changes paged messages it reads in through the queue's own cursor; Saranga leaves messages still in pages as they are.
- **`listBindingsForAddress`** names a queue binding as `LocalQueueBinding [address=..., queue=...]`. Artemis prints its queue object there, with an identity hash.
- **Connection IDs** are eight random hex digits, as Netty's short channel IDs look, but not Netty's.
- **Dates** in the `list*` views (`creationTime`) are written as `Date.toString` writes them in UTC, and those of the prepared transactions as `DateFormat`'s short date and medium time in the `en_US` locale, in UTC. Artemis uses the JVM's time zone and locale.
- **`proxyAddress` and `proxyProtocolVersion`** are always empty: Saranga does not take the PROXY protocol.
- **`closeSessionWithID`** closes Core sessions only. For a session of another protocol it returns false; Artemis closes the server side of any session.
- **A STOMP consumer closed by management** is removed from its session after the `ERROR` frame. Artemis drops the subscription but leaves the server consumer in place.
- **`getRoles` and `getRolesAsJSON`** list roles in the order the setting gives them. Artemis lists them in `HashSet` order.
- **`listUser`** lists users and each user's roles in the order Java's `HashMap` and `HashSet` iterate them, as Artemis does. For a basic security manager the users are first put in name order; Artemis puts them in the order of its own map of the journal's users, so a long list can come out in a different order.
- **`listNetworkTopology`** returns `[]` until clustering (Phase 10): the topology of a broker without cluster connections.
- **Notifications** not sent yet: those of `NotificationActiveMQServerPlugin` (`CONNECTION_CREATED`, `CONNECTION_DESTROYED`, `ADDRESS_ADDED`, `ADDRESS_REMOVED`, `MESSAGE_DELIVERED`, `MESSAGE_EXPIRED`; plugins come in stage 5), and those of clustering, bridges, discovery and grouping (Phase 10). A divert's `BINDING_ADDED` carries a new ID in `_AMQ_Binding_ID`, as Saranga's diverts have none of their own.
- **`management-message-rbac`** checks the permission before it looks for the operation. For an operation that does not exist, a caller without the permission gets the permission error; Artemis looks for the operation's method first and answers `AMQ229069: no operation`.
- **Message counter dates** are in UTC, as the other dates are, and so are the hours of a counter's history.
- **The slow-consumer advisory** (`ActiveMQ.Advisory.SlowConsumer.*`) is not sent to OpenWire clients; the `CONSUMER_SLOW` notification and the `KILL` policy work for consumers of every protocol.
- **Slow consumers** are checked by one task for all queues, within 200 ms of each queue's check period. Artemis schedules a task for each queue.
- **Records.** Paused queues and addresses, address settings and diverts are journaled as Artemis journals them (`QUEUE_STATUS_RECORD`, `ADDRESS_STATUS_RECORD`, `ADDRESS_SETTING_RECORD_JSON`, `DIVERT_RECORD`), so they move with the data directory in both directions. Like Artemis, Saranga journals every deployed divert, configured ones included.

## Web server differences
Artemis serves its web console, with Jolokia, and the metrics plugin's app. Saranga serves:
- **A REST API at `/api` on every binding**, which Artemis does not have. It is Saranga's documented management interface: the resources, operations and security of management messages, as plain JSON over HTTP (see `crates/saranga-management/src/rest.rs`). With broker security off it asks for no login, as the Core acceptors do.
- **The metrics** where `bootstrap.xml` declares the metrics app. JVM, process and Netty metrics are not exported; the broker, address and queue metrics are.
- **A Jolokia compatibility layer, not the web console.** Where `bootstrap.xml` declares the console's app, `/console/jolokia` answers the Jolokia 2.4.3 protocol from Rust: there is no JMX and no Java. The console's pages (hawtio) are not served, so the Artemis console must be run elsewhere and pointed at it. Without the console's app there is no Jolokia layer. Its approximations:
  - Only Artemis's MBeans exist: no `java.lang`, `JMImplementation` or `jolokia` MBeans.
  - An operation that fails answers status 500 and the failure's text, with the `error_type` of the class Artemis's message bundles declare for its AMQ code (`scripts/gen-exception-catalog.py`), or `java.lang.IllegalStateException` for the `ActiveMQServerControl` methods that rethrow as one. A failure without an AMQ code answers `java.lang.Exception`, where Artemis may name another class.
  - `list` gives no `ctor` (constructors) entries.
  - The console roles come from `-Dhawtio.roles`, `HAWTIO_ROLES` in `artemis.profile` or `-Dhawtio.roles=` in `artemis.profile.cmd`, and are `amq` by default.
  - Who may call what is `management.xml`'s `<authorisation>`, as Artemis's guard applies it. Without one, and with `-Djavax.management.builder.initial=org.apache.activemq.artemis.core.server.management.ArtemisRbacMBeanServerBuilder` among the system properties (the profile's `JAVA_ARGS`), the broker's security-settings on `mops.` addresses (`management-rbac-prefix`) guard the MBeans as Artemis's `ArtemisRbacInvocationHandler` does: each attribute and operation needs `view` or `edit` (by `view-permission-method-match-pattern`) on `mops.<component>.<name>.<method>`, a refusal answers status 403 with the `AMQ229032` message, and `search`, pattern reads and `list` keep only the MBeans the caller may view.
  - The overloads of an operation are listed in an order fixed by the catalog. Java lists them in `Class.getMethods` order, which can differ from one JVM run to the next.
- **`browse`'s messages** (in both APIs) are shown in the layout of Core messages' `toCompositeData`. An AMQP message is shown converted to Core, with `protocol` `AMQP`; Artemis shows it with the AMQP message's own items. A bytes property appears in `PropertiesText` as `[B@` and a number, as in Java, but not the same number.

## CLI differences
The Artemis CLI's `queue`, `address`, `user`, `producer`, `consumer`, `browser`, `transfer`, `check` and `stop` work against Saranga unchanged. The `saranga` command has them too, with the same options and output; these are the differences:
- **Connections** are Core over plain TCP. A URL with `sslEnabled=true` is refused, `--protocol AMQP` (and `--source-protocol`/`--target-protocol amqp`) is not supported, and of a list of URLs (`(tcp://a:61616,tcp://b:61616)`) only the first is used.
- **The default URL** comes from the instance's acceptor called `artemis` (or `--acceptor`), as in Artemis. Artemis also looks for a connector of that name; Saranga does not read connectors yet.
- **Files of messages** (`producer --data`, `consumer --data`) and `--serializer` are not supported: the XML message format is not ported yet.
- **A failed connection** is reported as Artemis reports it (`Connection failed::<reason>`), then, unless `--silent` is given, the URL (not when the credentials were refused), the user and the password are asked for and the connection is tried once more, as Artemis does, with a terminal or without. Standard input ending at a question fails the command as Artemis's does (`No line found`, then the usage). Where Artemis ends in an uncaught exception, with `--silent` or when the second try fails too, it prints the stack trace; Saranga prints one line and stops with status 1, as Artemis does.
- **`browser --verbose`** prints a message as `ActiveMQMessage[<id>]:PERSISTENT`. Artemis appends the Core message's own `toString`.
- **`--verbose`** does not print the `Executing <class> <arguments>` and `Home::...` lines.
- **`help`** prints Artemis's help: picocli's usage message of the command, laid out as picocli lays it out at 80 columns, with Artemis's descriptions and the commands `buildCommand` offers from an instance, from the home and in the shell. The commands Saranga does not have yet (`lock`, `properties`, `activation` and `check cluster`) are left out, and it is printed without picocli's colours. Every option it lists is one Saranga takes: `run` takes the data tools' folder options, which Artemis's takes and does not use. `saranga --help` (and `-h`) prints Saranga's own help, its own options included.
- **`queue stat --loop`** prints the time of each iteration in UTC.
- **Connection URLs** of the messaging commands (`producer`, `consumer`, `browser`, `queue`, `address`, the shell's `connect` and the like) take a list of servers, `(tcp://a:61616,tcp://b:61616)?params`, tried in turn from a random one as Artemis's round-robin policy tries them, and the `ServerLocator` parameters `ha`, `reconnectAttempts`, `failoverAttempts`, `initialConnectAttempts`, `retryInterval`, `retryIntervalMultiplier`, `maxRetryInterval`, `callTimeout`, `callFailoverTimeout`, `clientFailureCheckPeriod` and `connectionTTL`; the others are ignored. With `reconnectAttempts`, a connection fails over to the backup its server's topology names, then to the other servers, and recreates its sessions and consumers there, as Artemis's client does. The consumer credits and expiries it would send while a failover is in progress are dropped rather than held until it ends; the failover gives each consumer its credits again. On Windows, `binrtemis.cmd` hands its arguments to `cmd` again, which takes an `&` as the end of the command even inside quotes, so separate the parameters with `;`, which Artemis and Saranga both accept.
- **`saranga create`** writes the instance `artemis create` writes, from the same templates: the `etc/` files are the same but for the password hash's salt and the paths. `bin/` holds `artemis` and `saranga` (`artemis.cmd` and `saranga.cmd` on Windows), which run the `saranga` that made the instance, for the instance, and on Unix `artemis-service`, unchanged; there is no Windows service wrapper (`artemis-service.exe`). Without `--aio`, `--nio` or `--mapped` the journal type is `NIO`, as Artemis chooses where libaio is missing. The auto-tuning measures the NIO writes only. `--clustered`, `--static-cluster`, `--shared-store`, `--backup` and `--failover-on-shutdown`, with the cluster user and password, write the cluster and shared-store settings Artemis writes; `--replicated`, `--discovery-enabled` (Saranga has no discovery yet) and `--jdbc` are refused. The messages printed name Saranga.
- **`saranga run`** with neither `--config` nor `--etc` runs the instance named by `ARTEMIS_INSTANCE`, as an instance's `bin/artemis run` does, and stops cleanly on SIGTERM as well as on Ctrl-C, so `artemis-service stop` works. Its configuration URI picks another bootstrap file, as `artemis run -- xml:path/to/bootstrap.xml` does (the path relative to the current directory), and `--broker` another `broker.xml`; a URI with no scheme, another scheme than `xml`, or a file that is not there is refused with Artemis's `Invalid configuration URI` messages, and status 1.
- **The data tools** (`data print`, `exp`, `imp`, `compact`, `encode`, `decode` and `recover`) take the same options and print the same output, the JDBC ones included, though `--jdbc` is refused (Saranga has no JDBC store) and the others go unused, as Artemis leaves them without it: the configuration URI (`xml:<bootstrap.xml>`, refused as Artemis's `ConfigurationException` is, with status 1), `--verbose`, and for `print`, `exp` and `recover` `--f`, which skips the CLI lock so the data of a running broker can be read, and `--output`. `data exp` takes `log-interval` and `undefined-prefix` as Artemis declares them, without dashes (issue 11), and with them; on the golden data directories `data exp` writes Artemis's XML byte for byte and `data encode` its text. Without `--directory`, `encode` and `decode` use `broker.xml`'s `journal-directory` as written, so a relative one is taken from the current directory, not the instance, as Artemis's do (`getJournalDirectory`); from an instance's `bin`, the default `data/journal` is not there. `data imp` sends over Core only, to `--url`, or to `--host` and `--port` when `--host` is given (Artemis ignores `--port` alone). Like Artemis, they take the instance's CLI lock, so they refuse an instance whose broker is running. When a tool fails, it says so as Artemis's `treatError` does: `Error:<message>` on stderr between blank lines, with exit status 0. A held lock, or a missing directory for `print` or `recover`, ends the command with status 1, the latter with the usage hint. Java's stack traces are not printed.
- **`version`** prints `Saranga <version> (Apache Artemis 2.57.0)`, then the home and instance lines.
- **`kill`** writes `KILL_ME`, which a broker honours only when it was started with `run --allow-kill`, as in Artemis.
- **`perf client`, `producer` and `consumer`** take the same options and print the same reports, `--json` file and `--hdr` log (HdrHistogram's log format, readable by its tools). A send completes as soon as it is written, as the Core JMS client's `CompletionListener` does without a confirmation window, so `--max-pending` never holds a send back and `total blocked` stays 0. Artemis 2.57's own `perf producer` can stall over Core with the default `--max-pending 1`: a completion is lost while the producer waits for one, and the run never ends; `--max-pending 0` avoids it. The JVM's notice that it has no microsecond clock is not printed.
- **`perf-journal`** measures every journal type with plain file writes and `fdatasync`, as Artemis's `NIO` does; `--max-aio` has no effect. It also works outside an instance, on `./data/journal`; Artemis has it only in an instance's CLI.
- **`upgrade`** rewrites an instance's scripts and profiles as `artemis upgrade` does, with the same steps, backups (`old-config-bkp.<n>`) and kept lines (`ARTEMIS_INSTANCE_ETC`, the data and dump paths, `HAWTIO_ROLES`, `-Xmx` and the other kept JVM arguments), and the same `bootstrap.xml` and logging changes. Its `bin/artemis` then runs this `saranga`, so `saranga upgrade` moves an Artemis instance to Saranga and `artemis upgrade` moves it back. It also writes `bin/saranga` (`saranga.cmd`) beside `bin/artemis`. On Windows, an Artemis instance's service wrapper (`artemis-service.exe`, its `.config` and `artemis-service.xml`) is left as it is.
- **`completion`** prints the bash (and zsh) completion script `artemis completion` prints, generated as picocli 4.7's `AutoComplete.bash` generates it from Artemis's command line: TAB offers the subcommands, a word starting with `-` the options, and after an option that takes a value its candidates (`--protocol`'s `AMQP` and `CORE`) or file names. For the commands Saranga has, the script is Artemis's, byte for byte; `lock`, `properties`, `activation` and `check cluster` are left out, as `help` leaves them out.
- **`shell`**, and `saranga` without a command, run the CLI's commands typed at a prompt, as `artemis shell` does. In it, `connect` keeps a URL, user and password for the commands that follow and `disconnect` forgets them; the first command to connect keeps its own the same way, and the prompt names the connection. The history file is `--history`, else `ARTEMIS_SHELL_HISTORY` (which an instance's `bin/artemis` takes from its profile on Linux, where it defaults to `~/.artemis_history`, as Artemis's does), else the instance's `etc/history-file` after the same question, written in JLine's format. The differences: there is no line editing, completion or recall, since Saranga reads plain lines; the banner and prompt name Saranga. An empty line, and one starting with `#`, run nothing, as JLine's command registry has it. Without a terminal the lines of standard input are read at the prompts, as Artemis reads them through JLine's dumb terminal, except after a history question: Artemis's answer is read by a buffering `Scanner` that takes the lines after it too, so they never run there, and here they do.
- **Not there yet:** `properties` (Artemis builds its output by reflection over its configuration classes), and `lock` and `activation`, which belong with high availability (Phase 9).
- **`user` and `stop`** are always there; Artemis has them only in an instance's CLI. `stop` finds the instance through `ARTEMIS_INSTANCE` (or `ARTEMIS_INSTANCE_ETC`), as an instance's `bin/artemis` sets it, through a `xml:<bootstrap.xml>` argument, or through `--broker <broker.xml>`.

## Logging differences
`saranga run` logs as Artemis does: it reads the instance's `etc/log4j2.properties` (or the file `-Dlog4j2.configurationFile` names, on `saranga run` or in the profile's `JAVA_ARGS`) and writes Artemis's format, codes and logger names to its console and files, so runbooks that read `log/artemis.log` or change levels in that file work unchanged (see `crates/saranga-cli/src/logging.rs`). The differences:
- **Logger names.** Each message is logged under the logger of the Artemis message bundle its code belongs to (`AMQ22xxxx` under `org.apache.activemq.artemis.core.server`, `AMQ14xxxx` under `org.apache.activemq.artemis.journal`, and so on). A message without a code is logged under one logger for its component, where Artemis uses the class's own logger, so a level set for a single Artemis class has no effect.
- **Messages.** The startup and shutdown messages runbooks look for are there, with their codes (`AMQ101000`, `AMQ221000`, `AMQ221001`, `AMQ221002`, `AMQ221007`, `AMQ221020`, `AMQ241001` and the like); their text names Saranga and its version where Artemis names itself. Other messages carry Artemis's code and text where Saranga has the same event; Saranga's own messages have no code. JVM and Netty messages do not exist.
- **log4j 2.** The properties format is supported, with `Console`, `File` and `RollingFile` appenders, `PatternLayout`, `ThresholdFilter`, logger levels, appender references and additivity, `${sys:}`, `${env:}` and `property.` lookups, and `monitorInterval`. Rolling follows the date in `filePattern`: a `CronTriggeringPolicy` rolls when that date changes, whatever its schedule. XML, JSON and YAML configurations, other appenders and layouts, async loggers and colours are not supported; what is not understood is logged as a warning. `%t` is the Rust thread's name.
- **`RUST_LOG`**, when set, chooses what is logged in place of the configured levels, except that loggers set to `OFF` stay off.
- **The CLI's other commands** log as Artemis's `bin/artemis` has every command but `run` log (`artemis-utility.profile`): WARN to the console in Artemis's pattern, configured by the instance's `etc/log4j2-utility.properties` when there is one.

## Audit log differences
The three audit loggers (`org.apache.activemq.audit.base`, `.resource` and `.message`) are off unless `log4j2.properties` turns them on, as in Artemis, and log the same codes, texts and callers (`user(roles)@address`). The base logger's message for each management method comes from a catalog generated from Artemis's `AuditLogger` and `*ControlImpl` classes (`scripts/gen-audit-catalog.py`), so a method logs what Artemis's control logs, quirks included (the management `createQueue` and `destroyQueue` name their caller `anonymous`). Management calls are audited whichever way they come: management messages, the REST API or the Jolokia layer. [tests/interop/audit/audit.sh](tests/interop/audit/audit.sh) checks a CLI session's audit log against Artemis 2.57.0's. The differences:
- **Objects in messages** (sessions, connections, messages, routing contexts, transactions, queues, addresses) are shown in their Java classes' `toString` layout with Saranga's values. Their identity hash codes are not Java's, dates in them are in UTC, and a session's parameters show its connection briefly.
- **Not logged:** MBean registration and the JMX guard (601019, 601138, 601718), which Saranga does not have; the getters Artemis's list views (`listQueues` and the like) call on each queue's control; acknowledgements made without a consumer (`system@internal`: messages removed by management, expired, or left on a deleted queue); the end of XA branches; and the broker's own sends (management replies, OpenWire advisories).
- **Callers.** The console's (Jolokia) callers have no address (`@unknown`), as in Artemis. REST API callers, which Artemis does not have, have theirs. `%t` in the audit pattern is a Saranga thread's name.
- **Security failures** (601264) are logged without the stack trace Artemis appends.

## Critical analyzer differences
The analyzer reads `critical-analyzer`, `critical-analyzer-timeout`, `critical-analyzer-check-period` and `critical-analyzer-policy` as Artemis does, and watches the components Artemis watches: the journal's writer (Artemis's `TimedBuffer`), each queue and each session. A component past the timeout is reported once, with AMQ224107, AMQ224081/AMQ224080/AMQ224079 and AMQ222199, and the plugins are told (`criticalFailure`). LOG only logs, SHUTDOWN stops `saranga run` cleanly and HALT ends the process with status 70. The differences:
- **The "thread dump"** (AMQ222199) lists the components in a critical path and how long each has been there. A Rust process cannot dump its threads' stacks.
- **What a path covers.** A queue is in its critical path while its task handles one command, and a session while it sends or acknowledges, so the paths are not drawn exactly where Artemis's `CriticalMeasure`s are.

## Network check differences
`saranga run` reads `network-check-list`, `network-check-URL-list`, `network-check-period`, `network-check-timeout` and the ping commands as Artemis does (`NetworkHealthCheck`). Each address and URL is checked once as it is added, with AMQ202001, AMQ202002 and AMQ202003, and then every period. While none answers, the broker is stopped (AMQ201001). Once one answers again, a new broker is started on the same data and ports (AMQ201000), and the web server serves it. The runbook suite takes an instance made with `create --ping` through a network outage and back. The differences:
- **Reachability.** Without a custom ping command, an address first gets a TCP connection to its echo port (7), and a refusal counts as an answer, as `InetAddress.isReachable` does without privileges. Saranga never sends ICMP itself. When there is no answer, it runs the ping command, as Artemis does.
- **`network-check-NIC`** is reported and not used: the addresses are checked through any interface.
- **`https` URLs** are reported and not checked, as Saranga has no root certificate store. `http` and `file` URLs are checked.
- **Host names** are given to the ping command as the address they resolve to. Artemis gives the canonical host name from a reverse lookup.
- **An unhealthy network at startup** stops the broker right after it has started, as in Artemis. Artemis's `run` then fails to register the web server with the stopped broker (`IllegalStateException`) and the process exits. Saranga keeps the process and its web server, and starts the broker once the network answers.
- **While the broker is stopped**, the web server serves the stopped broker's last state. Artemis unregisters its MBeans.

## Broker plugin differences
A plugin is Rust code implementing `saranga_server::plugin::BrokerPlugin`, the equivalent of `ActiveMQServerPlugin`, registered by an embedding application in `BrokerConfig::plugins` or with `Broker::register_plugin`. `<broker-plugins>` in `broker.xml` selects Saranga's ports of the plugins Artemis ships, by their Java class names and with their properties: `LoggingActiveMQServerPlugin`, `NotificationActiveMQServerPlugin`, `BrokerMessageAuthorizationPlugin` and `ConnectionPeriodicExpiryPlugin`. [tests/interop/plugin/plugin.sh](tests/interop/plugin/plugin.sh) checks the logging plugin's lines for a CLI session against Artemis 2.57.0's. The differences:
- **Other classes.** A `<broker-plugin>` naming any other class is Java code Saranga cannot run, and the broker does not start: leaving out what such a plugin enforces could open what it closes. The same goes for a built-in plugin's own configuration errors.
- **Hooks.** Saranga has the hooks for connections, sessions (not `beforeCreateSession`), session metadata, consumers, addresses (adding and removing), queues, bindings of queues, sends, routing, `canAccept`, deliveries, acknowledgements, expiry and critical failures. It does not have the hooks for bridges, federation, diverts' bindings, `beforeRemoveAddress`, `updateAddress` or message moves, and the routing hooks are not given the transaction. Hooks run on the broker's tasks: a plugin must not block.
- **Arguments.** A message's acknowledgement is reported without its transaction (the logging plugin prints `with transaction: null`) and without its consumer; a destroyed queue is reported without the session that destroyed it (`session: null`).
- **Notifications.** The notification plugin's `MESSAGE_EXPIRED` has no `_AMQ_ConsumerName`, as expiry by a consumer is reported as by the reaper.
- **Objects in messages** print as in the audit log (Saranga's values, identity hashes not Java's), and a message's properties are in insertion order, not a Java `HashMap`'s.

## Security differences
- **Login modules.** `PropertiesLoginModule`, `GuestLoginModule`, `TextFileCertificateLoginModule`, `ExternalCertificateLoginModule` and `LDAPLoginModule` are supported. `Krb5LoginModule`, `KubernetesLoginModule`, `PrincipalConversionLoginModule` and custom Java modules are not. A `login.config` entry that names one gets a warning at startup, and logins that reach that module fail.
- **Security managers.** The JAAS security manager (`<jaas-security>`) and `ActiveMQBasicSecurityManager` are supported. The basic manager keeps its users in the bindings journal, so its users move with the data directory in both directions. Any other `<security-manager>` class stops the broker from starting. As in Artemis, the basic manager has no users without persistence. Users are added through the bootstrap credentials or through management (`addUser`).
- **A role named `*`** in a security setting grants nothing in Artemis 2.57, despite looking like a wildcard. Saranga matches this.
- **Security setting plugins** (`<security-setting-plugin>`) are not supported and produce a warning.
