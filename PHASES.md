# Saranga phases

Saranga is built in twelve phases. Each one ends with something runnable, and its exit check runs against real Artemis clients or real Artemis data, never only against Saranga's own tests. The design behind the phases is in [docs/design.md](docs/design.md). The pinned Artemis version (2.57.0) and the deliberate wire quirks are in [COMPAT.md](COMPAT.md).

| Phase | Name | Status |
|---|---|---|
| 0 | Foundation | Done |
| 1 | Encoding primitives | Done |
| 2 | Single-node in-memory broker (Core) | Done |
| 3 | Persistence, on-disk compatible (first usable release) | Done |
| 4 | Queue semantics parity | Done |
| 5 | Paging and large messages | Done |
| 6 | Config and security | Done |
| 7 | Protocols (AMQP, MQTT, STOMP, OpenWire, WebSockets) | Done |
| 8 | Management and operations | Done |
| 9 | High availability | Done |
| 10 | Clustering and federation | Done |
| 11 | Hardening and 1.0 | In progress |

Phase 3 is the first release anyone could adopt. Every phase after it can ship as a minor release. Work planned for after 1.0 is in [FUTURE.md](FUTURE.md).

---

## Phase 0: Foundation (done)

**Scope**
- Cargo workspace with one crate per subsystem, CI on Linux and Windows (fmt, clippy with warnings as errors, tests, cargo-deny), Apache-2.0 licence and NOTICE.
- Artemis 2.57.0 pinned and built from source into the Docker image `saranga/artemis-ref:2.57.0` by [scripts/build-artemis.sh](scripts/build-artemis.sh).
- Golden-corpus harness:
  - [scripts/golden.sh](scripts/golden.sh) runs a Java client scenario against the real broker through a recording proxy ([tools/saranga-capture](tools/saranga-capture)) and keeps the broker's data directory.
  - [scripts/packet-fixtures.sh](scripts/packet-fixtures.sh) has the real Java classes encode single packets.
- ADRs for the runtime model, I/O backends and error model in [docs/adr/](docs/adr/).

**Exit check (met):** CI is green, and the harness starts a Java broker and collects golden data.

## Phase 1: Encoding primitives (done)

**Scope**
- `saranga-buffer`: Artemis buffer semantics, `SimpleString`, Java string encodings, `TypedProperties`, both nullable encodings.
- `saranga-message`: the `CoreMessage` codec.
- `saranga-core-protocol`: frames and every Core packet type, about 120 of them, across protocol versions 121 to 136. This covers connection, session, XA, large-message, cluster/HA/federation and replication traffic.

**Exit check (met)**
- Every frame in the recorded conversations (`core-basic`, `core-xa`, `core-large`) decodes to a typed packet and re-encodes byte for byte. `tests/golden_wire.rs` fails if any packet falls back to `Unknown`.
- 208 fixtures encoded by the Java classes re-encode byte for byte (`tests/golden_packets.rs`).
- Every packet type constant in Artemis has a decoder.

## Phase 2: Single-node in-memory broker, Core protocol (done)

**Scope**
- TCP acceptor (`saranga-transport`) that accepts the `ARTEMIS` handshake and Core frames.
- Connections: pings and connection TTL, the cluster-topology subscription (answered with a single-node topology), and disconnect.
- Sessions: create/close, start/stop, metadata, and the queue and binding queries the JMS client issues before every producer and consumer.
- Addresses and queues: ANYCAST and MULTICAST routing, wildcards, fully qualified queue names (FQQN), auto-create and auto-delete. Everything in Phase 2 is kept in memory, durable or not.
- Producers and consumers with credit-based flow control: producer credits and the consumer window.
- Acknowledgements (individual and cumulative), local transactions (commit and rollback, with redelivery and delivery counts) and browse-only consumers.
- Enough of `broker.xml` for acceptors, address-settings (with Artemis's match rules) and addresses.
- The JMS selector engine (`saranga-filter`). It was planned for Phase 4, but durable subscriptions with selectors are part of the Phase 2 exit check, so it moved forward.
- `saranga run`.
- A minimal Rust Core client (`saranga-client`).

**Exit check**
- The Artemis JMS client passes send/receive, queue, topic, durable-subscription, transacted and client-ack tests against `saranga run`. `scripts/interop.sh saranga` runs [tests/interop/jms/Phase2.java](tests/interop/jms/Phase2.java) (24 tests) and the `core-basic` golden scenario; `scripts/interop.sh artemis` runs the same suite against the reference broker, so a wrong test shows up there first.
- The Rust client sends and receives through Saranga.

**Exit check (met)**
- All 24 JMS interop tests and the `core-basic` golden scenario pass against `saranga run`, as they do against Artemis 2.57.0.
- The Rust client (`saranga-client`) passes the same 9 broker tests against Saranga and against Artemis. CI runs them against `saranga run` on Linux and Windows.

**Deferred to later phases on purpose:** XA (Phase 3), large messages (Phase 5), expiry and dead-letter addresses, redelivery delay and max delivery attempts (Phase 4), acceptor address prefixes and the 1.x client prefixes (Phase 6), security (Phase 6).

## Phase 3: Persistence, on-disk compatible (first usable release)

**Scope**
- Journal file format: file headers, every record type, transactional records, reclaim, and compaction with its rename protocol.
- The bindings journal and the full set of `StorageManager` record IDs.
- Recovery on restart, XA (prepare, commit, rollback, recover) and the group-commit journal writer.
- Durable messages.
- `saranga data print`.

**Exit check**
- The Java broker recovers a data directory Saranga wrote, and Saranga recovers one the Java broker wrote, for every scenario in the corpus.
- Crash tests that kill the broker with `kill -9` lose no committed messages.

**Exit check (met)** — `scripts/cross-store.sh` runs all of it:
- Saranga recovers every golden data directory Artemis 2.57.0 wrote (7 scenarios, including a killed broker and a journal Artemis compacted) and a client sees what it saw on Artemis (`recovered.txt`). Three scenarios differ only through features of later phases: large messages (Phase 5), scheduled delivery and message groups (Phase 4).
- [tests/interop/jms/Persist.java](tests/interop/jms/Persist.java) passes in every direction through `scripts/persistence.sh`: Saranga to Saranga, Artemis to Saranga and Saranga to Artemis, each after a clean stop and after a kill. It covers persistent and non-persistent messages, acknowledgements, durable subscriptions with selectors, local transactions, persisted delivery counts, prepared XA branches, queue attributes and 4,000 messages over several journal files.
- `scripts/journal-interop.sh`: Artemis's `JournalImpl` loads a journal Saranga wrote (with compaction and every record type) to the same records, and the reverse.
- Every record of every golden journal re-encodes byte for byte, at the journal level (`saranga-journal`) and at the record-body level (`saranga-storage`). `saranga data print` prints what `artemis data print` prints for all 7 scenarios.
- XA in Core sessions: [tests/interop/jms/Phase3.java](tests/interop/jms/Phase3.java) (9 tests) and the `core-xa` scenario pass against Saranga and Artemis.

**Deferred to later phases on purpose:** scheduled-delivery and duplicate-ID records are kept in the journal but not acted on (Phase 4); large messages and paging records are read but not recovered (Phase 5); heuristic completions and `xaForget` (Phase 8); transaction timeouts (Phase 4). Compaction blocks appends while it runs (see COMPAT.md).

## Phase 4: Queue semantics parity

**Scope**
- The address-settings match hierarchy, dead-letter and expiry addresses, redelivery delay and backoff, and max delivery attempts.
- Scheduled delivery, duplicate detection and priority.
- Queue types: message groups (including rebalancing), exclusive, last-value, non-destructive, ring and temporary queues.
- Consumer filters: the selector engine is already done (Phase 2); what remains is the delivery cost of filtered consumers (per-consumer cursors).
- Diverts, exclusive and non-exclusive, with transformers written as Rust plugins.
- Consumer-window tuning.

**Exit check:** the ported Artemis integration tests for each feature pass.

**Exit check (met)**
- [tests/interop/jms/Phase4.java](tests/interop/jms/Phase4.java) has 48 tests ported from the Artemis integration tests. They cover:
  - the address-settings hierarchy;
  - dead-letter and expiry addresses, including auto-created resources and send-to-DLA-on-no-route;
  - redelivery delay and backoff;
  - expiry, both from the reaper and reported by the client;
  - scheduled delivery and duplicate detection;
  - priority, message groups (buckets, rebalance, first key), and exclusive, last-value, non-destructive, ring and temporary queues;
  - consumers-before-dispatch and delay-before-dispatch;
  - selectors, diverts, consumer windows and XA transaction timeouts.

  Run with [tests/interop/jms/phase4.broker.xml](tests/interop/jms/phase4.broker.xml), they pass against Artemis 2.57.0 and against Saranga: `CONFIG=tests/interop/jms/phase4.broker.xml SUITE=Phase4 scripts/interop.sh saranga`.
- The Phase 2 and Phase 3 suites still pass.
- `scripts/cross-store.sh` still passes. Saranga now recovers the `persist-durable` and `persist-crash` golden scenarios (scheduled messages and message groups) exactly as Artemis does. Only `core-large` waits for Phase 5.
- Divert transformers are Rust plugins: a `Transformer` registered in `BrokerConfig::transformers` under the class name that `broker.xml` gives.

**Deferred on purpose:**
- Per-consumer cursors for filtered consumers, a delivery-cost optimisation, to Phase 11.
- Diverts and queues created through management, and the slow-consumer policy, to Phase 8.
- Redistribution delay, to Phase 10.

The behaviour differences are listed in COMPAT.md.

## Phase 5: Paging and large messages

**Scope**
- Page stores, page cursors, page transactions and page counters.
- The PAGE, BLOCK, FAIL and DROP address-full policies.
- Large messages: streamed chunks, compression and the `.msg` file format.
- Large-message conversion between protocols.

**Exit check**
- Backlogs of several gigabytes page correctly.
- Paging and large-message directories interoperate with Java in both directions.

**Exit check (met)**
- `scripts/paging-soak.sh` fills a paging queue with 3 GiB (314,572 messages of 10 KiB), stops the broker, starts one on the same data directory and drains the queue. Every message arrives once, in order and intact. It passes in every direction:

  | Sent on | Drained on | Pages | Saranga peak memory |
  |---|---|---|---|
  | Saranga | Saranga | 10 MiB | about 340 MiB |
  | Saranga | Saranga | 20 KiB (one message per page file, 314,572 files) | 64 MiB |
  | Artemis | Saranga | 10 MiB | 337 MiB |
  | Saranga | Artemis | 10 MiB | 358 MiB |

  Saranga's memory does not grow with the backlog: a 1 GiB run peaks at the same level as a 3 GiB one. With 10 MiB pages, the peak is the 50 MiB the address may hold in memory, plus the page being written and the decoded pages cached for the cursors.
- [tests/interop/jms/Phase5.java](tests/interop/jms/Phase5.java) has 40 tests.
  - Large messages (22): bytes and text bodies, compressed bodies, streamed bodies, non-persistent, transacted, redelivered and pre-acknowledged messages, dead-letter and expiry moves, browsing, topic fan-out, selectors, small consumer windows, conversion of oversized regular messages, divert copies, scheduled delivery, duplicate detection, the Core streaming API (`setBodyInputStream`, `setOutputStream`), and consumers closed mid-transfer.
  - Paging (18): paging and depaging, message counts, non-persistent messages, topics and durable subscriptions, transactions, consumer rollback, selectors, dead-letter and expiry moves into paging addresses, paged large messages, browsing, `max-size-messages`, the BLOCK, FAIL and DROP policies, and `page-limit-messages` with `page-full-policy`.

  Run with [tests/interop/jms/phase5.broker.xml](tests/interop/jms/phase5.broker.xml), they pass against Artemis 2.57.0 and against Saranga: `CONFIG=tests/interop/jms/phase5.broker.xml SUITE=Phase5 scripts/interop.sh saranga`.
- [tests/interop/jms/Persist.java](tests/interop/jms/Persist.java) gains three tests:
  - large messages;
  - a prepared XA branch with a large message;
  - paging: a queue consumed part-way across pages, durable subscriptions consumed unevenly, committed and rolled-back transactions, a prepared XA branch and a paged large message.

  All three pass through `scripts/persistence.sh` in every direction (Saranga to Saranga, Artemis to Saranga, Saranga to Artemis, and Artemis to Artemis), after a clean stop and after a kill.
- `scripts/cross-store.sh` passes with nothing left for later phases. Saranga recovers `core-large` and the new `persist-paging` golden scenario exactly as Artemis does.
- Every golden page file re-encodes byte for byte. `saranga data print` prints the paging section that `artemis data print` prints.
- The Phase 2, 3 and 4 suites still pass.

**Deferred on purpose:**
- Large-message conversion between protocols, to Phase 7, which brings the other protocols.
- Core frame size limits before and after authentication, to Phase 6, which brings security.
- Large messages in the Rust client; the broker side is complete.
- Paging without persistence, browsers that read through page files, and reading page files incrementally rather than whole, to Phase 11.

The behaviour differences are listed in COMPAT.md.

## Phase 6: Config and security

**Scope**
- The full `broker.xml` schema, where unknown elements produce a warning, not a failure.
- `broker.properties`, environment overrides and hot reload.
- TLS with rustls: PEM, PKCS12 and JKS keystores, SNI and mutual TLS.
- Login modules: properties file, LDAP and certificate.
- Authorization through security settings with the match hierarchy.
- Password masking.

**Exit check:** unmodified Artemis `etc/` directories from typical deployments start Saranga.

**Exit check (met)**: `scripts/etc-check.sh` makes 13 instances with the reference image's own `artemis create` and runs each with `saranga run --etc` exactly as created.
- 10 variants start, take a login and a send and receive round trip, and refuse a wrong password. The variants are: the default, anonymous, NIO with `--blocking` and pre-declared queues and addresses, mapped journal with paging and retention, no persistence, a custom role and user, web options, a replicated primary, a static cluster member and a shared-store primary.
- 3 variants refuse to start with a reason: a shared-store backup, a replicated backup and the JDBC store.
- Every warning they print names something Saranga does not do yet: protocols other than Core, clustering, HA and retention.

What else Phase 6 delivered, each suite passing against both Artemis and Saranga:
- **Security:** properties, guest, certificate and LDAP login modules, password hashes and masks, security settings with role mapping, and checks on every Core operation, including login at `CONNECT`, the pre-authentication topology and frame size limits. Covered by `Phase6.java` (23 tests) and `Ldap.java` (6 tests, against a real OpenLDAP).
- **TLS:** JKS, PKCS12 and PEM stores, mutual TLS, CRLs, SNI, protocol and cipher choices, and reloading the stores. Covered by `Tls.java` (10 tests).
- **`broker.properties`:** `-D` system properties and `brokerconfig.` overrides, including `jaasConfigs`. Covered by `Props.java` (5 tests).
- **Configuration reload:** settings swap, diverts, address and queue deployment, `updateQueue` and the `config-delete-*` policies. Covered by `Reload.java` (7 tests).
- **`saranga run --etc`** reads `bootstrap.xml`, `login.config` and `broker.properties` the way `artemis run` does.
- **`ActiveMQBasicSecurityManager`** with bootstrap users, whose user and role records move between the brokers in both directions: `scripts/basic-security.sh`.
- **`saranga mask`**: the same results as `artemis mask` for the default and keyed two-way codecs, and one-way hashes (`--hash`) for users files.
- **Acceptor address prefixes** (`anycastPrefix`, `multicastPrefix`) on every Core operation: `Prefix.java` (6 tests).
- **1.x clients:** the old `jms.queue.`/`jms.topic.` prefixes are put back on query results and delivered messages. Checked with a real Artemis 1.5.6 JMS client by `scripts/legacy-interop.sh` (`Legacy.java`, 4 tests).

The differences from Artemis are listed in COMPAT.md.

## Phase 7: Protocols

**Scope**
- AMQP 1.0: transactions, links, durable subscriptions and message conversion.
- MQTT 3.1.1 and 5: sessions, retained messages, wills, shared subscriptions, and QoS 0, 1 and 2.
- STOMP 1.0 to 1.2.
- OpenWire: advisories, virtual topics and the prefetch model.
- WebSocket transport for every protocol, and protocol detection on a single port.

**Exit check**
- The client test matrix passes for every protocol: Qpid JMS, the ActiveMQ 5 client, Paho, a STOMP client, and Python, .NET and Rust AMQP clients.
- Messages convert correctly between protocols, for example MQTT in and JMS out.

**Stages**, each committed on its own:
1. **Groundwork.** Protocol detection on one port from the first 8 bytes, as `ProtocolHandler` does, honouring each acceptor's `protocols`. A `ProtocolManager` trait that protocol crates implement and `saranga run` registers. A protocol-neutral server session (`ServerSessionImpl`) split out of the Core session, which every protocol drives.
2. **STOMP** 1.0, 1.1 and 1.2: frames, heart-beating, subscriptions and ack modes, transactions, receipts and durable subscriptions.
3. **MQTT** 3.1, 3.1.1 and 5: sessions and their persisted state, retained messages, wills, shared subscriptions, QoS 0, 1 and 2, and the MQTT 5 properties.
4. **AMQP 1.0**: the type codec, SASL, connections, sessions and links, flow control, transactions, durable subscriptions, AMQP messages kept in their own format in the journal and in pages (as `AMQPMessagePersisterV3` writes them), and conversion to and from Core.
5. **OpenWire**: the marshallers for every version, the prefetch model, advisories and virtual topics.
6. **WebSockets** for every protocol.
7. **Exit check**: the client matrix and conversion between protocols.

**Progress**
- Stage 1 (groundwork) is done. Acceptors pick each connection's protocol from its first 8 bytes. `ServerSession` holds what Core and every other protocol share. `tests/protocols.rs` in `saranga-server` covers the detection.
- Stage 2 (STOMP) is done. [tests/interop/stomp/Stomp.java](tests/interop/stomp/Stomp.java) has 76 tests ported from Artemis's `StompTest`, `StompV11Test` and `StompV12Test`. They pass against Artemis 2.57.0 and against Saranga: `CONFIG=tests/interop/stomp/broker.xml SUITE_FILE=tests/interop/stomp/Stomp.java scripts/interop.sh saranga`. They cover:
  - version negotiation, `
` line ends, and header escaping and repetition;
  - receipts, and the ERROR frames with their texts;
  - the `auto`, `client` and `client-individual` ack modes, NACK, and consumer windows;
  - transactions;
  - topics, durable and no-local subscriptions, and selectors;
  - auto-creation, routing types and the `/queue/` and `/topic/` prefixes;
  - scheduled and expired messages, heart-beats and the TTL;
  - large messages in both directions;
  - messages crossing between STOMP and JMS.
- Stage 3 (MQTT) is done. The codec follows Netty's `MqttDecoder` and `MqttEncoder` 4.1.137, which Artemis uses: the same validations, the same handling of a bad packet, and the same byte layout, including the order of MQTT 5 properties. [tests/interop/mqtt/Mqtt.java](tests/interop/mqtt/Mqtt.java) has 40 tests using Paho 1.2.5 (3.1.1 and 5), raw sockets for byte-level checks, and JMS. They pass against Artemis 2.57.0 and against Saranga: `CONFIG=tests/interop/mqtt/broker.xml SUITE_FILE=tests/interop/mqtt/Mqtt.java SUITE_CP='<artemis lib>/*;<paho mqttv3 jar>;<paho mqttv5 jar>' scripts/interop.sh saranga`. They cover:
  - QoS 0, 1 and 2 in both directions, with QoS 2 duplicates and redelivery after a reconnect using the same packet ID;
  - wildcards, and topics containing `.`;
  - retained messages;
  - persistent and clean sessions, and session-present;
  - wills on failure and on keep-alive timeout, and no will after DISCONNECT;
  - link stealing;
  - MQTT 3.1 and its client ID rules;
  - malformed packets;
  - in MQTT 5: properties, subscription identifiers, no-local, retain handling, retain-as-published, shared subscriptions, session expiry, topic aliases, the CONNACK properties, authentication methods, reason codes and Receive Maximum;
  - messages crossing between MQTT and JMS.

  `tests/mqtt.rs` in `saranga-protocol-mqtt` checks that a session and its in-flight packet IDs survive a restart. Session state is kept in `$sys.mqtt.sessions`, packet-ID correlations as journal records of type 54, and QoS 2 packet IDs in the `mqtt.qos.*` duplicate-ID caches, all as Artemis keeps them.
- Stage 4 (AMQP 1.0) is done. Its parts:
  - **The codec** picks the same encodings as Proton-J 0.35.0, which Artemis uses, including its fast-path list forms. 158 values that Proton-J encodes (`tests/golden-gen/amqp/CodecFixtures.java`) and every frame of a Qpid JMS session with Artemis decode and re-encode to the same bytes.
  - **Messages** stay in their AMQP encoding in queues, the journal and pages, as `AMQPStandardMessage` and `AMQPLargeMessage` keep them. The broker works on a view of each message and carries its changes back, re-encoding only where Artemis does. `tests/golden-gen/amqp/MessageFixtures.java` checks these against Artemis's own classes, byte for byte: records, moves to a dead-letter address, diverts, added properties, redelivery, and conversion from Core. Conversion to Core is checked by its content, since Artemis keeps Core properties in a hash map.
  - **On disk.** `tests/golden/amqp-durable` is a journal Artemis wrote through Qpid JMS, with a large message and a message moved to the dead-letter address. `saranga data print` prints it line for line as `artemis data print` does, and Saranga recovers it to what Artemis shows. `Persist.java`'s AMQP cases pass from Artemis to Saranga, from Saranga to Artemis and from Saranga to Saranga, after a clean stop and after a kill.
  - **The protocol head** follows `AMQPConnectionContext`, the link contexts, `AMQPSessionCallback` and `ProtonTransactionHandler`:
    - SASL PLAIN, ANONYMOUS and EXTERNAL;
    - container-ID uniqueness, idle timeouts and heartbeats;
    - producer credit, consumer credit and drain;
    - anonymous relay, dynamic sources and targets, and FQQN sources;
    - durable, shared and volatile subscriptions, named as Artemis names them;
    - selectors and no-local, browsing, and every outcome a client settles with;
    - transactions, including the unsettled acknowledgements that a rolled-back transaction keeps with their consumer.
  - **Interop.** [tests/interop/amqp/Amqp.java](tests/interop/amqp/Amqp.java) has 34 Qpid JMS tests. They pass against Artemis 2.57.0 and against Saranga: `CONFIG=tests/interop/amqp/broker.xml SUITE_FILE=tests/interop/amqp/Amqp.java scripts/interop.sh saranga`. They cover message types, properties and headers, queues and topics, durable and shared subscriptions, selectors, no-local, transactions, acknowledgement modes, dead letters, expiry, temporary destinations, browsing, anonymous producers, FQQN, priority, delivery delay, groups, receiveNoWait, a large message, messages crossing between AMQP and Core JMS, and the SASL and Open exchanges on a raw socket.
- Stage 5 (OpenWire) is done. Its parts:
  - **The codec** handles versions 1 to 12, tight and loose, with the marshal cache. Its command structs are generated from the ActiveMQ 5.19.10 marshallers that Artemis ships (`tests/golden-gen/openwire`). About 5,000 frames the Java marshallers wrote decode and re-encode to the same bytes.
  - **Conversion** to and from Core ports `OpenWireMessageConverter`. `tests/golden-gen/openwire/MessageFixtures.java` checks it against Artemis's converter both ways: the Core messages match exactly, property order included, and dispatches match byte for byte except compressed bodies, which match once inflated.
  - **The protocol head** follows `OpenWireConnection`, `AMQSession`, `AMQConsumer` and `OpenWireProtocolManager`:
    - wire-format negotiation, `BrokerInfo`, keep-alive pings and the inactivity TTL;
    - the pre-login gate, client ID uniqueness, and the connection's own session `-1`;
    - sync and async sends, producer windows answered with `ProducerAck`, composite destinations and failover duplicate IDs;
    - the prefetch window with its delivered-ack extension, prefetch 0 with `MessagePull`, forced-delivery markers and null dispatches;
    - every ack type, matched by message ID range, with poison acks to the dead-letter address carrying the failure cause;
    - local and XA transactions; a rollback leaves acknowledged messages with their consumers, as `returnReferences` does;
    - durable and non-durable topic subscriptions, no-local, selectors, browsers, wildcards and virtual topic consumers mapped to FQQNs;
    - temporary destinations, removed with their connection;
    - the connection and destination advisories, and the replay of temporary destinations to advisory subscribers.
  - **Interop.** [tests/interop/openwire/OpenWire.java](tests/interop/openwire/OpenWire.java) has 60 tests using the ActiveMQ 5.19.10 client, ported mostly from Artemis's `SimpleOpenWireTest` and its neighbours. They pass against Artemis 2.57.0 and against Saranga: `CONFIG=tests/interop/openwire/broker.xml SUITE_FILE=tests/interop/openwire/OpenWire.java scripts/interop.sh saranga`. They cover message types, compression and encodings, every acknowledgement mode, redelivery and the dead-letter queue, transactions and XA (two-phase commit, recovery, rollback), producer windows, async sends, queues and topics, durable subscriptions, no-local, selectors, browsing, prefetch 0 and 1, groups, composite destinations, wildcards, virtual topics, scheduled and expired messages, temporary destinations, missing destinations, auto-deletion, advisories, keep-alive, duplicate client IDs and messages crossing between OpenWire and Core JMS.
- Stage 6 (WebSockets) is done. An acceptor answers an HTTP request whose first bytes it reads with the WebSocket handshake, as `ProtocolHandler` and Netty's `WebSocketServerHandshaker13` do, offering the subprotocols of its protocols (`v10.stomp`, `v11.stomp`, `v12.stomp`, `mqtt`, `mqttv3.1`, `amqp`). It then detects the protocol again inside the WebSocket. Text, binary and continuation frames carry the stream, pings are answered and a close is echoed. What the broker writes goes out in binary (or, with `webSocketEncoderType=text`, text) frames of at most `webSocketMaxFramePayloadLength` bytes, and a larger frame from the client closes the connection with 1009. [tests/interop/websocket/WebSocket.java](tests/interop/websocket/WebSocket.java) has 19 tests. They pass against Artemis 2.57.0 and against Saranga: `CONFIG=tests/interop/websocket/broker.xml SUITE_FILE=tests/interop/websocket/WebSocket.java SUITE_CP='<artemis lib>/*;<paho mqttv3 jar>' scripts/interop.sh saranga`. They cover the handshake and subprotocol choice, refused requests, fragmentation both ways, control frames, STOMP through the JDK's WebSocket client and a raw socket, MQTT through Paho (`ws://`), AMQP through Qpid JMS (`amqpws://`), the OpenWire handshake, and messages crossing to Core JMS.
- Stage 7 (the exit check) is done, and with it Phase 7. Every client in the matrix passes against Artemis 2.57.0 and against Saranga:
  - **Java clients**, in the suites of the stages above: the Artemis JMS client (Core), Qpid JMS (AMQP), the ActiveMQ 5 client (OpenWire), Paho 3.1.1 and 5 (MQTT), and STOMP over raw sockets. The same suites cover WebSockets.
  - **Python, .NET and Rust AMQP clients**: Qpid Proton's Python binding (`python-qpid-proton` 0.40.0), AMQPNetLite 2.5.4 and fe2o3-amqp 0.18.2. Each runs the same checks from [tests/interop/clients](tests/interop/clients): header fields and application properties, a modified or released delivery coming back, rejection, a 600 KB body, and a map body. `scripts/client-matrix.sh saranga` fetches and builds them outside the repository and runs them.
  - **Conversion between protocols.** [tests/interop/conversion/Conversion.java](tests/interop/conversion/Conversion.java) sends from each of Core JMS, Qpid JMS, the ActiveMQ 5 client, STOMP and MQTT 5 to each of them: 25 pairs. It checks the body, a string property, and whether a JMS receiver gets text or bytes. MQTT user properties reach only MQTT receivers, as in Artemis. Run it with `CONFIG=tests/interop/conversion/broker.xml SUITE_FILE=tests/interop/conversion/Conversion.java SUITE_CP='<artemis lib>/*;<paho mqttv5 jar>' scripts/interop.sh saranga`.

## Phase 8: Management and operations

**Scope**
- A REST API covering the operations of the `ActiveMQServerControl`, `AddressControl` and `QueueControl` equivalents.
- Prometheus metrics with the same metric names Artemis exposes.

## Phase 9: High availability

**Scope**
- Shared-store primary/backup using file locks on the journal directory, including NFS lock semantics.
- Replication: initial sync and live journal replication over the Core replication packets, wire-compatible with a Java peer.
- Failback.
- Client failover and reconnection.
- Pluggable quorum through ZooKeeper.

**Exit check**
- Failover tests lose no committed messages.
- A Java primary works with a Saranga backup, and a Saranga primary works with a Java backup.

**Stages**, each committed on its own:
1. **Shared store.** `FileLockNodeManager` in full: the state byte of `server.lock` and the locks on it, `serverlock.1` (primary) and `serverlock.2` (backup), taken as Java takes them (`fcntl` record locks on Unix, `LockFileEx` on Windows), so that a Java broker and a Saranga broker exclude each other on one journal directory; `journal-lock-acquisition-timeout` and the lock monitor. `<ha-policy><shared-store>` with its `primary` and `backup` options: a backup waits for the backup lock, then for the primary to fail, and becomes active on its data; `failover-on-shutdown`.
2. **Topology, failback and client failover.** The cluster connection a backup uses to announce itself to its primary (`ClusterConnect`, `NodeAnnounce`), so that the topology clients receive pairs each primary with its backup; shared-store failback (`allow-failback`, `restart-backup`: the active backup hears the restarted primary through the cluster connection and gives way), and `artemis create --shared-store`, which makes a clustered instance; `DisconnectMessage` on shutdown; and in `saranga-client`, reconnection and failover to the backup (`reconnectAttempts`, `retryInterval`, `ha=true`, the URL list), with the Artemis JMS client failing over to a Saranga backup.
3. **Replication.** A backup registers with its primary (`BackupRegistrationMessage`), receives the journals, paging and large messages in the initial synchronization (`ReplicationStartSyncMessage`, `ReplicationSyncFileMessage`), then every journal append, page write and large message as it happens, each acknowledged before the primary's client is answered. The backup becomes active when the primary fails, after a quorum vote among the cluster's primaries (`vote-on-replication-failure`, `quorum-size`), and the primary stops when it loses the vote (`QuorumVoteMessage`).
4. **Replication failback** (`check-for-active-server`, `allow-failback`, `max-saved-replicated-journals-size`): a restarted primary synchronizes from the active backup and takes over again.
5. **Pluggable quorum** with ZooKeeper (`<replication><primary><manager>`), activation sequences and the coordination Artemis's `CuratorDistributedPrimitiveManager` does.
6. **Exit check:** failover tests that lose no committed messages, with Saranga and Java brokers in each role.

**Progress**
- Stage 1 (shared store) is done. `server.lock`'s states and the locks on `server.lock`, `serverlock.1` and `serverlock.2` are taken as Java takes them, so Java and Saranga brokers exclude each other ([crates/saranga-server/src/filelock.rs](crates/saranga-server/src/filelock.rs), [crates/saranga-server/src/node.rs](crates/saranga-server/src/node.rs)). `<ha-policy><shared-store>` is parsed with its options, and `journal-lock-acquisition-timeout`, `journal-lock-monitor-timeout`, `journal-lock-monitor-max-retries` and `node-manager-lock-directory` are honoured. A primary waits for the lock, a backup for its primary to fail, and an active broker whose lock another takes stops. [tests/interop/ha/shared-store.sh](tests/interop/ha/shared-store.sh) runs a primary and a backup on one journal directory through their instances' `bin/artemis`: a crash failover, a primary waiting for the active backup, failover on shutdown, and a backup kept waiting by paused data. Its output is recorded with Artemis in both roles and compared with Saranga in both, and with each of Artemis and Saranga as the other's backup.
- Stage 2 (topology, failback and client failover) is done. A shared-store backup connects to its primary through its cluster connection's static connectors (`ClusterConnect` with the cluster user, then `NodeAnnounce`), and the primary pairs it with itself in the topology it sends clients ([crates/saranga-server/src/cluster.rs](crates/saranga-server/src/cluster.rs)); a restarted primary announces itself to the active backup the same way, and the backup gives way (`allow-failback`) and waits as a backup again (`restart-backup`). Node IDs are made and read as Artemis makes them (time-based, version and variant bits forced), so a Java and a Saranga broker on one journal directory agree on theirs. A broker stopped while it waits for a lock logs `AMQ221002`, and connected clients get a `DisconnectMessage` when it stops. `saranga create` takes `--clustered`, `--static-cluster`, `--shared-store`, `--backup` and `--failover-on-shutdown`. In `saranga-client`, a `Connection` is now a session factory with its locator ([crates/saranga-client/src/connection.rs](crates/saranga-client/src/connection.rs)): it connects to the first of a list of servers that answers, keeps the topology, and with `reconnectAttempts` or `failoverAttempts` connects again to its server or the backup the topology paired with it, then to the other servers, recreating its sessions under new names with their consumers; a transaction that had work in it can then only roll back (`TRANSACTION_ROLLED_BACK`, `TRANSACTION_OUTCOME_UNKNOWN`). The CLI's messaging commands take the URL list and the locator's parameters. [crates/saranga-client/tests/failover.rs](crates/saranga-client/tests/failover.rs) restarts an in-process broker under a reconnecting client. [tests/interop/ha/failback.sh](tests/interop/ha/failback.sh) runs instances made with `create --shared-store --static-cluster` through their own `bin/artemis`: the topology a client receives, a crash failover and a failback of the Artemis JMS client, and a consumer of the primary's own CLI failing over to the backup, in all four Artemis/Saranga pairings against the output recorded with Artemis in both roles.
- Stage 3 (replication) is done. A backup with `<ha-policy><replication><backup>` moves its old data aside, finds its primary through its cluster connection, authorizes as the cluster user and registers (`BackupRegistrationMessage`); the primary copies its journals, page files and large messages to it in Artemis's order (`ReplicationStartSyncMessage`, `ReplicationSyncFileMessage`), each journal moving to a new file first, and replicates every append, page write and large-message write from then on ([crates/saranga-server/src/replication/](crates/saranga-server/src/replication/)). The journal hands each record to a replicator under its lock ([crates/saranga-journal/src/journal.rs](crates/saranga-journal/src/journal.rs)), and the backup writes the copied files and what arrives meanwhile with `SyncJournal` ([crates/saranga-journal/src/sync.rs](crates/saranga-journal/src/sync.rs)), loading them once synchronized with transactions left open. Every packet gets one response in order, and a client is answered once the backup has answered for its writes. A backup that loses its primary holds a quorum vote among the other primaries (`QuorumVoteMessage`, which Saranga also answers) and becomes active on its copy with the primary's node ID; a primary that loses its backup votes with `vote-on-replication-failure` and stops if it loses. `saranga create --replicated` writes Artemis's replication settings. [crates/saranga-client/tests/replication.rs](crates/saranga-client/tests/replication.rs) runs a primary and backup in process; [tests/interop/ha/replication.sh](tests/interop/ha/replication.sh) runs instances made with `create --replicated --static-cluster` with data from before and after the backup, large messages, a crash failover of the Artemis JMS client and the CLI consuming the rest from the backup, in all four Artemis/Saranga pairings against the output recorded with Artemis in both roles.
- Stage 4 (replication failback) is done. A primary with `check-for-active-server` first asks its cluster connection's brokers whether one is active with its node ID, opening a session there as the cluster user (`isNodeIdUsed`); if one is, it moves its data aside and replicates that broker as a backup asking for failback ([crates/saranga-server/src/replication/backup.rs](crates/saranga-server/src/replication/backup.rs)). The active broker, if it allows failback (a backup's `allow-failback`, or a primary, which always does), waits for the new backup to announce itself, tells it to take over (`STOP_CALLED`, then `FAIL_OVER` as it stops, the backup's connection left open while the clients are disconnected), stops and replicates it again as its backup, logging `AMQ221039` ([crates/saranga-server/src/replication/primary.rs](crates/saranga-server/src/replication/primary.rs)); otherwise the restarted primary logs `AMQ224056` and stays its backup. [crates/saranga-client/tests/replication.rs](crates/saranga-client/tests/replication.rs) runs a failback in process; [tests/interop/ha/replication.sh](tests/interop/ha/replication.sh) goes on after the failover with messages consumed and produced on the active backup, restarts the primary, which takes its node back with the backup's data while the Artemis JMS client fails back, and consumes the rest there, in all four Artemis/Saranga pairings.

## Phase 10: Clustering and federation

**Scope**
- Discovery by UDP broadcast and static lists. JGroups is supported only as far as UDP compatibility needs; full JGroups is not planned.
- Cluster connections and topology broadcast to clients.
- Server-side load balancing: OFF, STRICT, ON_DEMAND and OFF_WITH_REDISTRIBUTION.
- Redistribution and grouping handlers.
- Core bridges.
- Federation of addresses and queues, upstream and downstream.
- AMQP broker connections, including mirroring.

**Exit check**
- Mixed clusters of Java and Saranga nodes work.
- Federation and mirroring work in both directions.

**Stages**, each committed on its own:
1. **Discovery.** Broadcast groups (`<broadcast-groups>`: the node ID, a unique ID and the connectors, encoded as `BroadcastGroupImpl` encodes them, sent to a UDP multicast group every `broadcast-period`) and discovery groups (`<discovery-groups>`: `refresh-timeout`, `initial-wait-timeout`). A broker's cluster connection finds the others through its `discovery-group-ref`, so a backup finds its primary by discovery. saranga-client and the CLI take `udp://` URLs. Artemis 2.57's switch applies (`artemis.discovery.enabled` or `ARTEMIS_DISCOVERY_ENABLED`; `AMQ229262`, `AMQ229263`, `AMQ219070`), and `create --discovery-enabled` makes instances that use discovery. JGroups configurations (`jgroups-file`, `jgroups-channel`) are refused. Broadcast groups have their management controls and notifications.
2. **Core bridges.** `<bridges>`: a bridge consumes a local queue and sends to an address on another broker (`static-connectors` or `discovery-group-ref`), with its `filter`, `forwarding-address`, `routing-type`, `ha`, reconnection settings, `confirmation-window-size`, `producer-window-size`, `use-duplicate-detection` (`_AMQ_BRIDGE_DUP`) and `concurrency`. `BridgeControl`, `deployBridge` and `destroyBridge` work, with the configurations persisted.
3. **Cluster connections.** Each node bridges to every other primary in the topology, through a store-and-forward queue (`$.artemis.internal.sf.<cluster>.<node ID>`) and a notification consumer that learns the other node's bindings and consumers (`BINDING_ADDED`, `BINDING_REMOVED`, `CONSUMER_CREATED`, `CONSUMER_CLOSED`, `_AMQ_Distance` against `max-hops`). Remote queue bindings join the post office, and messages are routed among local and remote bindings by `message-load-balancing` (`OFF`, `STRICT`, `ON_DEMAND`, `OFF_WITH_REDISTRIBUTION`), with the IDs the remote broker routes by (`_AMQ_ROUTE_TO`). The cluster's topology goes to clients, and saranga-client balances its connections across it.
4. **Redistribution and grouping.** `redistribution-delay` and the redistributor, which moves messages to a node with consumers when a queue has none. `<grouping-handler>` `LOCAL` and `REMOTE`: proposals and responses as notifications, `timeout`, `group-timeout` and `reaper-period`, and groupings persisted in the bindings journal.
5. **Core federation.** `<federations>`: upstreams and downstreams with their connection settings; address policies (include and exclude, `max-hops`, `auto-delete`, `enable-divert-bindings`) and queue policies (`include-federated`, `priority-adjustment`); federated consumers on the remote broker, and a downstream's `FederationDownstreamConnectMessage`.
6. **AMQP broker connections.** `<broker-connections><amqp-connection>`: Saranga connects out as an AMQP client (SASL, reconnection), with `sender`, `receiver` and `peer` elements, and `BrokerConnectionControl`.
7. **AMQP federation.** `<federation>` with local and remote address and queue policies, its control link and events, on both the source and the target.
8. **AMQP bridges.** `<bridge>` with its from and to address and queue policies.
9. **Mirroring.** `<mirror>`: the source sends its messages, acknowledgements and address and queue events on the mirror link, and the target applies them (the `AckManager`, message IDs kept). Dual mirroring runs without loops, and `sync` waits for the target.
10. **Exit check:** mixed clusters of Java and Saranga nodes (load balancing, redistribution, grouping), core and AMQP federation, and mirroring, each in both directions.

For each queue an element matches (by `queue-name`, or its address by `address-match`), now and when created later, a `sender` attaches a link sending the queue's messages to its address on the peer, a `receiver` a link taking the peer's messages to the queue's address with its routing type, and a `peer` both, with `qd.waypoint`. A link the peer refuses (`AMQ119023`, `AMQ119029`) or closes (`AMQ119021`) makes the connection again.

- Stage 7 (AMQP federation) is done.
  - **Policies and messages** ([crates/saranga-protocol-amqp/src/federation/policy.rs](crates/saranga-protocol-amqp/src/federation/policy.rs)): `FederationReceiveFromAddressPolicy` and `FederationReceiveFromQueuePolicy` with their matching (multicast addresses only; includes and excludes anchored at the end, as `Pattern.asPredicate` is), and the control and event messages of `AMQPFederationPolicySupport` and `AMQPFederationEventSupport`, encoded and decoded as Artemis does them (`x-opt-amq-federation-op-type`, `x-opt-amq-federation-ev-type`, an `amqp-value` map). Once the events sender's outcome is known the remote policies go to the peer, routed through the control link's temporary queue; once the events receiver's is known the local policies start. A refused control link (`AMQ119025`) or a missing capability (`AMQ119018`) makes the connection again.
  - **The target** ([crates/saranga-protocol-amqp/src/connection.rs](crates/saranga-protocol-amqp/src/connection.rs)): a peer's link desiring `AMQ_FEDERATION_CONTROL_LINK` (after a `SEND` check on `$ACTIVEMQ_ARTEMIS_FEDERATION`) makes this end its target, with the configuration it sent; the policies on the control link become its local policies, attaching receivers back over the same connection. It goes with its connection, and a link closed unexpectedly closes the connection.
  - **Local policies** ([crates/saranga-protocol-amqp/src/federation/manager.rs](crates/saranga-protocol-amqp/src/federation/manager.rs)) are broker plugins, as `AMQPFederationAddressPolicyManager` and `AMQPFederationQueuePolicyManager` are. Demand on an address is a queue bound to it, other than the peer's own federation binding (`federation.<fed>.policy.<policy>.address.<address>.node.<peer>`); demand on a queue is a consumer of it, other than a federation's own unless `include-federated`, at its priority adjusted (or the default's, with `ignoreQueueConsumerPriorities`) and with its filter. `AMQPFederationConsumerManager`'s state machine is kept: a receiver is attached on the first demand, stopped by draining its credit when the last goes (`receiverQuiesceTimeout`), started again if demand comes back, and closed after `addressReceiverIdleTimeout` or `queueReceiverIdleTimeout`; an unanswered attach fails the connection after `attach-timeout` (`AMQ119020`). Receivers have Artemis's names, terminus, filters (no-local and the hops filter), properties and capabilities, FQQN subscriptions with a version 2 peer; an address receiver adds a hop (`x-opt-amq-fed-hops`) to each message.
  - **Senders for the peer's receivers**: `AMQPFederationAddressSenderController` (the federation binding, made with the receiver's auto-delete settings and filters, and removed when the peer closes the link) and `AMQPFederationQueueSenderController` (the queue, with the receiver's filter and priority). A missing address or queue (`AMQ119010`, `not-found`), or one deleted while attached, is watched for, and the events link tells the peer when it is added, which then attaches again.

- Stage 8 (AMQP bridges) is done.
  - **Policies and settings** ([crates/saranga-protocol-amqp/src/bridge/policy.rs](crates/saranga-protocol-amqp/src/bridge/policy.rs), [config.rs](crates/saranga-protocol-amqp/src/bridge/config.rs)): `AMQPBridgeAddressPolicy` and `AMQPBridgeQueuePolicy` as `AMQPBridgeSupport` makes them (multicast addresses only, the remote address with its prefix and suffix, terminus capabilities), and `AMQPBridgeConfiguration` with the per-policy receiver and sender settings over it, with Artemis's defaults (`AMQPBridgeConstants`).
  - **The bridge** ([crates/saranga-protocol-amqp/src/bridge/mod.rs](crates/saranga-protocol-amqp/src/bridge/mod.rs)): each `<bridge>` of a broker connection is an `AMQPBridgeManager`, started and stopped with the connection after its federation; the connection desires `SHARED-SUBS`, and the bridge's policies take each connection once the peer's Open is in, knowing whether it offers it. Links the peer closes are attached again after `linkRecoveryInitialDelay`, then `linkRecoveryDelay`, up to `maxLinkRecoveryAttempts`; an unanswered attach fails the connection after `attach-timeout` (`AMQ119020`), and a remote close for not-found, resource-deleted or detach-forced does not.

Receivers have Artemis's link names (durable, shared durable with `|` and the sequence, or unique), sources (durable subscriptions with the `copy` distribution mode and the `shared` capability), filters (the policy's, else the consumer's, else the queue's), priorities and settle modes, and route into the local address or the queue's FQQN.
  - **To policies** ([to.rs](crates/saranga-protocol-amqp/src/bridge/to.rs)): a sender for each matching address, consuming a temporary subscription (removed with the link) or a durable one of its own, and for each matching queue, at the policy's priority and with its filter, for as long as the address or queue exists (`AMQPBridgeSenderManager`).

  - **Tests.** In-process tests in [crates/saranga-protocol-amqp/tests/bridge.rs](crates/saranga-protocol-amqp/tests/bridge.rs) (each policy kind, and a refused receiver recovered once the queue is made). [tests/interop/cluster/amqp-bridge.sh](tests/interop/cluster/amqp-bridge.sh) makes two instances, node 1 bridging to node 2 with all four policy kinds: messages each way, a queue node 2 lacks taken once made there (link recovery), and the bridge again after node 2 restarts. It passes in all four Artemis/Saranga pairings.
- Stage 9 (mirroring) is done.
  - **The broker's hooks** ([crates/saranga-server/src/mirror.rs](crates/saranga-server/src/mirror.rs)): mirror sources are told of what is routed (in `page_routed`, as `processRoute` tells them), of each reference leaving a queue (as `preAcknowledge` and `postAcknowledge`; not a replaced last value), and of addresses and queues added and removed. A mirror target applying its peer's event is the target in use, which a source does not send back to; an expired message's copy is not mirrored. With `sync`, what a client sends, acknowledges or commits is answered once the peer has it, after the queue updates.
  - **The source** ([crates/saranga-protocol-amqp/src/mirror/source.rs](crates/saranga-protocol-amqp/src/mirror/source.rs)): `installMirrorController` makes the internal store-and-forward queue `$ACTIVEMQ_ARTEMIS_MIRROR_<connection>`, paging (blocking with `sync`) whatever its settings say, sends every address and queue there is (`scanAddresses`), and from then on takes a reference to each routed message (a copy with `x-opt-amq-mr-id` when it pages) and a control message (`AMQPMirrorMessageFactory`) for each acknowledgement and each address and queue change, within `queue-creation`, `queue-removal`, `message-acknowledgements` and `address-filter`. The mirror link sends the queue with each message's delivery annotations (`x-opt-amq-bkr-id`, `x-opt-amq-mr-id`, `x-opt-amq-mr-dst`), desiring `amq.mirror` and naming this broker; a peer that does not offer it, does not name itself or is this broker fails the connection (`AMQ119018`, `AMQ119019`, `AMQ119022`).
  - **The target** ([target.rs](crates/saranga-protocol-amqp/src/mirror/target.rs)): a link to `$ACTIVEMQ_ARTEMIS_MIRROR...` that may send there and desires `amq.mirror` (`AMQ119017`, `AMQ119024`) is answered with `amq.mirror` and this broker's ID. Control messages add and remove addresses and queues; other messages are routed locally without diverts (or to `x-opt-amq-mr-trg-q`'s queues), in a transaction with the mirror's duplicate cache, keeping their broker and ID as broker properties. Acknowledgements go to the broker's `AckManager`, which finds the message by its broker and ID and acknowledges or expires it, retrying those not found every `mirror-ack-manager-retry-delay`, in pages after `mirror-ack-manager-queue-attempts`, giving up after `mirror-ack-manager-page-attempts`, journaled as `ACK_RETRY` records and reloaded at startup.
  - **Tests.** In-process tests in [crates/saranga-protocol-amqp/tests/mirror.rs](crates/saranga-protocol-amqp/tests/mirror.rs) (queues, messages, acknowledgements and deletion mirrored; dual mirrors without loops; `sync`). [tests/interop/cluster/amqp-mirror.sh](tests/interop/cluster/amqp-mirror.sh) makes two instances mirroring each other: a queue made on one is on both, messages sent to either are on both once, consumed ones leave both, a subscription made on node 2 takes what is published on node 1 on both, what node 1 is sent while node 2 is down reaches it when it is back, and a queue deleted on node 2 goes from node 1. It passes in all four Artemis/Saranga pairings.

## Phase 11: Hardening and 1.0

**Scope**
- Soak and chaos testing: network partitions, full disks and injected fsync failures.
- Jepsen-style linearizability checks on HA.
- Fuzzing every codec with cargo-fuzz.
- Benchmarks against Artemis: throughput, p99 latency, memory and startup time.
- Documentation, a migration guide, container images and the release.

**Exit check:** Saranga 1.0 ships.

**Stages**, each committed on its own:
1. **Storage faults.** A fault-injecting layer under every file the broker writes (the journal, paging, large messages, the server lock and the node ID), switched on only in tests. A failed write or fsync is a critical I/O error, as `IOCriticalErrorListener` makes it in Artemis: AMQ222010, the broker stops, and clients get an error in place of a response. A full disk blocks producers as `max-disk-usage` says. Tests: in-process failures at each write and sync, and a soak on a small real file system. None of them may lose a message a client was told is stored, and the broker must restart cleanly.
2. **Network chaos.** A TCP fault proxy (`tools/saranga-chaos`) that delays, drops, cuts and black-holes connections on a schedule. Soak scripts run HA pairs, clusters, bridges, federation and mirroring through it for a set time, with Java and Saranga nodes, and check that nothing is lost and nothing is duplicated beyond what each feature allows.
3. **Linearizability on HA.** Jepsen-style histories: clients record each send, receive and acknowledgement with its outcome while the chaos proxy partitions the pair and kills nodes. A checker then compares each history with the queue model. Acknowledged sends are received, and nothing is received twice unless the client was told the outcome was unknown. Replication and shared-store pairs both run, with Saranga and Java on each side.
4. **Fuzzing.** cargo-fuzz targets for every codec: buffers and `TypedProperties`, `CoreMessage`, Core packets, journal records and files, page files, AMQP, MQTT, STOMP, OpenWire, WebSocket frames, filters and `broker.xml`. Each target is seeded from the golden corpus. Every crash found is fixed and kept as a regression test, and CI runs each target for a short time.
5. **Benchmarks.** `scripts/bench.sh` runs Artemis and Saranga on the same machine and the same scenarios: Core and AMQP, persistent and not, small and large messages, and many queues. It measures throughput, p99 latency, memory and startup time, and its results are written to `docs/benchmarks.md`.
6. **The web console.** Artemis's own console (`web/console.war`, hawtio 4.7.0 with the Artemis plugin) served as Artemis serves it: its pages from the `.war`, with the `<base href>` set and the console's client routes answered with `index.html`, and the hawtio endpoints behind them (the login form and its session, logout, `/user`, `/refresh`, the auth configuration, `/keycloak/enabled`, `/proxy/enabled` and `/plugin`), with Jolokia taking the session as well as Basic authentication. Tests: each endpoint's answers compared with Artemis's, and a browser that logs in and opens the console's pages on both brokers.
7. **Documentation.** The user guide (installing, configuring, the CLI, protocols, security, HA, clustering, management and operations) and a migration guide from Artemis (data directories, `broker.xml`, clients, what differs), checked against COMPAT.md.
8. **Container images and the release.** A container image laid out as Artemis's, binaries for Linux, Windows and macOS, a release workflow, the version set to 1.0.0, and a changelog.
9. **Exit check:** every stage's tests and the full interop matrix pass, and Saranga 1.0.0 is tagged and released.

**Progress**
- Stage 1 (storage faults) is done.
  - **Fault injection** ([crates/saranga-fault](crates/saranga-fault)): every file operation of the journals (data files, the compaction control file), page files, large message files and `server.lock` asks the crate first. A test arms a fault for the files under its own directory: an open, write, sync, rename or removal fails with `EIO` or `ENOSPC`, after so many successes, so many times, and a write can be torn after part of its bytes. Without the `inject` feature, which only tests turn on, the checks compile to nothing.
  - **Critical I/O errors**, as Artemis's `IOCriticalErrorListener` handles them. The journal's first I/O error, in its flusher or in its own file handling, latches: no write is accepted after it, and it is reported once (AMQ144011, or AMQ144010 without a file). Page and large message files report theirs the same way. The broker logs AMQ222010 and stops as `stopTheServer(true)` stops it. The client waiting on the write gets an `IO_ERROR` exception, the stop goes on whatever the failing disk refuses, and `saranga run` exits with status 1 (COMPAT.md).
  - **Tests.** [crates/saranga-journal/tests/faults.rs](crates/saranga-journal/tests/faults.rs) fails a sync, fills the disk, tears a write and fails a new file: the journal reports once, refuses later writes, and reloads with every record whose append was answered, without the torn one. [crates/saranga-client/tests/storage_faults.rs](crates/saranga-client/tests/storage_faults.rs) puts a client in front of an in-process broker and fails the journal (sync, full disk, torn write, a file it cannot make), a page write and sync, a large message write, a transaction's commit and an acknowledgement commit. In each case the client gets an error rather than waiting, the broker asks to stop, and a broker started on the same data has every message whose send or commit was answered, once and in order, and a failed transaction all or nothing. A `server.lock` that cannot be written stops the start, and every stopped broker must be freed with its storage.
  - **The full-disk soak** ([scripts/disk-soak.sh](scripts/disk-soak.sh), [disk_soak.rs](crates/saranga-client/tests/disk_soak.rs), in CI): producers of small, paged and large messages fill a 64 MiB tmpfs, cycle after cycle. In odd cycles `max-disk-usage` holds them back, and in even cycles the disk runs out: `ENOSPC`, a critical stop, and a restart that keeps every answered send. After each cycle no file is left open and the space is back.
  - **Fixed along the way.** The soak found that a stopped broker was never freed. Each queue's actor held its queue, its paging store and the storage, so a broker stopped in-process (as the network check and failback stop one) kept its queues, its pages and the bindings journal open. The actors now end with the broker, leaving their messages as stored. The lock monitor holds the node manager weakly, so `server.lock` closes with the broker rather than at its next check, and both journals are closed even when the first fails to stop.
  - **Fixed in the suites.** The failback suite with an Artemis backup failed about one run in six, `backup: stopped` missing. The backup does stop, but Artemis's `Run` stops the broker from its daemon `STOP_ME` timer thread. The broker shuts its own non-daemon threads down before it logs AMQ221002, so the JVM can begin exiting by itself, and the shutdown hooks (log4j's closing the appenders) race the end of the stop: the line is lost from the log file, or from both log and console, and "Server stopped!" is never printed. A backup restarted by failback has the fewest such threads and stops fastest, so it is the one that loses the race. A non-daemon thread kept alive with an agent made every stop go through the timer (15 runs of 15). The failback and discovery suites now wait for the `artemis run` process to end rather than for the log line. `KEEP=1` on the failback suite keeps its work directory.
- Stage 2 (network chaos) is done.
  - **The proxy** ([tools/saranga-chaos](tools/saranga-chaos)) forwards named routes (`name=listen,target`), each in one mode at a time:

    - `delay MS [JITTER]`, which holds each chunk and keeps their order;
    - `blackhole`, a partition: nothing passes, nothing is closed, new connections are held, and what was held goes on when it heals;

    `cut` resets a route's open connections once. Commands come from a control port (`saranga-chaos ctl ADDR COMMAND`), a schedule file (`TIME COMMAND`) or the random chaos, which applies a fault to a route at random every `--every`, holds it for `--hold` and heals it, from a logged seed. Every command applied is logged. Its tests put it in front of an echo server and check each mode, the control port, a schedule and the random chaos.

- Stage 3 (linearizability on HA) is done.
  - **Histories.** [History.java](tests/interop/chaos/History.java) runs three producer and three consumer processes with the Artemis JMS client, each operation one message in its own transaction. Each completed operation is written to the history as `PROCESS TYPE F VALUE INVOKE COMPLETE`, with times in microseconds from one clock. The type is:
    - `ok` when the commit returned;
    - `fail` when the transaction was rolled back, or the send failed before the commit;
    - `info` when the commit failed otherwise and the outcome is unknown. As in Jepsen, the process is then replaced by a new one.
  - **The checker** (`saranga-chaos check HISTORY`, [history.rs](tools/saranga-chaos/src/history.rs)) compares a history with the model of a queue. It reports:
    - a lost value, enqueued `ok` and never dequeued;
    - a duplicated value, dequeued `ok` twice (`ok` and `info` is allowed);
    - an unexpected value, dequeued but never enqueued, or enqueued `fail`;
    - an early value, dequeued before its enqueue began;
    - a malformed history: overlapping operations in one process, an operation after an `info`, or a value enqueued twice.

    It exits 1 unless the history is valid.
  - **The runs** ([scripts/linearizability.sh](scripts/linearizability.sh)) pair a primary and a backup made by `artemis create`, with the clients going through the proxy. The proxy's random faults run throughout. Meanwhile a nemesis kills the primary in odd rounds (the backup becomes active, and the primary is started again and takes its node back) and the backup in even rounds (it is started again and rejoins). A supervisor starts again any broker that stops by itself, as one that loses its lock or its quorum does. Then the proxy heals, the pair must become whole, the producers stop and the consumers drain the queue, and the history must be valid. The pairs are:
    - shared store, with the cluster connections also through the proxy;
    - replication with the quorum vote, `check-for-active-server` and `allow-failback`, under delays only (see below);
    - replication with the ZooKeeper lock manager, with replication and each broker's ZooKeeper session also through the proxy, so the pair is partitioned from each other and from ZooKeeper.

    `scripts/linearizability.sh all` runs the three pairs in the four Artemis/Saranga pairings. All 12 runs pass, each with four kills under faults. The runs complete 1,100 to 15,000 sends, with 6 to 16 outcomes unknown, and every history is valid. CI runs three mixed pairings.
  - **The proxy** now makes a dead node look dead. When a route's target refuses a connection, or ends one before its client has, the route checks the target. While the target refuses, the route stops listening, so clients are refused rather than accepted and then reset. Accept-then-reset stalled the Artemis client's failover for its 30 s call timeout: it holds `connectionLock` while CONNECT's blocking call runs, and a reset during that handshake is noticed only when the call times out.
  - **Split brain in a lone vote-replication pair.** The backup of a pair with no other primaries decides with a cluster size of 1. It needs no votes ("AMQ221083: ignoring quorum vote as max cluster size is 1"), so any break of its replication connection makes it active beside a live primary, in Artemis as in Saranga. Replication follows the connector the primary announces, so it cannot be kept off the proxy while the clients go through it. A run with partitions found 3 duplicated and 2 lost values with Saranga on both sides. The vote-replication pair therefore gets delays only, and partitions are tested on the pluggable pair, which is Artemis's answer to this. Stage 2's replicated soak gets delays only for the same reason.
  - **Seen once in Artemis, not yet diagnosed.** In one failing run, an Artemis backup that was active and failing back to a Saranga primary hung in `JournalStorageManager.internalStop`, waiting for the storage write lock. `stopReplication` and the readers waited too, and no thread showed as holding the read lock: perhaps a read lock leaked on an exception path. It has not been seen since and is not drafted as an issue.

  - **Targets.** Each target's body is a plain function in [crates/saranga-fuzz](crates/saranga-fuzz), so the workspace builds and tests it on stable. The cargo-fuzz crate [fuzz](fuzz), outside the workspace, wraps each one in a line. There are 15 targets:

    - `amqp_frame`, `amqp_value` and `amqp_message`: frames, the type system with performatives and SASL frames, and messages scanned and re-encoded;
    - `mqtt`, `stomp` and `openwire`: each version (OpenWire also with tight encoding, the marshal cache, stack traces and no size prefix);
    - `websocket`: the HTTP upgrade and handshake, and frames as a binary or text stream;
    - `filter`: parsed, converted from ActiveMQ syntax, and matched;
    - `config`: `broker.xml`, `bootstrap.xml`, acceptor URIs and properties files.

    Each target decodes its input and, where it decodes, encodes it, decodes that again and checks that the second encoding equals the first. Anything other than an error from the decoder is a bug.
  - **Seeds.** `fuzz-seeds` writes 4,602 seeds from the golden corpus: Core and AMQP wire frames and the messages and properties they carry, the packet fixtures, OpenWire frames of every version, the journal, bindings and page files of the data directories, and the broker configurations. MQTT, STOMP, WebSocket, filter and JSON seeds are written by hand. A seed is at most 32 KiB, and an OpenWire run with the cache on at most 8 KiB, since bigger ones slowed their targets to a few executions a second.
  - **Found and fixed.**
    - A Core message's end-of-body position below 13 overflowed an `i32` (also from `data print`).
    - An AMQP descriptor that was itself described recursed without bound and overflowed the stack. Values are now at most 100 deep, and a described descriptor is an error.
    - An AMQP array with a zero-width element type (null, true, false, uint0, ulong0, list0) could claim four billion elements in a few bytes, and the decoder pushed them until memory ran out. As in proton-j, whose zero-width element limit is 0, such an array must be empty, and no array may count more elements than it has bytes.
    - A JSON number beyond a double's range became an infinity that could not be written back. It is now an error (COMPAT.md).
    - A harness bug: an AMQP empty frame with an extended header was re-encoded without it.

    Each input is kept in [fuzz/regressions](fuzz/regressions), and [regressions.rs](crates/saranga-fuzz/tests/regressions.rs) runs them with the workspace's tests. `SARANGA_FUZZ_DIR` runs a whole corpus the same way.
  - **Running.** [scripts/fuzz.sh](scripts/fuzz.sh) writes the seeds, builds the targets with nightly and runs each for a set time (`JOBS` at once), failing if any finds a crash. Three rounds of 120 s each ran in all; the last found nothing in any target. A CI job runs each target for 60 s and keeps what it finds.
  - **Fixed along the way.** Random chaos could apply a new fault just after `random off` had healed every route, leaving it held. A test caught it about one run in five. The fault is now applied only while the flag is on, under the flag's lock.
- Stage 5 (benchmarks) is done.
  - **The script** ([scripts/bench.sh](scripts/bench.sh), Linux) drives both brokers with the same client, Artemis's `perf client`. Each broker is an instance made by its own `create` with the NIO journal, on two cores, with the client on the others. Each scenario measures:
    - throughput, received a second with the producer unbounded;
    - latency, p50 and p99 at one rate for both, half the lower throughput;
    - peak resident memory;
    - startup, until the acceptor takes a connection, with the resident memory then.

    The scenarios are Core and AMQP, persistent and not, 1 MiB large messages in each, and 100 queues at a set total rate. Unbounded, 100 producers outran their consumers, and Artemis stalled under its backlog. `start` refuses a port still held by the last broker, which had made one run's client fail at once.
  - **Results** ([docs/benchmarks.md](docs/benchmarks.md), WSL 2 on 4 CPUs).
    - Saranga starts in 53 ms against 2.3 s and holds 19 MiB when started against 198 MiB.
    - Its peak memory is a tenth or less of Artemis's, except non-persistent AMQP: Saranga does not withhold AMQP credit from a filling address (COMPAT.md), so its backlog grows further.
    - Its throughput is 0.87 to 0.93 of Artemis's on Core, 0.75 to 0.78 on AMQP, and 1.07 to 1.08 with large messages, and both keep up with the 100 queues.
    - Its p99 at the same rate is lower in every scenario but the 100 queues.
    - Two full runs an hour apart moved some ratios by up to 0.2, so differences under 15% are a tie.
- Stage 6 (the web console) is done.
  - **The console** ([console.rs](crates/saranga-management/src/console.rs)): where `bootstrap.xml` declares the console's app, Saranga serves the `console.war` directory of the instance's `web` directory, else of the home's, with what its hawtio 4.7.0 filters and servlets do:
    - the console's own routes answered with `index.html`, its `<base href>` set to the app's URL, and a user without a session sent to `/login` unless the request carries a valid `Authorization: Basic`;
    - the JSON login form, which starts a session (the `JSESSIONID_<binding>_<port>` cookie, `HttpOnly`, `SameSite=Strict`) and throttles a user who keeps failing (429 with `Retry-After`), audited as Artemis's own filter audits it;
    - logout, `/user`, `/refresh`, a session ending after `hawtio.sessionTimeout` (1800 s) without use other than Jolokia's, the auth configuration, `/keycloak/*`, `/plugin` and `/proxy/enabled`;
    - the headers of hawtio's filters (`Content-Security-Policy`, `Strict-Transport-Security` as the profile sets it, caching) and Jetty's redirects, error pages and `If-Modified-Since`.

    Jolokia takes the session as well as Basic authentication; another user's `Authorization` ends the session.
  - **What the console needed from the Jolokia layer:**
    - `canonicalNaming=false`, which the console sends: names with their keys in registered order. The console builds its tree from that order, so with sorted keys a queue's menu had no Send, Purge, Browse or Delete;
    - hawtio's permission checks, `hawtio:type=security,area=jmx,name=ArtemisJMXSecurity` (`canInvoke` by name, method or signature, and in bulk), answered by `management.xml`'s guard or the RBAC guard;
    - the platform MBeans of the Runtime tab (`java.lang:type=Runtime`, `Memory`, `OperatingSystem`, `Threading`, `ClassLoading`), described as Artemis on OpenJDK 25 lists them and answered from the Saranga process ([platform](crates/saranga-management/src/platform));
    - `listLockCoordinatorsAsJSON` (an empty list) and the broker's `HAPolicy`, `Backup`, `SharedStore`, `Clustered`, `ReplicaSync` and `FailoverOnServerShutdown`, which had been fixed values.
  - **Tests.** [console.py](tests/interop/web/console.py) sends the same requests to Saranga and to Artemis 2.57.0 and compares statuses, headers and bodies: every route, endpoint and error, every file `index.html` loads, the login's throttling, sessions ended by logout, another user, Keycloak's check and idleness, Jolokia through a session, both naming modes and the permission checks. [web.sh](tests/interop/web/web.sh) runs it after web.py, Saranga serving the Artemis distribution's console (`ARTEMIS_DIST`), against the Artemis container or one already running (`ARTEMIS_WEB_URL`), and CI's `web` job runs it on every push. All 156 checks of both pass. In Chrome, against both brokers side by side, the console logs in and shows the Status page, connections, addresses, queues with their menus, browsing a queue's messages, the broker diagram, the JMX trees and the Runtime tab.
  - **Found along the way, and fixed.** While the disk is beyond `max-disk-usage`, Artemis refuses a send from a connection without flow control (`ServerSessionImpl.send`, `AMQ229119`) and fails the connection; Saranga accepted it. Now it does the same, checked against Artemis 2.57.0 on a disk past 90%:
    - STOMP: the ERROR carrying `AMQ229119`, then the SEND's own ERROR (`AMQ339011`) with its receipt, then the connection closes, with Artemis's `AMQ222067`, `AMQ222061` and `AMQ222107` lines;
    - MQTT: the connection closes without a PUBACK;
    - management's `sendMessage` on an address or queue: `IllegalStateException` with the `AMQ229119` text, whatever the address's `disk-full-policy`.

    Core, AMQP and OpenWire have flow control, so they are blocked or refused by the address's policy as before.
- Stage 7 (documentation) is done. [docs/guide](docs/guide/README.md) has the user guide: getting started, the CLI, configuration, protocols, security, storage, high availability, clustering, management and operations, and the migration guide from Artemis (in place with `saranga upgrade`, side by side, and without downtime through a mixed HA pair or cluster, and back again). Each page says where Saranga does as Artemis does, linking Artemis's manual, and links COMPAT.md for the differences. Every claim was checked against the code, COMPAT.md and the CLI's help, and the examples were run on throwaway instances. Checking found, and fixed:
  - `<lock-coordinators>` was ignored without the warning the other unsupported elements give;
  - COMPAT.md called the critical analyzer settings accepted silently, though they are acted on, and left `bridgeConfigurations` out of the broker properties applied;
  - COMPAT.md did not say that cluster connections have no management control, or that HORNETQ is not served;
  - `saranga run --help` said `--config` opens only the acceptors that speak CORE.
- HORNETQ is served, closing the one protocol of Artemis's Saranga lacked (left out of Phase 7's scope by omission). As in `HornetQProtocolManager`, it is Core with the `HORNETQ` handshake, which a client may leave out, and with the interceptors Artemis adds: `_HQ_` properties renamed to `_AMQ_` on sends and back on deliveries (`HQPropertiesConversionInterceptor`), and `HQ` identifiers in consumer and queue filters made `AMQ` ones (`HQFilterConversionInterceptor`) ([hornetq.rs](crates/saranga-server/src/core_protocol/hornetq.rs)). [HornetQ.java](tests/interop/hornetq/HornetQ.java), run by [hornetq-interop.sh](scripts/hornetq-interop.sh), is a HornetQ 2.4.7 JMS client on the `hornetq` acceptor: queue, topic and durable round trips, a `JMSPriority` selector, duplicate detection and scheduled delivery through `_HQ_` properties, groups, a dead-lettered message's origin and a large message. All 9 pass against both brokers. They differ in one value: Artemis's `applyPrefixForLegacyConsumer` puts `jms.queue.` on the queued message itself, so a message delivered to an old client and then dead-lettered has `jms.queue.hq.dead` as its origin in Artemis and `hq.dead` in Saranga, a difference COMPAT.md records rather than reproduces.

## How every phase is verified
- `cargo test --workspace` runs the unit tests, property tests and golden-corpus round-trips.
- `scripts/golden.sh <scenario>` records new real-broker traffic and data. `scripts/packet-fixtures.sh <group>` regenerates the Java-encoded packet fixtures.
- From Phase 2 on, an interop script runs the same Java client scenarios against Saranga.
- From Phase 3 on, a cross-store check moves data directories from Java to Saranga and from Saranga to Java.
- From Phase 9 on, CI runs a mixed Java and Saranga cluster test.
